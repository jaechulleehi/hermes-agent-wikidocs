# Hermes Agent 사례 장 확장 정리 메모

작성일: 2026-04-30
정리 상태: 2026-04-30 기준 11장 확장 반영 후 보관

## 목적

이 문서는 `11. Hermes Agent AI 업무 자동화 사례` 장을 더 매력적인 실전 레시피형 장으로 만들기 위해 작성한 내부 편집 메모다. 공개 WikiDocs 본문이 아니라, 사례 장을 보강할 때 참고하는 기획/검토 자료다.

## 외부 참고에서 얻은 신호

OpenClaw 활용서류의 강점은 기능 설명보다 독자가 바로 자기 업무에 대입할 수 있는 사례형 제목과 실습 흐름이다.

관찰한 패턴:

- 이메일 중요도 분류/답장 초안
- 파일 정리/노트 정리
- 뉴스 요약/모닝 브리핑/가격 모니터링
- 자료조사/비교표/회의자료
- PPT/문서 초안
- 블로그/콘텐츠 발행
- 멀티 에이전트 협업

우리 책에 그대로 복제하면 Hermes Agent의 차별점이 흐려진다. 대신 `역할형 에이전트 / 기억 계층 / Skill / cron / Slack / GitHub / WikiDocs 검증`이 드러나는 업무 레시피로 바꾸는 방향이 맞다.

## 현재 반영된 방향

기존에는 11장이 콘텐츠/WikiDocs/Slack 운영 사례 중심으로 보일 수 있었다. 이후 11장을 다음처럼 확장했다.

- 이메일 정리와 답장 초안
- 자료조사 결과를 비교표와 결정 메모로 바꾸는 흐름
- 매일 아침 브리핑과 주간 리포트 자동화
- 제품 요구사항 정리
- 실행/배포/검증 handoff
- 파일과 노트를 장기 기억으로 남기는 흐름
- 회의록을 보고서/발표자료로 바꾸는 흐름
- 이미지 생성 요청/검수/재사용
- Google Workspace/메일 MCP 연결
- Slack 고객응대 초안/승인/기록
- 블로그/뉴스레터 재가공
- 정기 리서치에서 의사결정 회의자료 만들기
- 크론 오류를 Skill/메모리 개선으로 바꾸는 운영 케이스

결과적으로 11장은 단순 사례 보관함보다 `이메일 / 이미지와 상세페이지 / 자료조사와 결정 메모 / 회의록과 보고서 / WikiDocs와 블로그 발행` 같은 독자 업무 기준의 레시피 장에 가까워졌다.

## 앞으로 유지할 사례 포맷

각 사례는 가능하면 아래 구조를 따른다.

1. 시작 상황: 어떤 반복 업무/불편에서 시작했나
2. 맡긴 역할: 하비/방울이/뽀동이/하망이/봉구/비벙이 중 누가 무엇을 맡았나
3. 막힌 지점: 처음에 왜 바로 자동화되지 않았나
4. 핵심 원인: 도구 문제가 아니라 운영 기준/입력/검증/권한 중 무엇이 문제였나
5. 운영 규칙: 다음부터 같은 일을 어떻게 맡길 것인가
6. 따라 하는 방법: 독자가 바로 복사해 쓸 수 있는 요청/체크리스트
7. 좋은 예와 나쁜 예: 직관적인 비교
8. 확장 아이디어: Skill/cron/MCP/Slack/GitHub/WikiDocs로 어떻게 키울 수 있나

## 11장 부모 페이지 운영 기준

11장 부모 페이지는 전체 사례를 번호순으로 나열하는 장이 아니라, 독자가 자기 업무 유형을 고르는 입구여야 한다.

유지할 구조:

- 이 장을 읽는 방법
- 먼저 고를 업무 유형
- 바로 따라 하는 대표 레시피
- 전체 사례 색인
- 사례를 읽고 남길 실행 기준
- 먼저 준비할 것
- 공통 아키텍처
- 바로 써볼 수 있는 요청 예시

## 남은 편집 메모

- 11장 하위 페이지가 많아질수록 부모 페이지는 더 짧고 길찾기 중심이어야 한다.
- 새 사례를 추가하기보다 대표 사례의 Before/After, 샘플 산출물, 30분 실습, 체크리스트를 더 깊게 만드는 편이 좋다.
- 공개 페이지에서는 내부 고객명, 실제 채널명, 토큰, 비공개 파일명, raw Slack 대화를 드러내지 않는다.
- 위험 작업은 기본적으로 `초안 생성 → 사람 승인 → 실행/발송/게시 → 기록` 순서를 둔다.
