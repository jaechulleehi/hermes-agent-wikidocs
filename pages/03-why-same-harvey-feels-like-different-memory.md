## 같은 AI 개인비서인데 기억은 왜 다르게 느껴질까

![session memory skill profile로 나뉘는 기억 구조](../assets/how-image-agent-creates-wikidocs-visuals/ch4-1-memory-layers-codex.png)

같은 AI 개인비서라도 대화마다 다르게 느껴질 수 있다. 어제는 잘 알던 기준을 오늘은 모르는 것 같고, 어떤 대화에서는 도구를 잘 쓰는데 다른 대화에서는 못 쓰는 것처럼 보인다. 이때 바로 “기억력이 나쁘다”고 보면 문제를 놓친다.

Hermes Agent에서 기억은 하나가 아니다. 현재 대화의 session, 장기 선호를 담는 memory, 에이전트별 profile, 팀 공통 원본인 shared-memory, 누적 지식이 쌓이는 Obsidian/HALOX Brain이 서로 다른 역할을 한다. 중요한 것은 많이 저장하는 것이 아니라, 맞는 층에 저장하는 것이다.

## 기억은 하나가 아니라 층이다

| 층 | 담는 것 | 넣으면 안 되는 것 |
|---|---|---|
| session | 지금 대화의 요청, 작업 범위, 최근 결정 | 다음 달에도 필요한 장기 규칙 |
| memory | 오래 유지될 선호, 반복 교정, 안정적 사실 | 일일 로그, 작업 진행 내역, 긴 초안 |
| profile | 에이전트 역할, 도구, 말투, 권한 경계 | 다른 에이전트의 임시 업무 상태 |
| shared-memory | 팀 공통 규칙, handoff, 공용 작업 원본 | 개인 취향의 장황한 기록 |
| Obsidian/HALOX Brain | 누적 지식, 모니터링 원장, 연결형 위키 | 짧은 시스템 규칙 전체 |
| GitHub/WikiDocs | 공개 문서의 원본과 배포 결과 | 비공개 운영값 |

이 구분은 [Hermes Agent 주요 개념과 기능](https://wikidocs.net/346055)의 핵심이다. memory는 모든 것을 넣는 저장소가 아니라, 다음 세션에 항상 주입되어도 좋은 작은 규칙 저장소에 가깝다.

## 실제 운영 장면: 보고 방식 피드백

한 번은 뽀동이의 보고가 너무 길다는 피드백이 있었다. 이 피드백은 단순히 “이번 답변을 짧게 하라”가 아니었다. 앞으로 반복될 선호였기 때문에 memory나 profile 운영 기준에 남기는 것이 맞다.

반대로 “이번 3장 커밋이 어디까지 됐는가” 같은 내용은 memory에 넣으면 안 된다. 그것은 세션 기록이나 GitHub 로그에서 확인할 일이다. 진행 상황을 모두 memory에 넣으면 다음 세션마다 오래된 작업 상태가 주입되어 오히려 헷갈린다.

이 차이를 이해하면 “왜 기억을 못 하지?”라는 불만이 줄어든다. AI가 잊은 것이 아니라, 찾아야 할 위치가 다른 경우가 많기 때문이다.

## 왜 같은 하비가 다르게 느껴지는가

| 상황 | 사용자가 느끼는 문제 | 실제 원인 |
|---|---|---|
| 다른 profile에서 대화함 | 같은 하비인데 도구가 다름 | profile별 권한/설정 차이 |
| 긴 대화가 압축됨 | 앞부분 합의가 약해짐 | session context가 줄어듦 |
| 작업 로그를 memory에 안 넣음 | 지난 작업을 모르는 듯함 | session_search나 GitHub 로그로 찾아야 함 |
| Obsidian과 shared-memory가 충돌함 | 어느 문서가 맞는지 애매함 | source of truth 순서 미정 |
| 공개 문서와 내부 기록이 섞임 | 독자가 볼 필요 없는 정보가 노출됨 | 공개 기준과 운영 원본 경계가 없음 |

## 운영 기준

- 반복될 선호와 역할 규칙만 memory에 남긴다.
- 작업 진행 상황은 memory보다 세션 기록, GitHub 로그, shared-memory handoff에서 찾는다.
- profile은 에이전트 정체성과 도구 경계를 나누는 단위로 본다.
- HaloX 질문은 memory만 보고 답하지 않고 Obsidian/HALOX Brain과 shared-memory를 함께 확인한다.
- 공개 글에는 독자가 몰라도 되는 사적인 운영값을 넣지 않는다.

## FAQ

### memory에 많이 넣으면 더 잘 기억하지 않나요?

아니다. memory는 항상 주입되는 정보에 가깝기 때문에 많아질수록 오히려 판단이 흐려질 수 있다. 오래 유지될 선호와 안정적 규칙만 남기는 편이 좋다.

### session_search와 memory는 어떻게 다른가요?

memory는 항상 참고할 장기 정보이고, session_search는 과거 대화에서 필요한 작업 맥락을 찾아오는 회수 도구다. WikiDocs 보강처럼 이전 세션 흐름이 필요할 때는 memory보다 session_search가 맞다.

### profile을 나누면 기억도 나뉘나요?

운영상 그렇게 느껴질 수 있다. profile은 도구, 말투, 역할, 설정이 다르기 때문에 같은 요청도 다르게 처리한다. 그래서 [역할형 에이전트](https://wikidocs.net/345925)를 운영할 때 profile 경계가 중요하다.
