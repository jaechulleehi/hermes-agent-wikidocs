## Slack 스레드에서 하비가 일을 분배하는 방식

Slack 스레드는 [Hermes Agent](https://wikidocs.net/346055) 운영에서 실제 요청이 시작되는 곳이다. 로이드는 하비에게 한 줄로 요청하고, 하비는 그 요청을 바로 처리할지, 방울이/뽀동이/하망이/봉구 같은 역할형 에이전트에게 나눌지 판단한다.

이 케이스의 핵심은 멀티봇이 동시에 말하게 만드는 것이 아니다. 하비를 [AI 개인비서 메인 창구](https://wikidocs.net/345892)로 두고, 필요한 역할만 불러서 결과를 다시 하나로 묶는 것이다. Slack은 빠른 대화 공간이지만, 기준 없이 쓰면 작업 지시, 조사 결과, 실행 보고, 사람 대화가 한곳에 섞인다. 그래서 스레드마다 “누가 창구인지”가 먼저 정해져야 한다.

## 실제 업무 상황

좋은 Slack 운영은 이렇게 흐른다.

```text
로이드: 하비야, 이 주제 콘텐츠로 만들 수 있을지 봐줘.
하비: 방울이 시켜서 확장조사하고, 뽀동이가 WikiDocs 구조로 정리하게 할게요.
방울이: 근거와 사례를 조사한다.
뽀동이: 독자 문제, 제목, 본문 구조, FAQ, 다음 링크로 바꾼다.
하비: 최종 방향과 다음 액션을 묶어 보고한다.
```

반대로 호출 규칙이 없으면 봇들이 동시에 답하고 스레드가 시끄러워진다. 7장에서 정리한 [멀티봇](https://wikidocs.net/345913) 규칙이 여기서 필요해진다.

Slack 스레드가 작업장으로 잘 굴러갈 때는 공통점이 있다. 처음 요청은 짧아도, 하비가 목적과 담당을 분리하고, 각 에이전트는 자기 역할만 수행한다. 마지막에는 하비가 다시 결과를 묶어 사용자가 다음 결정을 쉽게 하도록 만든다.

## 하비가 판단하는 기준

| 판단 | 하비가 보는 것 |
|---|---|
| 직접 답변 | 짧고 위험 낮은 질문인가 |
| 조사 위임 | 근거, 비교, 최신 정보가 필요한가 |
| 정리 위임 | 글, 문서, 보고서 구조가 필요한가 |
| 이미지 위임 | 시각 콘셉트나 썸네일이 필요한가 |
| 실행 위임 | 파일 수정, 명령, 검증이 필요한가 |
| 최종 통합 | 여러 결과를 하나로 묶어야 하는가 |

이 기준이 있으면 Slack 스레드는 작업장이 되지만 소음은 줄어든다. 핵심은 모든 일을 하비가 직접 하는 것이 아니라, 하비가 사용자의 요청을 작업 단위로 번역하고 적절한 역할로 보내는 것이다.

## 좋은 스레드와 나쁜 스레드

| 구분 | 좋은 스레드 | 나쁜 스레드 |
|---|---|---|
| 시작 | 요청 목적이 짧게 드러난다 | 질문, 잡담, 실행 요청이 섞인다 |
| 창구 | 하비가 기본 창구다 | 여러 봇이 각자 반응한다 |
| 위임 | 방울이/뽀동이/하망이/봉구 역할이 분명하다 | 누가 무엇을 맡는지 불명확하다 |
| 보고 | 완료/남음/다음이 짧게 정리된다 | 중간 결과가 길게 쌓이고 결론이 없다 |
| 기록 | 중요한 기준은 WikiDocs, skill, 체크리스트로 이동한다 | Slack에만 남아 다시 찾기 어렵다 |

이 차이는 사소해 보이지만 운영이 길어질수록 커진다. Slack은 흐름을 시작하기 좋지만, 최종 기준이 되기에는 약하다. 반복되는 판단은 [체크리스트](https://wikidocs.net/345917)나 [WikiDocs](https://wikidocs.net/345908)로 옮겨야 한다.

## 하비가 분배할 때의 실제 패턴

Slack에서 하비가 자주 하는 일은 세 가지다.

1. 요청을 다시 읽고 목적을 정한다.
2. 지금 필요한 역할을 고른다.
3. 결과를 다시 사용자 결정 단위로 묶는다.

예를 들어 “이 내용 블로그로 가능할까?”라는 요청이 들어오면 하비는 바로 긴 글을 쓰기보다 먼저 판단한다. 최신 정보가 필요한 주제면 방울이에게 확장조사를 맡기고, 이미 자료가 충분하면 뽀동이에게 구조화를 맡긴다. 이미지가 필요하면 하망이를 부르고, 파일 수정과 검증이 필요하면 봉구나 실행 흐름으로 넘긴다.

이 과정에서 중요한 것은 하비가 모든 중간 결과를 길게 다시 설명하지 않는 것이다. 사용자는 최종적으로 “진행할지/보류할지/어디를 고칠지”를 결정해야 한다. 그래서 보고는 가능한 한 짧고, 판단 근거는 필요한 만큼만 남긴다.

## 운영 기준

1. 기본 창구는 하비로 둔다.
2. [역할형 에이전트](https://wikidocs.net/345925)는 명시 호출 또는 하비의 명시 위임이 있을 때 답한다.
3. 사람 대화가 끼면 역할형 에이전트는 자동 응답을 멈춘다.
4. 하비는 위임 결과를 마지막에 하나로 묶는다.
5. 공개 콘텐츠로 바꿀 내용은 뽀동이가 독자 기준으로 다시 쓴다.
6. 반복되는 Slack 흐름은 skill, 체크리스트, WikiDocs 케이스 중 하나로 남긴다.

## FAQ

### 모든 Slack 스레드를 WikiDocs로 바꿔야 하나요?

아니다. 반복될 가능성이 있거나 독자에게 설명할 수 있는 운영 기준이 생긴 스레드만 자산화한다. 단순 확인, 일회성 실행, 민감정보가 많은 대화는 내부 기록이나 체크리스트로 남기는 편이 낫다.

### 하비가 다 쓰면 되지 왜 뽀동이가 필요한가요?

하비는 메인 창구와 최종 통합에 강하고, 뽀동이는 독자 기준 구조화와 문서 품질 관리에 강하다. 공개 글은 뽀동이가 한 번 더 다듬는 편이 안정적이다. 특히 WikiDocs처럼 책으로 읽히는 문서는 제목, 흐름, 내부 링크, FAQ, 다음 글 연결까지 함께 봐야 한다.

### 멀티봇 스레드가 시끄러워지면 어떻게 하나요?

호출 규칙을 explicit mention only로 되돌린다. 누가 말할지보다 누가 침묵할지를 먼저 정해야 한다. 이미 스레드가 복잡해졌다면 하비가 마지막에 현재 상태, 담당, 다음 액션을 다시 정리하고 이후 응답 주체를 하나로 제한한다.
