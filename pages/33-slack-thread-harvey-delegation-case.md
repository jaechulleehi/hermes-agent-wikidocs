## Slack 스레드에서 하비가 일을 분배하는 실제 방식

AI 개인비서를 메인 창구로 둔다는 말은 사용자가 모든 에이전트를 직접 불러야 한다는 뜻이 아니다. 사용자는 하비에게 방향을 말하고, 하비가 필요한 경우 방울이, 뽀동이, 하망이, 실행형 에이전트로 일을 나누는 구조가 더 안정적이다.

Slack 스레드는 이 구조가 가장 잘 드러나는 공간이다. 대화가 빠르게 오가고, 사람과 여러 봇이 섞일 수 있기 때문에 메인 창구, 호출 규칙, handoff 기준이 없으면 금방 시끄러워진다.

## 실제 업무 상황

로이드가 Slack에서 “이 내용도 WikiDocs에 올릴 만하지 않아?”라고 말하면, 하비는 단순히 “좋아요”라고 답하는 데서 끝나면 안 된다. 먼저 이 내용이 어느 장에 들어갈지 판단하고, 필요한 역할을 나눠야 한다.

```text
로이드: 방향 제시
하비: 책 구조와 우선순위 판단
방울이: 필요한 경우 확장조사
뽀동이: 글 구조와 발행 기준 정리
하망이: 필요한 경우 이미지 방향 정리
실행형 에이전트: 파일 수정, 검증, 커밋, push
하비: 최종 통합과 보고
```

## 왜 메인 창구가 필요한가

여러 에이전트가 각자 답하면 사용자는 편해지는 게 아니라 더 피곤해진다. 조사형은 근거를 더 모으자고 하고, 정리형은 구조를 바꾸자고 하고, 실행형은 파일을 고치려 한다. 이때 누가 최종 판단을 하는지 없으면 스레드는 길어지고 결론은 흐려진다.

하비의 역할은 모든 일을 직접 하는 것이 아니라, 다음 네 가지를 정하는 것이다.

1. 지금 바로 답할 일인가?
2. 조사형 에이전트가 더 봐야 하는가?
3. 정리형 에이전트가 문서 구조로 바꿔야 하는가?
4. 실행형 에이전트가 실제 파일을 고쳐도 되는가?

## Slack 스레드 운영 기준

- 사용자가 특정 에이전트를 부르면 그 에이전트가 응답한다.
- 여러 봇이 있는 스레드에서는 호출받지 않은 봇이 끼어들지 않는다.
- 사람이 대화에 다시 끼면 자동 응답을 멈추고 직접 호출을 기다린다.
- 하비가 최종 통합을 맡을 때는 역할별 결과를 짧게 묶는다.
- 뽀동이는 문서/콘텐츠 구조와 최종 산출물 품질을 맡는다.
- 실행형 에이전트가 파일을 수정할 때는 범위와 검증 기준이 있어야 한다.

## 케이스를 글로 바꾸는 기준

Slack 대화가 곧바로 WikiDocs 글이 되지는 않는다. 스레드에는 맥락 생략, 내부 표현, 임시 판단이 많기 때문이다. 글로 바꾸기 전에 다음을 정리한다.

| Slack 대화 요소 | WikiDocs 변환 방식 |
|---|---|
| 즉흥 아이디어 | 독자 문제로 재정의 |
| 내부 이름 | 공개 개념을 먼저 설명한 뒤 사례로 사용 |
| 링크/스레드 맥락 | 필요한 내용만 요약하고 민감정보 제거 |
| 실행 지시 | 운영 기준과 체크리스트로 변환 |
| 완료 보고 | 결과보다 재사용 가능한 흐름을 설명 |

## 재사용 체크리스트

- 이 스레드에서 실제 독자에게 도움이 되는 문제는 무엇인가?
- 메인 창구가 판단한 기준이 드러나는가?
- 역할형 에이전트의 입력과 출력이 분리되어 있는가?
- 공개하면 안 되는 채널 링크나 계정 정보가 제거되어 있는가?
- 단발 대화가 아니라 반복 가능한 운영 케이스로 바뀌었는가?
- 마지막에 FAQ, 체크리스트, 다음 링크가 붙어 있는가?

## FAQ

### 모든 Slack 스레드를 WikiDocs로 바꿔야 하나?

아니다. 반복될 가능성이 있고, 독자가 자기 업무에 적용할 수 있는 판단 기준이 있을 때만 책으로 옮긴다.

### 하비가 다 쓰면 되지 왜 뽀동이가 필요한가?

하비는 메인 창구와 최종 통합에 강하다. 하지만 공개 글은 구조, 독자 흐름, 제목, CTA, WikiDocs 기준까지 봐야 한다. 이 부분은 정리형 에이전트가 맡는 편이 품질이 안정적이다.

### 멀티봇 스레드가 시끄러워지면 어떻게 하나?

호출 규칙을 우선한다. 누가 응답해야 하는지 명확하지 않으면 메인 창구만 답하고, 나머지는 직접 호출될 때까지 기다리는 편이 낫다.
