## 3장. 조사형/정리형/실행형 에이전트 나누기

![3장 조사형 정리형 실행형 에이전트 역할 분리](../assets/images/chapter-heroes/ch03-role-agent-splitting-codex.png)

[AI 개인비서 메인 창구](https://wikidocs.net/345891)가 잡히면 다음 문제는 역할 분리다. 하비가 모든 일을 직접 처리하면 병목이 생기고, 반대로 기준 없이 에이전트를 늘리면 누가 무엇을 책임지는지 흐려진다. 그래서 3장은 [Hermes Agent 주요 개념과 기능](https://wikidocs.net/346055) 중에서도 역할형 에이전트를 실제 운영 기준으로 나누는 장이다.

로이드의 운영에서는 이 문제가 Slack 스레드에서 바로 드러났다. 처음에는 “이 글을 정리해줘”, “이 흐름을 봐줘”처럼 한 문장으로 시작했지만, 실제 작업은 금방 여러 갈래로 나뉘었다. 원문과 공식 문서를 확인해야 했고, 이전 블로그가 잘 옮겨졌는지도 봐야 했고, 본문 링크가 독자 흐름 안에서 작동하는지도 검수해야 했다. 이 일을 한 에이전트에게 모두 맡기면 결과는 빨라 보여도 약해진다.

그래서 하비는 메인 창구로 요청을 받고, 방울이는 조사형 에이전트로 근거와 누락을 찾고, 뽀동이는 정리형 에이전트로 독자 흐름과 문장 구조를 다듬는다. 실행형 에이전트는 파일 수정, 검증, 커밋처럼 되돌리기와 확인이 필요한 일을 맡는다. 하망이 같은 이미지 제작형 에이전트는 메시지를 시각 자산으로 바꾼다. 핵심은 이름이 아니라 책임 경계다.

## 이 장에서 다루는 문제

역할형 에이전트는 “AI를 많이 띄우는 방법”이 아니다. 실패가 생겼을 때 원인을 찾기 쉽게 만드는 운영 구조다.

| 문제 상황 | 한 에이전트에게 몰아줄 때 | 역할을 나눌 때 |
|---|---|---|
| 새 주제 조사 | 빠른 결론은 나오지만 근거와 미확인이 섞인다 | 방울이가 사실/해석/미확인을 나눠 넘긴다 |
| WikiDocs 페이지 보강 | 문장은 늘지만 독자 흐름이 약해질 수 있다 | 뽀동이가 원자료와 독자 문제를 기준으로 구조화한다 |
| 파일 수정/검증 | 글쓰기 중간에 실행 실수가 섞일 수 있다 | 실행형이 변경 범위와 검증 결과를 분리한다 |
| 이미지 제작 | 예쁜 그림은 나오지만 메시지와 어긋날 수 있다 | 하망이가 페이지 핵심 메시지와 QA 기준을 따른다 |
| 최종 보고 | 중간 결과가 흩어진다 | 하비가 완료/남음/다음을 통합한다 |

이 장은 특히 조사형과 정리형의 차이를 자세히 본다. 방울이와 뽀동이는 둘 다 콘텐츠 흐름에 참여하지만, 실패하는 방식이 다르기 때문이다.

## 실제 운영에서 역할이 갈라진 순간

Hermes WikiDocs 보강 작업을 보면 역할 분리의 이유가 선명해진다. 로이드는 “블로그 내용을 잘 옮겼는지”, “공식 docs가 잘 반영됐는지”, “처음 보는 독자에게 축약되어 보이지 않는지”를 동시에 물었다. 이 요청은 단순 글쓰기 요청이 아니다.

먼저 필요한 것은 조사다. 기존 블로그 1~27편이 어디에 매핑됐는지, 공식 Hermes Agent docs 중 어떤 주제가 책의 어느 장에 들어갔는지, WikiDocs의 본문 링크가 실제 페이지 URL로 연결되는지 확인해야 한다. 이 영역은 [조사형 에이전트](https://wikidocs.net/345895)가 강하다.

다음으로 필요한 것은 정리다. 조사 결과를 그대로 붙이면 독자는 따라오지 못한다. “왜 챗봇이 아니라 AI 팀인가”, “하비는 왜 메인 창구인가”, “방울이와 뽀동이는 왜 다르게 실패하는가”처럼 책의 흐름으로 다시 배치해야 한다. 이 영역은 [정리형 에이전트](https://wikidocs.net/345896)가 강하다.

마지막으로 필요한 것은 실행과 검증이다. 링크를 바꾸고, 페이지를 고치고, H1 금지/이미지 경로/중점 문자/민감정보 패턴을 검사한 뒤 GitHub에 커밋하고 push해야 한다. 이 영역은 실행형 기준이 필요하다.

## 처음에 생기는 착각

처음 역할형 에이전트를 만들 때 가장 흔한 착각은 “역할을 나누면 관리가 복잡해진다”는 것이다. 실제로는 반대다. 역할을 나누지 않으면 결과가 틀렸을 때 질문이 더 복잡해진다.

예를 들어 WikiDocs 페이지가 약해 보인다고 하자. 이때 원인이 무엇인지 나눠야 한다.

- 원자료가 부족한가?
- 공식 문서 확인이 빠졌는가?
- 독자 흐름이 끊겼는가?
- 본문 링크가 약한가?
- 검증 없이 발행됐는가?

이 질문들이 모두 한 대화 안에 섞이면 “다시 잘 써줘”라는 요청만 반복된다. 하지만 조사형/정리형/실행형을 나누면 교정 지점도 나뉜다. 방울이에게는 근거와 누락을 다시 보게 하고, 뽀동이에게는 흐름과 문체를 다시 보게 하고, 실행형에게는 변경 파일과 검증 결과를 다시 보게 한다.

## 이 장에서 얻을 기준

3장을 읽고 나면 역할형 에이전트를 다음 기준으로 나눌 수 있어야 한다.

| 기준 | 질문 | 맡길 역할 |
|---|---|---|
| 사실 확인 | 무엇이 맞고 무엇이 미확인인가? | 조사형 |
| 구조화 | 독자가 어떤 순서로 이해해야 하는가? | 정리형 |
| 실행 | 어떤 파일/도구/명령을 실제로 바꿔야 하는가? | 실행형 |
| 시각화 | 핵심 메시지를 어떤 이미지로 보여줄 것인가? | 이미지형 |
| 통합 | 누가 최종 판단과 보고를 묶을 것인가? | 메인 창구 |

이 기준은 사람 조직에도 그대로 적용된다. 역할을 나누는 목적은 개성을 꾸미는 데 있지 않다. 책임 경계를 만들고, 품질 검수 위치를 만들고, 실패했을 때 되돌아갈 지점을 만드는 데 있다.

## 다음 장으로 가기 전 체크 질문

3장을 읽을 때는 아래 질문을 붙잡고 보면 좋다.

1. 지금 맡기려는 일은 조사인가, 정리인가, 실행인가?
2. 결과가 틀렸을 때 어느 지점을 다시 확인해야 하는가?
3. 최종 답변을 누가 통합해야 하는가?
4. 민감정보나 내부 디테일을 누가 제거해야 하는가?
5. 결과가 재사용 가능한 기록으로 남는가?

이 질문에 답하지 않고 에이전트만 늘리면 멀티 에이전트가 아니라 멀티 혼선이 된다.
