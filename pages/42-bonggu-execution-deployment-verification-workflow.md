## 봉구는 실행/배포/검증을 어떻게 이어받을까

AI 업무 자동화에서 실행형 에이전트는 가장 편하지만 가장 위험한 역할이다. 파일을 고치고, 명령을 실행하고, 배포까지 이어갈 수 있기 때문이다. 그래서 봉구 같은 실행형 에이전트에게는 “빨리 해줘”보다 “무엇을 어디까지 바꾸고 어떻게 검증할지”를 먼저 줘야 한다.

이 사례의 핵심은 실행 자체가 아니라 실행 전후의 경계다. 요청 범위, 변경 파일, 검증 명령, 실패 시 중단 기준이 있어야 실행형 에이전트가 안정적으로 일한다.

## 시작 상황

문서나 코드 작업이 어느 정도 정리되면 마지막에는 실제 파일 수정이 필요하다. WikiDocs 문서를 고치고, TOC를 바꾸고, 링크를 검증하고, GitHub에 푸시하는 작업이 대표적이다.

이때 봉구에게 바로 맡길 수 있는 일은 아래처럼 명확해야 한다.

| 작업 | 실행 전 필요한 기준 |
|---|---|
| Markdown 수정 | 대상 파일, 변경 목적, 금지 표현 |
| 이미지 연결 | asset 위치, 상대 경로, 캡션 기준 |
| 검증 명령 실행 | 링크 검사, H1 검사, 중점 문자 검사 |
| Git 커밋/푸시 | 커밋 범위, 포함하지 않을 파일 |
| 배포 확인 | GitHub 원본과 WikiDocs 공개본 확인 |

## 맡긴 역할

| 역할 | 담당 |
|---|---|
| 하비 | 실행해도 되는 범위와 우선순위를 판단한다 |
| 뽀동이 | 문서 구조와 문체 기준을 정리한다 |
| 봉구 | 파일 수정, 명령 실행, 테스트, 커밋/푸시를 맡는다 |
| 하비 또는 사람 | 최종 공개 반영과 위험 변경을 승인한다 |

## 막힌 지점

실행형 에이전트가 흔들리는 지점은 보통 두 가지다.

첫째, 바꿔야 할 파일이 불명확하다. 둘째, 성공 기준이 “잘 됐는지 봐줘”처럼 흐릿하다. 이 상태에서 실행하면 변경 범위가 커지고, 검증 없이 완료 보고가 나올 수 있다.

## 운영 규칙

봉구에게 실행을 맡길 때는 아래 순서를 지킨다.

1. 변경 대상 파일과 제외 파일을 먼저 적는다.
2. 실행 전 현재 상태를 확인한다.
3. 작은 단위로 수정한다.
4. 검증 명령을 실행한다.
5. 실패하면 수정 범위를 넓히기보다 원인을 보고한다.
6. 커밋/푸시는 검증 통과 후 진행한다.
7. 공개 채널 반영까지 확인한 뒤 완료 보고한다.

## 따라 하는 방법

```text
봉구야, 아래 범위만 실행해줘.

목표:
11장 사례 페이지 1개를 추가하고 TOC에 연결한다.

범위:
- 수정 가능: TOC.md, pages/10-chapter-10.md, 새 pages/*.md 1개
- 수정 금지: README.md, 기존 0~10장 본문

검증:
- TOC 링크가 모두 존재하는지 확인
- pages 본문에 H1이 없는지 확인
- 중점 문자가 없는지 확인
- git diff로 변경 범위 보고

검증 통과 후에만 커밋/푸시해줘.
```

## 좋은 예와 나쁜 예

| 구분 | 예시 |
|---|---|
| 나쁜 예 | “문서 좀 고치고 올려줘” |
| 좋은 예 | “TOC와 11장 부모 페이지, 새 사례 파일 1개만 수정하고 링크/H1/문체 검증 후 커밋해줘” |

## 체크리스트

- 수정 가능 파일과 금지 파일을 나눴는가?
- 실행 전 `git status`를 확인했는가?
- 검증 명령을 명시했는가?
- 커밋에 내부 메모나 임시 파일이 섞이지 않았는가?
- 공개 반영까지 확인했는가?

## 확장 아이디어

봉구의 실행 흐름은 문서뿐 아니라 배포, 데이터 정리, 이미지 일괄 생성, 리포트 자동 발송에도 적용할 수 있다. 단, 실행 권한이 커질수록 승인 지점을 더 앞에 둬야 한다. 특히 삭제, 결제, 외부 발송, 고객 데이터 변경은 자동 실행보다 사람 승인 흐름을 먼저 설계해야 한다.
