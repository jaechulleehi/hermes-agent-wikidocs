## 부록 A-5. 바로 복사해서 쓰는 자동화 템플릿

이 부록은 11장의 사례를 실제 업무에 바로 적용하기 위한 복사용 템플릿이다. 긴 설명을 다시 읽기보다, 지금 줄이고 싶은 업무에 맞는 템플릿 하나를 골라 Slack, CLI, 메일 MCP, WikiDocs 작업에 붙이면 된다.

중요한 원칙은 하나다. 자동화는 “알아서 다 해줘”가 아니라 `입력 → 역할 분리 → 중간 판단 → 사람 승인 → 검증 → 다음 기준으로 저장`의 흐름으로 설계해야 한다. 특히 Hermes Agent의 강점은 결과물을 한 번 만드는 데서 끝나지 않고, 반복 기준을 memory와 Skill로 나눠 다음 작업 품질을 올리는 데 있다.

## 템플릿을 쓰기 전 확인할 것

| 확인 질문 | 이유 |
|---|---|
| 이 업무는 한 번만 할 일인가, 반복될 일인가 | 반복되면 Skill 후보가 된다 |
| AI가 바로 실행해도 되는가, 초안만 만들어야 하는가 | 메일/고객응대/계약/권한 작업은 승인 지점이 필요하다 |
| 결과물은 어디에 남길 것인가 | Slack에만 남기면 다시 찾기 어렵다 |
| 다음에도 같은 기준을 써야 하는가 | memory, shared-memory, Skill 중 위치를 정해야 한다 |
| 공개 문서로 옮겨도 되는가 | 내부 값, 고객명, 토큰, URL은 제거해야 한다 |

## 1. 메일 정리와 답장 초안 템플릿

```text
하비야, 최근 메일 중 확인이 필요한 것만 정리해줘.

대상:
- 기간: 최근 24시간
- 범위: 고객/파트너/일정 관련 메일만
- 제외: 뉴스레터, 광고, 자동 알림

출력 형식:
1. 바로 답장할 메일
2. 일정/할 일로 바꿀 메일
3. 보류하거나 추가 확인할 메일
4. 삭제 또는 무시해도 되는 후보

각 항목에는 아래를 넣어줘.
- 보낸 사람
- 핵심 요청
- 필요한 액션
- 답장 초안 여부
- 사람 확인 필요 여부

주의:
- 실제 발송은 하지 마.
- 가격, 계약, 일정 확정, 계정 정보는 사람 확인 필요로 표시해줘.
- 반복되는 분류 기준이 보이면 Skill 후보로 따로 정리해줘.
```

### 결과물 체크

| 확인할 것 | 통과 기준 |
|---|---|
| 분류 | 바로 답장/일정/보류/무시 후보가 분리됐는가 |
| 승인 | 자동 발송이 아니라 초안/승인 흐름인가 |
| 위험 정보 | 계약/가격/계정/개인정보가 사람 확인으로 표시됐는가 |
| 다음 기준 | 반복 분류 기준이 memory나 Skill 후보로 분리됐는가 |

## 2. 자료조사에서 결정 메모 만들기 템플릿

```text
방울이는 아래 주제를 조사해줘.

주제:
[조사 주제]

최종 목적:
링크 목록이 아니라 선택 가능한 결정 메모를 만들고 싶어.

조사 기준:
1. 선택지 3개 이하
2. 공식 문서 또는 신뢰 가능한 출처 우선
3. 각 선택지의 장점/약점/비용/운영 리스크
4. 아직 불확실한 부분
5. 반례나 주의할 점

뽀동이가 이어받을 수 있게 아래 형식으로 넘겨줘.
- 결론 후보
- 비교표 재료
- 추천안
- 리스크
- 다음 액션
```

```text
뽀동이는 방울이 조사 결과를 결정 메모로 바꿔줘.

형식:
1. 결론 먼저
2. 선택지 비교표
3. 선택 기준
4. 리스크
5. 이번 주에 할 다음 액션
6. 추가 확인 질문

주의:
- 링크를 많이 보여주는 것보다 판단 기준을 선명하게 해줘.
- 사실과 추정을 분리해줘.
- 추천안이 있으면 왜 그 선택이 맞는지 한 문장으로 설명해줘.
```

### 결과물 체크

| 확인할 것 | 통과 기준 |
|---|---|
| 결정 질문 | “무엇을 선택할 것인가”가 보이는가 |
| 비교표 | 실제 선택 기준이 컬럼에 들어갔는가 |
| 출처 | 공식 문서/사례/의견성 글이 구분됐는가 |
| 다음 액션 | “추가 조사”가 아니라 실행 가능한 액션인가 |

```text
화면 구성:
- 왼쪽:
- 가운데:
- 오른쪽:

스타일:
- 분위기:
- 색감:
- 비율:
- 텍스트 사용량:
```

### 상세페이지 섹션 구조

```text
1. 문제 제기: 독자가 지금 겪는 불편
2. 해결 흐름: Hermes Agent가 요청을 받고 역할형 에이전트로 나눔
3. 사용 장면: 메일 / 자료조사 / 이미지 / 문서 발행
4. 결과물: 답장 초안 / 비교표 / 이미지 asset / 공개 문서
5. 검증: 사람 승인 / 링크 확인 / vision QA / 공개 반영 확인
6. CTA: 내 업무에서 먼저 자동화할 일 하나 고르기
```

```text

요청 원문:
[Slack 요청 붙여넣기]

나눌 기준:
1. 하비가 직접 판단할 것
2. 방울이가 조사할 것
3. 뽀동이가 구조화할 것
4. 하망이가 이미지 방향을 잡을 것
5. 봉구가 실행/검증할 것
6. 비벙이가 제품 요구사항으로 바꿀 것

출력 형식:
```

## 5. WikiDocs / 블로그 발행 검증 템플릿

```text
뽀동이는 원고를 WikiDocs용으로 정리하고, 봉구는 검증/발행 흐름을 확인해줘.

검증 항목:
1. TOC 링크가 맞는가
2. 페이지 본문에 H1을 쓰지 않았는가

4. 이미지 경로가 assets 기준으로 맞는가
5. 중점 문자 대신 슬래시를 썼는가
6. 내부 정보, 토큰, 고객명, 개인 경로가 제거됐는가
7. GitHub commit/push 후 WikiDocs 공개 반영을 확인했는가

완료 보고 형식:
- 완료:
- 검증:
- 커밋:
- 공개 확인:
- 남은 것:
```

## 6. Skill 만들기 판단 템플릿

```text
이 작업을 Skill로 남길지 판단해줘.

작업 내용:
[반복된 작업 설명]

확인 질문:
1. 같은 작업이 앞으로도 반복되는가?
2. 실행 순서가 어느 정도 고정되어 있는가?
3. 실패 패턴이나 주의점이 분명한가?
4. 검증 방법이 있는가?
5. 특정 프로젝트/계정/토큰에만 묶이지 않는가?
6. 공개 Skill과 내부 Skill 중 어디에 가까운가?

출력:
- Skill로 만들지 여부
- Skill에 넣을 절차
- Skill에 넣으면 안 되는 정보
- 검증 단계
- 나중에 보강해야 할 조건
```

### Skill 후보 예시

| 반복 업무 | Skill 후보가 되는 이유 |
|---|---|
| WikiDocs 발행 검증 | TOC, H1, 이미지, 공개 반영 확인이 반복된다 |
| 이미지 생성 후 vision QA | 메시지, 텍스트, 잘림, 과장 여부를 매번 본다 |
| 크론 오류 복구 | schedule/tool/model/delivery 레이어 구분이 반복된다 |
| 자료조사 결정 메모화 | 조사 결과를 비교표/추천안/다음 액션으로 바꾸는 흐름이 반복된다 |

## 7. 크론 오류 복구 템플릿

```text
하비야, 이 cron 실패를 단순 로그 요약이 아니라 재발 방지 기준으로 정리해줘.

오류 상황:
[오류 로그 또는 현상]

분류 기준:
1. schedule 문제인가?
2. prompt가 fresh session에서 혼자 실행 가능한가?
3. toolset이나 권한 문제가 있는가?

5. delivery target 문제가 있는가?
6. workdir/context_from/script 설정 문제가 있는가?

출력 형식:
- 증상
- 원인 후보
- 확인한 것
- 수정할 것
- 다음 실행 전 체크리스트
- memory로 남길 것
- Skill로 보강할 것
```

## 10. 압축 실패 복구 템플릿

```text
압축 실패 메시지가 나왔어. 이걸 단순 오류 요약이 아니라 복구 체크리스트로 정리해줘.

오류 메시지:
[Compression summary failed 또는 fallback marker 메시지]

확인할 것:
1. 압축 요약에 쓰는 summary_model은 무엇인가?
2. summary_provider는 무엇인가?
3. 해당 provider를 호출할 API key가 active profile에 있는가?
4. 일반 대화 모델과 압축 요약 모델이 서로 다른 경로를 쓰고 있지는 않은가?
5. threshold / target_ratio / protect_last_n 값이 작업 성격에 맞는가?
6. Slack에서 수동 압축을 쓰려면 slash command가 manifest에 등록되어 있는가?

출력 형식:
- 증상:
- 원인 후보:
- 확인한 설정:
- API/provider 점검:
- 권장 수정:
- 압축 후 재개 handoff:

주의:
- API key 값은 절대 출력하지 마.
- “키가 있다/없다”, “어느 provider를 쓰는지”만 말해줘.
```

## 이 부록을 쓰는 기준

이 템플릿들은 그대로 외우기 위한 문장이 아니다. 처음에는 복사해서 쓰고, 실제 운영에서 자주 바뀌는 부분은 팀 기준에 맞게 줄이면 된다. 중요한 것은 매번 더 긴 프롬프트를 쓰는 것이 아니라, 반복 업무가 생길 때마다 `기억할 것 / 절차화할 것 / 검증할 것 / 공개할 것`을 나누는 습관이다.

Hermes Agent의 강점은 여기서 나온다. 한 번의 작업이 끝나도 그 기준이 memory, Skill, WikiDocs, 체크리스트로 남으면 다음 작업은 처음부터 다시 시작하지 않는다.
