## 실제 운영 케이스로 보는 하망이 WikiDocs 이미지 제작

이 케이스는 하망이가 WikiDocs 책 이미지를 만들며 겪은 실제 운영 기록이다. 겉으로 보면 “AI로 이미지를 몇 장 만들었다”에 가깝지만, 실제로는 훨씬 복잡했다. 어떤 이미지를 먼저 만들지 정하고, Codex-only로 갈지 판단하고, 한글 라벨을 줄이고, 생성 결과를 QA하고, 파일을 GitHub/WikiDocs 자산으로 편입하는 흐름까지 이어졌다.

이 사례를 따로 남기는 이유는 성공 결과보다 시행착오가 더 중요하기 때문이다. 이미지형 에이전트는 예쁜 이미지를 빠르게 뽑을 수 있다. 하지만 WikiDocs 책에 들어갈 이미지는 예쁘기만 해서는 부족하다. 독자에게 페이지 메시지를 설명해야 하고, 책 전체의 톤과 이어져야 하며, GitHub 연동 구조에서도 깨지지 않아야 한다.

## 시작점: 표지를 만들자는 요청에서 운영 시스템으로 확장됐다

처음 요청은 단순했다. WikiDocs 책 표지가 필요하다는 이야기였다. 책 제목은 `에르메스 에이전트(Hermes Agent) 업무 자동화: 나만의 AI 팀 만들기`였고, Codex로 만들어보자는 방향이 있었다.

여기서 바로 표지 하나만 만들 수도 있었다. 하지만 실제 운영에서는 표지보다 먼저 물어야 할 질문이 있었다.

- 이 책의 전체 시각 톤은 무엇인가?
- 상위 장마다 대표 이미지를 둘 것인가?
- 하위 페이지마다 이미지를 만들 것인가?
- 이미지 안에 한글을 어느 정도까지 넣을 것인가?
- Codex-only로 충분한가, 아니면 구조형 이미지는 HTML-to-PNG가 맞는가?

하망이는 먼저 상위 장 대표 이미지를 잡는 쪽으로 정리했다. 1장은 책 전체에서 가장 중요한 관점 전환을 담당한다. “AI 챗봇이 아니라 AI 팀”이라는 메시지가 여기서 선명해야 뒤의 장들도 같은 흐름으로 이어진다.

## 1차 판단: 하위 페이지보다 1장 대표 이미지가 먼저였다

로이드는 처음에 1장, 1-1장, 1-2장처럼 각 장과 하위 페이지까지 대표 이미지를 만드는 구조인지 물었다. 이 질문은 중요했다. 범위를 잘못 잡으면 이미지를 많이 만들고도 책 전체의 시각 기준이 흔들릴 수 있기 때문이다.

하망이는 이렇게 판단했다.

```text
먼저 상위 장 대표 이미지를 만든다.
그 이미지로 전체 스타일 기준을 잡는다.
그다음 필요한 하위 페이지 이미지만 확장한다.
```

이 판단 덕분에 1장 대표 이미지는 단순한 한 장짜리 결과물이 아니라, 이후 1-1, 1-2 이미지의 기준점이 되었다. 1장 대표 이미지의 핵심 메시지는 `단일 챗봇 → AI 팀 → 운영 구조`였다. 이 메시지는 책 전체의 첫 관문이다.

## 2차 판단: Codex-only로 가되 한글을 짧게 제한했다

이번 작업은 Codex-only로 진행했다. 다만 Codex-only는 한글 텍스트에서 리스크가 있다. 긴 문장을 넣으면 글자가 깨지거나, 의미 없는 가짜 텍스트가 생기거나, 일부 단어가 흐려질 수 있다.

그래서 하망이는 이미지 안 텍스트를 짧게 제한했다. 1장 대표 이미지에서는 `01`, `왜 챗봇이 아니라 AI 팀인가`, `챗봇`, `AI 팀`, `운영 구조` 정도만 허용했다. 1-1 이미지에서는 `챗봇`, `답변`, `AI 개인비서`, `업무 흐름`만 남겼다.

## 3차 판단: 1-1 이미지는 메시지를 한 문장으로 줄였다

1-1 페이지의 제목은 `AI 챗봇과 AI 개인비서는 어떻게 다를까`다. 하망이가 잡은 메시지는 “챗봇은 답변 도구이고, AI 개인비서는 업무 흐름을 관리한다”였다.

![AI 챗봇과 AI 개인비서의 차이를 보여주는 WikiDocs 본문 이미지](../assets/how-image-agent-creates-wikidocs-visuals/ch1-1-chatbot-vs-ai-assistant-codex.png)

결과물은 본문 이미지로 사용할 수 있었다. 하지만 “완벽해서 통과”가 아니었다. QA 중 로봇 스카프 쪽에 아주 작은 생성 아티팩트가 보였다. 하망이는 이를 숨기지 않고, 일반 삽입 크기에서는 거의 보이지 않으므로 현재본 사용 가능하다고 기록했다. 이 작은 기록이 운영 품질을 만든다.

## 4차 판단: 1-2부터 1-5까지 한 번에 가려다 속도와 안정성을 다시 봤다

1-1이 통과하자 로이드는 같은 톤과 캐릭터를 유지하면서 1-2부터 1-5까지 이어서 만들자고 했다. 하망이는 1-1의 스타일 기준을 크림 배경, 금색 포인트, 둥근 AI 비서 캐릭터, 교육용 editorial 톤, 16:9 본문 대표 이미지로 정리했다.

그런데 실제 생성 과정은 오래 걸렸다. 본문을 다시 읽고, 각 절의 메시지를 뽑고, 이미지 생성 프로세스를 돌리고, 결과 파일을 확인해야 했다. 중간에는 15분, 18분, 21분까지 “아직 작업 중”인 상태가 보였다.

![나만의 AI 팀 구성을 보여주는 WikiDocs 본문 이미지](../assets/how-image-agent-creates-wikidocs-visuals/ch1-2-my-ai-team-codex.png)

이 장면에서 중요한 배움은 이것이다. 이미지 생성은 결과물이 보일 때까지 오래 걸릴 수 있고, 오래 걸리는 동안 운영자는 프로세스가 살아 있는지, 결과 파일이 생겼는지, 중간에 멈췄는지를 확인해야 한다. 따라서 여러 장을 한 번에 맡길 때는 반드시 작은 단위로 끊어야 한다.

## 5차 판단: 스크립트 실패를 숨기지 않고 안전하게 재시도했다

1장 대표 이미지를 로컬 repo에 넣는 과정에서는 스크립트 따옴표 실수가 있었다. 하망이는 “파일은 아직 안 건드렸고, 다시 안전하게 적용한다”고 보고했다. 이 말이 중요한 이유는 파일 작업의 신뢰 때문이다. 무엇이 실패했는지, 파일이 바뀌었는지, 재시도해도 안전한지 알려야 한다.

## 6차 판단: GitHub 인증은 이미지 작업의 일부가 아니지만 발행의 일부다

이미지를 만들고 본문에 넣어도 GitHub에 push되지 않으면 GitHub 연동 WikiDocs에는 반영되지 않는다. 이때 하망이 프로필에서는 GitHub 인증이 없어서 push가 막혔다. 그래서 `gh auth login` device login을 열고, 로이드가 코드를 입력한 뒤 push를 마무리했다.

이 장면도 운영 케이스로 남길 가치가 있다. 이미지 제작 자체는 성공했지만, 발행 파이프라인은 인증에서 막힐 수 있다. 그리고 GitHub 연동 WikiDocs에서는 발행 파이프라인까지 끝나야 작업이 끝난다.

## 이 케이스를 어디에 두는 게 좋은가

이 사례는 두 층으로 나누는 게 좋다.

첫째, 6장 콘텐츠 시스템에는 운영 기준을 둔다. `이미지형 에이전트로 WikiDocs 본문 이미지를 만드는 법`처럼 정리하면 독자가 바로 재사용할 수 있다.

둘째, 실제 운영 케이스 장에는 지금처럼 시행착오의 흐름을 남긴다. 표지 요청에서 시작해 1장 대표 이미지, 1-1 이미지, 1-2 이후 확장, 스크립트 실패, 인증 이슈까지 이어진 과정을 기록하면 “우리의 실제 운영 방식”이 보인다.

## 체크리스트

- 이 작업이 표지, 장 대표 이미지, 하위 페이지 이미지 중 무엇인지 정했는가?
- 먼저 스타일 기준이 될 대표 이미지를 만들었는가?
- 페이지 메시지를 한 문장으로 줄였는가?
- 이미지 안 한글 라벨을 충분히 줄였는가?
- 한글 오탈자, 가짜 텍스트, 워터마크, 잘림을 QA했는가?
- 작은 아티팩트가 있다면 사용 가능 여부를 기록했는가?
- 결과 파일을 `assets/` 아래로 편입했는가?
- 본문 상대 경로가 깨지지 않는가?
- 커밋 범위를 의도한 파일로 제한했는가?
- GitHub push까지 완료했는가?
