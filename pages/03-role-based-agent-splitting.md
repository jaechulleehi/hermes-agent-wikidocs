## 역할형 에이전트는 어떤 기준으로 나눌까

역할형 에이전트는 “누가 더 잘하느냐”가 아니라 “어떤 실패를 줄이느냐”를 기준으로 나눈다. 좋은 역할 분리는 일을 예쁘게 분류하는 것이 아니라, 문제가 생겼을 때 어디를 고쳐야 하는지 보이게 만든다.

예를 들어 글이 약할 때 원인은 여러 가지일 수 있다. 근거가 부족해서 약할 수도 있고, 구조가 나빠서 약할 수도 있고, 검증 없이 발행돼서 약할 수도 있다. 이 세 문제를 한 역할에 모두 묶으면 “다시 잘해줘”라는 말만 반복된다.

## 역할을 나누는 첫 번째 기준: 실패 패턴

| 실패 신호 | 필요한 역할 | 확인할 것 |
|---|---|---|
| 근거가 얕다 | 조사형 | 출처, 날짜, 반례, 누락 범위 |
| 글은 매끄럽지만 속이 비었다 | 정리형 | 독자 문제, 실제 장면, 판단 기준 |
| 말은 맞지만 실행되지 않았다 | 실행형 | 변경 범위, 검증 결과, 되돌릴 방법 |
| 이미지가 예쁘지만 메시지가 약하다 | 이미지형 | 핵심 문장, 채널, 가독성 |
| 결과가 흩어졌다 | 메인 창구 | 우선순위, 최종 통합, 보고 형식 |

역할을 이렇게 나누면 피드백이 구체적이 된다. “별로야”가 아니라 “근거가 부족하니 조사형으로 다시 보자”, “문장은 괜찮지만 실제 사례가 없으니 정리형이 보강하자”처럼 고칠 지점이 보인다.

## 실제 예시: WikiDocs 보강 요청

“전체 독자 흐름을 보고, 본문 링크도 자연스럽게 고치고, 내용이 축약되어 보이지 않게 보강해줘”라는 요청을 생각해보자. 한 문장처럼 보이지만 실제로는 여러 역할이 필요하다.

| 작업 | 역할 |
|---|---|
| 기존 글과 현재 목차가 맞는지 확인 | 조사형 |
| 공식 설명과 실제 운영 기준을 대조 | 조사형 |
| 장별 흐름을 독자 여정으로 재배열 | 정리형 |
| 기록용 표현을 독자용 사례로 전환 | 정리형 |
| 링크, 이미지, 서식 문제 검증 | 실행형 |
| 완료/남음/다음을 묶어 보고 | 메인 창구 |

이 요청을 한 역할로만 처리하면 분량은 늘 수 있지만 품질은 흔들린다. 조사 없이 정리하면 그럴듯하지만 약해지고, 정리 없이 실행하면 파일은 바뀌어도 독자 흐름이 남지 않는다.

## 역할 분리의 운영 기준

역할을 나눌 때는 아래 질문을 먼저 본다.

1. 이 작업은 근거를 더 찾아야 하는가?
2. 이미 있는 재료를 읽히는 구조로 바꿔야 하는가?
3. 실제 파일 수정, 발행, 검증처럼 상태 변경이 필요한가?
4. 이미지나 시각 자료처럼 별도 메시지 설계가 필요한가?
5. 여러 결과를 누가 최종 판단으로 묶을 것인가?
6. 공개 글이라면 독자에게 필요한 정보와 제거할 세부 정보를 누가 나눌 것인가?

역할을 나누는 순간 책임도 나뉜다. 그래서 위임 전에는 입력물, 완료 기준, 검증 기준을 함께 줘야 한다.

## 좋은 handoff와 나쁜 handoff

나쁜 handoff는 일을 던지는 말이다.

```text
이거 조사해줘.
이거 정리해줘.
이거 고쳐줘.
```

좋은 handoff는 역할, 목적, 완료 기준이 보인다.

```text
공식 설명과 현재 페이지를 비교해서 빠진 근거만 찾아줘.
독자가 처음 읽는다는 기준으로 장 흐름을 다시 잡아줘.
변경한 링크와 이미지가 공개 화면에서 깨지지 않는지 확인해줘.
```

역할형 에이전트는 지시가 길어야 잘하는 것이 아니다. 무엇을 맡고, 어디까지 하면 끝인지가 분명해야 잘한다.

## 공식 기능과 운영 기준은 다르다

Hermes Agent에는 profile, delegation, parallel work, 독립 subagent 실행, cron처럼 일을 나눠 움직이는 여러 방식이 있다. 하지만 기능이 있다고 해서 곧바로 좋은 역할 분리가 되는 것은 아니다.

기능은 “나눌 수 있다”를 제공한다. 운영 기준은 “무엇을 왜 나눌지”를 정한다. 조사형/정리형/실행형은 역할의 문제이고, profile 직접 호출/delegation/subagent/cron은 실행 방식의 문제다. 두 층을 나눠 보면 어떤 업무를 누구에게 맡기고 어떤 방식으로 돌릴지 더 선명해진다. 실행 방식의 차이는 [Hermes Agent에서 일을 나누는 네 가지 실행 방식](pages/35-four-ways-to-assign-work-in-hermes-agent.md)에서 이어서 다룬다.

## 운영 체크리스트

- 이 작업의 실패 신호는 무엇인가?
- 근거 부족, 구조 부족, 실행 부족 중 어디에 가까운가?
- 역할별 입력물과 완료 기준이 있는가?
- 최종 통합을 누가 맡는가?
- 공개 글이라면 독자에게 필요한 정보만 남겼는가?
- 반복될 작업이라면 skill이나 체크리스트로 남길 수 있는가?

## FAQ

### 역할형 에이전트는 몇 개가 적당한가요?

처음부터 많이 만들 필요는 없다. 메인 창구 1개와 조사형/정리형/실행형 정도면 시작할 수 있다. 이미지나 제품 문서처럼 반복되는 일이 생기면 그때 이미지형/제품형을 분리한다.

### 역할을 나누면 속도가 느려지지 않나요?

짧은 작업은 느려질 수 있다. 하지만 반복 업무나 공개 문서처럼 품질 검증이 필요한 작업에서는 역할을 나누는 편이 전체 수정 비용을 줄인다.

### 에이전트 이름이 꼭 필요할까요?

필수는 아니다. 다만 반복 운영에서는 이름이 있으면 호출과 책임이 쉬워진다. “방울이 시켜서 확장조사”, “뽀동이가 구조 정리”처럼 부르면 역할이 바로 보인다.
