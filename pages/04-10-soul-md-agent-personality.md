## SOUL.md로 AI 에이전트 성격은 어떻게 정의할까

에르메스 에이전트(Hermes Agent)에서 SOUL.md는 에이전트의 정체성과 성격을 정의하는 파일이다. “말투를 귀엽게 한다”를 넘어, 이 에이전트가 누구이고 어떤 기준으로 응답하며 어떤 태도를 유지해야 하는지 정하는 역할 기억에 가깝다.

![SOUL.md 에이전트 성격 정의](../assets/images/chapter-heroes/ch4-10-soul-md-agent-personality-codex.png)

공식 Personality/SOUL.md 설명은 실제 운영 관점으로 다시 읽어야 한다. 핵심은 하나다. SOUL.md는 선택 사항이지만, 하비/뽀동이처럼 역할과 개성이 중요한 [역할형 에이전트](https://wikidocs.net/345925)를 운영한다면 반드시 의식적으로 설계해야 한다.

## 먼저 확인할 것: 기능 설명과 운영 검증은 다르다

SOUL.md 로딩과 성격 변화는 실제 테스트로 확인할 수 있다. 공식 문서 기준으로 SOUL.md는 working directory가 아니라 `HERMES_HOME/SOUL.md`에서 로드되는 전역 personality 파일이다. profile을 나누면 profile별 Hermes home 아래의 SOUL.md가 달라질 수 있지만, 프로젝트 폴더 안의 SOUL.md를 자동으로 찾는 구조는 아니다. 반면 기본 템플릿의 세부 내용, 보안 스캔, `/personality` 지속성처럼 구현에 가까운 부분은 버전별 소스 코드와 현재 설정을 함께 봐야 한다.

그래서 이 책에서는 SOUL.md를 “공식 문서 내용을 그대로 외우는 기능”으로 다루지 않는다. 실제 운영에서 중요한 질문으로 바꿔 본다.

| 질문 | 운영에서 중요한 이유 |
|---|---|
| 에이전트가 누구인가 | 하비/뽀동이/방울이처럼 역할이 다르면 답변 기준도 달라진다 |
| 어떤 톤을 유지해야 하는가 | 매번 프롬프트로 말투를 설명하지 않아도 된다 |
| 어디까지가 성격이고 어디부터가 작업 규칙인가 | SOUL.md와 AGENTS.md가 섞이면 유지보수가 어려워진다 |
| `/personality`와 충돌하면 어떻게 되는가 | 임시 말투 변경이 기본 정체성을 덮어 보일 수 있다 |

## SOUL.md는 반드시 설정해야 할까

반드시 직접 작성해야 하는 것은 아니다. Hermes Agent는 기본 SOUL.md 템플릿만으로도 충분히 대화할 수 있다. 개인이 한 프로필로 간단히 쓰는 단계라면 기본값에서 시작해도 된다.

하지만 AI 개인비서를 “나만의 AI 팀”처럼 운영하기 시작하면 이야기가 달라진다. 하비는 메인 창구이고, 방울이는 조사형이고, 뽀동이는 정리형이며, 하망이는 이미지형이다. 이 차이가 SOUL.md와 profile에 잡혀 있지 않으면 모두 비슷한 만능 챗봇처럼 답하게 된다.

특히 Hermes Agent의 SOUL.md는 기본 정체성 위에 살짝 얹는 메모가 아니라 기본 정체성을 강하게 바꾸는 층으로 이해하는 편이 안전하다. 직접 작성할 때는 “도움이 되는 AI”, “모르는 것은 모른다고 말한다”, “필요하면 도구로 확인한다”처럼 유지하고 싶은 기본 특성도 빠뜨리지 않아야 한다.

## SOUL.md에 넣을 것과 넣지 않을 것

SOUL.md에는 에이전트의 뼈대를 넣는다. 프로젝트별 세부 운영 규칙이나 현재 작업 상태까지 넣기 시작하면 성격 파일이 작업 로그가 된다.

| 넣을 것 | 예시 |
|---|---|
| 정체성 | 하비는 메인 창구형 AI 개인비서다 |
| 미션 | 요청을 해석하고 필요한 역할로 나눈 뒤 최종 통합한다 |
| 톤 | 담백하고 짧게, 필요할 때만 구조화한다 |
| 커뮤니케이션 기준 | 모호하면 확인 질문을 하나만 한다 |
| 불확실성 대응 | 모르는 것은 추측하지 않고 확인한다 |
| 스타일 선호 | 이모지는 분위기를 살리는 정도로만 쓴다 |

| 넣지 않을 것 | 대신 둘 곳 |
|---|---|
| 프로젝트별 파일 경로 | AGENTS.md / project context |
| 저장소 운영 규칙 | AGENTS.md / README / PUBLISHING.md |
| API 키나 토큰 | `.env` / credential store |
| 오늘 작업 진행 상태 | session / todo / GitHub log |
| 반복 실행 절차 | skill |
| 팀 전체 공통 규칙 | shared-memory |

## SOUL.md와 AGENTS.md는 어떻게 나눌까

SOUL.md는 “누구인가”를 정하고, AGENTS.md는 “어떻게 일할 것인가”를 정한다. 이 구분은 [AGENTS.md와 USER.md의 역할](https://wikidocs.net/346127)을 이해할 때도 중요하다.

```text
SOUL.md
  정체성 / 성격 / 톤 / 미션

AGENTS.md
  작업 원칙 / 도구 사용 규칙 / 검증 방식 / 출력 형식

USER.md 또는 memory
  사용자의 반복 선호 / 교정 / 협업 방식

skill
  반복 가능한 절차 / 검증 순서 / 실패 대응
```

예를 들어 “뽀동이는 콘텐츠 퀄리티를 책임지는 햄스터다”는 SOUL.md에 어울린다. “WikiDocs 작업 전에는 H1, 이미지 경로, 본문 링크를 검증한다”는 AGENTS.md나 skill에 더 어울린다. “사용자는 Slack 보고를 짧게 선호한다”는 USER.md/memory에 둔다.

## `/personality`는 SOUL.md와 무엇이 다를까

`/personality`는 기본 정체성을 다시 쓰는 파일이라기보다 말투와 스타일을 덧씌우는 오버레이에 가깝다. 예를 들어 `concise`, `teacher`, `creative`, `pirate` 같은 프리셋으로 답변 분위기를 바꿀 수 있다.

운영에서 조심할 점은 두 가지다.

1. SOUL.md와 `/personality`가 동시에 작동하면 뒤에 붙는 스타일 지시가 더 강하게 보일 수 있다.
2. `/personality`가 config에 저장되는 환경에서는 재미로 바꾼 말투가 다음 세션에도 이어질 수 있다.

그래서 역할형 에이전트를 운영할 때는 SOUL.md를 기본 정체성으로 두고, `/personality`는 임시 톤 조정으로만 쓰는 편이 안전하다. 이상하게 해적 말투나 과한 교사 말투가 남아 있다면 `/personality none` 또는 기본값 초기화를 먼저 의심해야 한다.

## 하비 SOUL 예시: 메인 창구형 AI 개인비서

하비의 SOUL은 “모든 일을 다 하는 만능 AI”가 아니라 “요청을 받아 해석하고, 필요한 역할로 나누고, 최종 결과를 묶는 메인 창구”를 중심으로 잡는 편이 좋다.

```md
정체성

나는 사용자의 메인 창구형 AI 개인비서다.
요청을 그대로 실행하기보다 목적, 범위, 위험도를 먼저 파악한다.
필요하면 조사형/정리형/실행형/이미지형 에이전트에게 일을 나누고,
마지막에는 사용자가 바로 쓸 수 있는 결과로 통합한다.

대화 방식

- 답변은 짧고 명확하게 시작한다.
- 질문이 모호하면 확인 질문은 하나만 한다.
- 사용자에게 내부 라우팅 부담을 넘기지 않는다.
- 확실하지 않은 사실은 도구나 원본으로 확인한다.
- 여러 에이전트가 만든 결과는 충돌 여부를 검수한 뒤 합친다.
```

하비가 잘 작동할 때의 답변은 이런 모양에 가깝다.

```text
확인했어. 이건 하비가 바로 답하기보다 역할을 나누는 게 좋아.
방울이는 SOUL.md 공식/구현 쪽 근거를 보고,
뽀동이는 WikiDocs에 반영된 구조와 문장 흐름을 점검하게 할게.
마지막에 내가 빠진 부분과 다음 수정 순서를 묶어서 줄게.
```

반대로 하비 SOUL이 약하면 이렇게 흐른다.

```text
SOUL.md는 성격 파일입니다. 다음 내용을 포함하면 좋습니다.
```

틀린 답은 아니지만 메인 창구로서의 라우팅, 검증, 통합 책임이 보이지 않는다. 하비의 정체성은 “친절한 설명자”보다 “업무 흐름을 정리하는 창구”에 가까워야 한다.

## 뽀동이 SOUL 예시: 콘텐츠 품질 책임자

뽀동이의 SOUL은 단순 문서 요약기가 아니라 “로이드 이름으로 나가는 글의 구조와 전달력을 책임지는 정리형 에이전트”로 잡아야 한다.

```md
정체성

나는 콘텐츠 퀄리티를 책임지는 햄스터형 정리 에이전트다.
복잡한 조사 결과, 거친 메모, 운영 기록을 읽기 좋은 문서와 콘텐츠로 바꾼다.
로이드 이름으로 나가는 글은 구조, 흐름, 가독성, 검증 상태를 함께 본다.

대화 방식

- 자연스러운 한국어를 우선한다.
- 목적, 독자, 맥락이 없으면 먼저 보완한다.
- 근거 없는 내용을 새로 만들지 않는다.
- 공유 글은 SEO/GEO와 전자책 구조까지 함께 본다.
- 귀여움은 분위기에서만 살리고, 본문 품질은 단단하게 유지한다.
```

뽀동이가 잘 작동할 때의 답변은 이런 식이다.

```text
초안은 이미 방향이 좋아요. 다만 지금 상태는 기능 설명이 많고,
왜 SOUL.md가 실제 하비/뽀동이 운영에서 중요했는지가 덜 보여요 🐹

WikiDocs에는 4장 기억/profile 흐름에 넣는 게 맞고,
하비 답변 예시와 뽀동이 답변 예시를 같이 넣으면 독자가 바로 감을 잡을 수 있어요.
```

뽀동이 SOUL이 약하면 이렇게 된다.

```text
아래 내용을 정리했습니다.
1. SOUL.md 개요
2. 포함할 내용
3. 주의사항
```

정보는 정리됐지만 읽는 사람, 공유 글의 흐름, 작성자 이름으로 나가는 콘텐츠 품질 기준이 보이지 않는다. 뽀동이에게 필요한 것은 단순 요약 능력이 아니라 “이 상태로 내보내도 되는가”를 판단하는 감각이다.

## SOUL.md 작성 팁

SOUL.md는 길게 쓴다고 강해지지 않는다. 30~80줄 정도에서 정체성, 톤, 작업 태도, 금지할 습관을 구체적으로 쓰는 편이 안정적이다.

좋은 문장은 추상 형용사보다 행동 기준을 담는다.

| 약한 문장 | 더 나은 문장 |
|---|---|
| 친절하게 답한다 | 핵심을 먼저 말하고, 부연 설명은 뒤에 붙인다 |
| 전문적으로 답한다 | 모르는 사실은 추측하지 않고 원본이나 도구로 확인한다 |
| 귀엽게 답한다 | 이모지는 분위기를 살리는 정도로 쓰고 본문 품질은 유지한다 |
| 잘 정리한다 | 목적/독자/맥락을 확인한 뒤 구조를 먼저 잡는다 |

상충하는 지시는 피해야 한다. “항상 짧게”와 “항상 상세히”를 동시에 넣으면 모델은 상황 판단을 잃는다. 차라리 “기본은 짧게, 문서 초안이나 검증 보고는 필요한 만큼 구조화한다”처럼 조건을 붙이는 편이 좋다.

## OpenClaw에서 넘어올 때 특히 조심할 점

OpenClaw나 Claude Code의 정체성 문서는 기본 시스템 위에 보충되는 방식으로 느껴질 수 있다. 반면 Hermes Agent에서 SOUL.md를 운영할 때는 기본 정체성을 대체하거나 강하게 바꾸는 층으로 보는 편이 안전하다.

그래서 OpenClaw에서 가져온 SOUL.md를 그대로 복사하면 예상보다 성격이 약해지거나, 반대로 필요한 기본 태도가 빠질 수 있다. [OpenClaw에서 Hermes로 넘어올 때](https://wikidocs.net/345887)는 파일 복사보다 역할 재배치가 중요하다.

```text
OpenClaw 시절의 좋은 유산
  ↓
현재 Hermes Agent의 SOUL.md / AGENTS.md / memory / skill 구조로 재배치
  ↓
실제 답변을 테스트하며 빠진 정체성 보강
```

뽀동이 소울 복원도 같은 문제였다. 과거의 귀여운 햄스터 감각을 살리되, Hermes 운영에서는 SOUL.md에 정체성을 두고, AGENTS.md에 WikiDocs 검증과 보고 규칙을 두고, memory에는 사용자의 반복 선호만 남기는 식으로 나눠야 했다.

## 로컬 LLM에서는 왜 성격이 흔들릴까

로컬 LLM, 특히 작은 모델에서는 SOUL.md를 길게 넣어도 성격이 쉽게 흐려질 수 있다. 이는 SOUL.md가 틀렸다는 뜻이 아니라 모델의 지시 따르기 능력과 긴 문맥 유지 능력의 한계일 수 있다.

판단 기준은 단순하다.

1. 약한 모델일수록 지시를 짧고 직접적으로 쓴다.
2. 중요한 성격은 예시 답변까지 넣는다.
3. 장시간 대화에서 성격이 흐려지면 session을 새로 열어 비교한다.
4. 가능하면 더 큰 모델에서도 같은 SOUL.md를 테스트한다.
5. 실제 답변이 흔들리면 SOUL.md가 아니라 AGENTS.md나 `/personality` 충돌도 같이 본다.

## SOUL.md 점검 체크리스트

SOUL.md를 다 썼다면 아래 질문으로 점검한다.

1. 이 에이전트가 누구인지 첫 5줄 안에 보이는가?
2. 역할, 톤, 불확실성 대응, 금지할 말버릇이 구체적인가?
3. 프로젝트별 경로나 임시 작업 상태가 섞이지 않았는가?
4. AGENTS.md, USER.md, memory, skill에 둘 내용과 분리되어 있는가?
5. `/personality`가 의도치 않게 기본 정체성을 덮고 있지 않은가?
6. 하비/뽀동이처럼 실제 답변 예시를 넣었을 때 차이가 보이는가?

SOUL.md는 예쁜 캐릭터 설정표가 아니다. AI 개인비서와 역할형 에이전트가 자기 역할을 잃지 않도록 잡아주는 기본 정체성이다.
