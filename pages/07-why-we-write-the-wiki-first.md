## 왜 WikiDocs를 먼저 쓰고 블로그/강의를 나중에 뽑을까

에르메스 에이전트(Hermes Agent) 운영에서 WikiDocs를 먼저 쓰는 이유는 글을 길게 쓰기 위해서가 아니다. 운영 기준을 책처럼 정리해 두면 블로그, 강의, 카드뉴스, Slack 답변이 모두 같은 기준에서 파생되기 때문이다.

블로그를 먼저 쓰면 당장의 메시지는 선명할 수 있다. 하지만 여러 글이 쌓이면 같은 설명이 반복되고, 공식 docs 반영 여부나 실제 운영 케이스가 어디에 있는지 찾기 어려워진다. WikiDocs는 이 문제를 줄이는 콘텐츠 모체다.

## 왜 강의부터 만들면 남는 게 적을까

강의는 전달력이 좋지만, 흐름과 시간에 맞춰 압축된다. 강의만 먼저 만들면 기준 문장, 체크리스트, 링크 구조가 흩어질 수 있다. 반대로 WikiDocs에 문제/착각/운영 기준/FAQ를 먼저 정리하면 강의는 그중 필요한 흐름을 가져가면 된다.

이 책도 그렇게 다듬고 있다. 기존 블로그를 옮긴 뒤, 로이드는 “처음 보는 사람은 축약되어 있다고 느낄 것 같다”고 봤다. 그래서 단순 분량 추가가 아니라 실제 세션/Slack/shared-memory에서 운영 이야기를 회수해 각 장에 다시 넣었다.

## WikiDocs는 콘텐츠 모체다

| 채널 | 역할 | WikiDocs와의 관계 |
|---|---|---|
| WikiDocs | evergreen 운영서 | 기준과 내부 링크를 보관 |
| 블로그 | 특정 문제/검색 유입 | WikiDocs의 한 주제를 캠페인형으로 압축 |
| 강의 | 순서와 실습 | WikiDocs 기준을 학습 흐름으로 재배열 |
| 카드뉴스/이미지 | 한 메시지 전달 | 본문 핵심을 시각 자산으로 변환 |
| Slack 답변 | 즉시 운영 | 필요 시 WikiDocs 기준으로 회수/보강 |

## 실제 운영 장면: 내부 링크가 콘텐츠 구조를 바꿨다

처음에는 각 페이지 끝에 `이어서 읽기`를 붙이는 방식으로 내부 링크를 보강했다. 하지만 로이드가 원한 것은 본문 안에서 [AI 개인비서](https://wikidocs.net/345923), [역할형 에이전트](https://wikidocs.net/345925), [memory/profile/session](https://wikidocs.net/345902), [MCP/cron/gateway](https://wikidocs.net/345907)가 자연스럽게 연결되는 구조였다.

이 피드백 덕분에 WikiDocs는 단순 글 모음이 아니라 개념 지도에 가까워졌다. 블로그는 보통 한 글 안에서 끝나지만, 책은 페이지 사이를 읽으며 이해가 깊어져야 한다.

## 운영 기준

1. 먼저 WikiDocs에서 기준 페이지를 만든다.
2. 블로그는 독자 문제와 검색 키워드에 맞춰 파생한다.
3. 강의는 WikiDocs 순서를 그대로 읽지 말고 실습 흐름으로 재구성한다.
4. 본문 내부 링크는 페이지 끝 이동보다 문장 안의 개념 연결을 우선한다.
5. 공개 콘텐츠에는 민감정보와 내부값을 제거하고, 이야기와 판단 기준만 남긴다.

## FAQ

### 블로그와 WikiDocs를 같은 글로 운영하면 안 되나요?

완전히 같게 두면 둘 다 약해진다. WikiDocs는 책 구조와 개념 연결, 블로그는 문제 해결과 유입에 집중하는 편이 좋다.

### 강의는 언제 만들면 좋나요?

WikiDocs에서 기준과 사례가 어느 정도 안정된 뒤가 좋다. 그때 강의는 문서 복사가 아니라 학습 순서 설계가 된다.

### WikiDocs를 먼저 쓰면 속도가 느려지지 않나요?

처음에는 느려 보인다. 하지만 기준이 쌓이면 블로그/강의/이미지 제작 속도가 오히려 빨라진다.
