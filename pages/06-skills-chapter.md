## 6장. Hermes Agent Skill 운영과 자기 개선형 AI 에이전트

에르메스 에이전트(Hermes Agent)에서 Skill은 “다음에도 같은 일을 더 안정적으로 처리하기 위한 작업법”이다. 프롬프트를 예쁘게 모아둔 문서가 아니라, 반복 업무에서 생긴 순서, 판단 기준, 실패 패턴, 검증 방법을 다음 세션에서도 다시 쓰게 만드는 운영 지식이다.

![6장 Skill 운영과 자기 개선 흐름](../assets/images/chapter-heroes/ch06-skill-ops-self-improving-agent-codex.webp)

이 장은 Skill을 기능 설명으로만 다루지 않는다. 하비가 요청을 나누고, 방울이가 근거를 찾고, 뽀동이가 WikiDocs 원고를 다듬고, 하망이가 이미지를 만들며, 봉구가 실행과 검증을 맡는 흐름 속에서 어떤 기준이 Skill로 남는지 보여준다. 독자가 가져가야 할 질문은 “스킬이 몇 개인가”가 아니라 “우리 팀의 반복 실수를 어떤 작업법으로 줄일 것인가”다.

앞 장의 [외부 도구/MCP/채널 연동](https://wikidocs.net/345907)이 도구를 어떻게 붙일지 다뤘다면, 6장은 그 도구를 어떤 순서와 기준으로 쓸지 남기는 방법을 다룬다. 뒤의 [콘텐츠 시스템](https://wikidocs.net/345911)과 [실제 업무 자동화 사례](https://wikidocs.net/345990)는 Skill이 결과물 품질을 어떻게 지키는지 보여준다.

## 이 장에서 다루는 문제

| 순서 | 글 | 핵심 질문 |
|---|---|---|
| 06-1 | Hermes Agent Skill은 무엇이고 언제 만들까 | 반복 절차와 검증 기준이 생겼을 때 Skill로 남길 수 있을까 |
| 06-2 | 반복 업무는 어떻게 Skill이 되는가 | 한 번의 시행착오를 다음 작업의 실행 기준으로 바꿀 수 있을까 |
| 06-3 | 역할형 에이전트별 Skill은 어떻게 나눌까 | 하비/방울이/뽀동이/하망이/봉구의 Skill 경계를 어떻게 잡을까 |
| 06-4 | Skill은 어떻게 보강하고 QA해야 할까 | 실제 운영과 어긋난 Skill을 언제 어떻게 고칠까 |
| 06-5 | 공개 GitHub Skill과 내부 Skill은 어떻게 분리할까 | 공유할 수 있는 절차와 팀 내부 기준을 어떻게 나눌까 |
| 06-6 | Skill과 memory/MCP/cron/gateway는 어떻게 다를까 | 기억, 도구 연결, 예약 실행, 채널 입구와 Skill을 어떻게 구분할까 |

## Skill 장에서 정리할 산출물

| 산출물 | 확인 질문 |
|---|---|
| Skill 후보 목록 | 반복 업무와 반복 실수가 구분되어 있는가 |
| Skill 작성 기준 | 순서/판단 기준/검증 기준이 함께 들어 있는가 |
| 역할별 Skill 경계 | 하비/방울이/뽀동이/하망이/봉구가 같은 Skill을 억지로 공유하지 않는가 |
| 보강/QA 흐름 | 실제 운영과 어긋난 Skill을 발견했을 때 바로 고치는 절차가 있는가 |
| 공유 범위 기준 | 공개 GitHub Skill과 팀 내부 Skill에서 보호해야 할 정보가 분리되어 있는가 |

## Skill 장을 따로 둔 이유

Skill은 Hermes Agent가 경험을 쌓는 방식과 맞닿아 있다. memory가 사용자 선호와 오래 유지할 판단 기준을 기억한다면, Skill은 반복 업무를 처리하는 방법을 기억한다. MCP가 외부 도구를 연결한다면, Skill은 그 도구를 어떤 순서로 쓰고 어떤 결과를 확인할지 정한다.

예를 들어 WikiDocs 발행 작업에서 중요한 것은 “원격 저장소에 반영한다”는 한 줄이 아니다. 원고가 H1을 쓰지 않는지, 이미지 경로가 깨지지 않는지, TOC 링크가 실제 파일을 가리키는지, 본문 링크가 WikiDocs 공개 URL로 바뀌었는지, 첫 문단이 독자의 질문에 답하는지까지 확인해야 한다. 이 반복 검증 흐름이 Skill이다.

## 우리 팀에서 Skill 기준이 생긴 순간들

처음에는 뽀동이가 WikiDocs 원고를 다듬을 때 문장과 구조를 고치는 일이 중심이었다. 그런데 작업이 반복되자 품질 기준이 더 분명해졌다. 전자책 호환을 위해 H1을 쓰지 않는다. 제목과 첫 문단에는 `에르메스 에이전트(Hermes Agent)` 같은 핵심 키워드를 자연스럽게 둔다. 본문 링크는 단순한 페이지 끝 순차 링크가 아니라 본문 안에서 개념과 사례를 연결해야 한다. 검증 후에는 GitHub와 WikiDocs 공개 페이지가 모두 맞는지 확인한다.

하망이의 이미지 작업도 같은 방식으로 Skill이 됐다. 처음에는 이미지를 잘 만드는 일이 중요해 보였지만, 실제로는 본문 메시지와 맞는지, 한글이 깨지지 않았는지, 워터마크나 잘림이 없는지, 이전 장의 톤과 이어지는지 확인해야 했다. 그래서 이미지형 에이전트 Skill에는 생성 프롬프트만이 아니라 vision QA와 배포 포맷 기준이 함께 들어간다.

하비의 Skill은 또 다르다. 하비는 모든 일을 직접 처리하는 기준이 아니라, 어떤 일은 방울이에게 조사시키고 어떤 일은 뽀동이에게 구조화시키며, 어떤 작업은 봉구나 하망이로 넘겨야 하는지 판단하는 기준이 필요하다. 이처럼 Skill은 “에이전트를 더 똑똑하게 보이게 하는 장식”이 아니라, 역할별 실패를 줄이는 작업법이다.

## 이 장에서 가져갈 기준

- Skill은 프롬프트 저장소가 아니라 반복 업무 절차/판단 기준/검증 기준이다.
- 한 번의 성공보다 반복되는 실패와 수정 기준이 Skill 후보를 만든다.
- 최신 정보, 토큰, 계정값, 일회성 로그는 Skill에 넣지 않는다.
- 하비/방울이/뽀동이/하망이처럼 역할이 다르면 Skill도 역할별로 나누는 편이 좋다.
- 공개 Skill과 내부 Skill은 보호해야 할 정보, 경로, 계정, 조직 맥락 기준으로 분리한다.
- 오래된 Skill은 자산이 아니라 위험이므로 실제 운영과 어긋나면 바로 고친다.

## 다음 장으로 가기 전 체크 질문

1. 지금 반복되는 일은 memory가 아니라 Skill로 남길 절차인가?
2. 이 Skill은 어떤 도구를 어떤 순서로 쓰는지 말하는가?
3. 실패했을 때 어디를 확인해야 하는지 들어 있는가?
4. 검증 기준이 실제 명령/체크 항목으로 적혀 있는가?
5. 공유해도 되는 기준과 팀 내부에만 둘 기준이 분리되어 있는가?
