## 6장. Hermes Agent Skill 운영과 자기 개선형 AI 에이전트

에르메스 에이전트(Hermes Agent)에서 Skill은 반복 업무를 다시 설명하지 않게 만드는 운영 지식이다. 단순 프롬프트 모음이 아니라, 특정 일을 처리할 때 필요한 순서, 도구 선택, 실패 패턴, 검증 기준을 묶어 다음 세션에서도 재사용하게 하는 단위다.

공식 문서의 Skills Hub는 여러 내장 Skill과 카테고리를 보여준다. 하지만 실제 운영에서 더 중요한 질문은 “스킬이 몇 개 있나”가 아니라 “어떤 경험을 스킬로 남길 것인가”다. 이 장은 Hermes Agent를 자기 개선형 AI 에이전트로 운영할 때 반복 업무가 Skill이 되고, Skill이 다시 보강되는 흐름을 정리한다.

앞 장의 [외부 도구/MCP/채널 연동](https://wikidocs.net/345907)이 도구를 어떻게 붙일지 다뤘다면, 6장은 그 도구를 어떤 순서와 기준으로 쓸지 남기는 방법을 다룬다. 뒤의 [콘텐츠 시스템](https://wikidocs.net/345911)과 [실제 업무 자동화 사례](https://wikidocs.net/345990)는 이 Skill이 결과물 품질을 어떻게 지키는지 보여준다.

## 이 장에서 다루는 문제

| 순서 | 글 | 핵심 질문 |
|---|---|---|
| 06-1 | Hermes Agent Skill은 무엇이고 언제 만들까 | 반복 절차와 검증 기준이 생겼을 때 Skill로 남길 수 있을까 |
| 06-2 | 반복 업무는 어떻게 Skill이 되는가 | 한 번의 시행착오를 다음 작업의 실행 기준으로 바꿀 수 있을까 |
| 06-3 | 역할형 에이전트별 Skill은 어떻게 나눌까 | 하비/방울이/뽀동이/하망이/봉구의 Skill 경계를 어떻게 잡을까 |
| 06-4 | Skill은 어떻게 보강하고 QA해야 할까 | 실제 운영과 어긋난 Skill을 언제 어떻게 고칠까 |
| 06-5 | 공개 GitHub Skill과 내부 Skill은 어떻게 분리할까 | 공유할 수 있는 절차와 불필요한 내부값을 어떻게 나눌까 |
| 06-6 | Skill과 memory/MCP/cron/gateway는 어떻게 다를까 | 기억, 도구 연결, 예약 실행, 채널 입구와 Skill을 어떻게 구분할까 |

## 왜 Skill 장을 따로 두는가

Skill은 Hermes Agent의 성장 단위다. memory가 사용자 선호와 안정 규칙을 기억한다면, Skill은 반복 업무를 수행하는 방법을 기억한다. MCP가 외부 도구를 연결한다면, Skill은 그 도구를 어떤 순서로 쓰고 어떤 결과를 검증할지 정한다.

예를 들어 WikiDocs 발행 작업에서 중요한 것은 “원격 저장소에 반영한다”는 한 줄이 아니다. 원고가 H1을 쓰지 않는지, 이미지 경로가 깨지지 않는지, TOC 링크가 실제 파일을 가리키는지, 공개 본문에 raw `.md` 링크가 남지 않았는지, WikiDocs 동기화 후 공개 페이지가 바뀌었는지까지 확인해야 한다. 이 반복 검증 흐름이 Skill이다.

## 실제 운영에서 생긴 장면

뽀동이가 WikiDocs 원고를 다듬을 때 처음에는 문장 수정과 구조 정리가 중심이었다. 하지만 작업이 반복되면서 품질 기준이 분명해졌다. 전자책 호환을 위해 H1을 쓰지 않는다. 제목과 첫 문단에는 `에르메스 에이전트(Hermes Agent)` 같은 핵심 키워드를 자연스럽게 둔다. 내부 링크는 WikiDocs 공개 page ID로 바꾼다. 검증 후 GitHub 원본에 반영하고 공개 페이지를 spot-check한다.

이 기준은 매번 말로 다시 설명할 내용이 아니다. `wikidocs-github-ebook-pipeline` 같은 Skill로 남겨야 한다. 그래야 긴 세션이 압축되거나 다른 에이전트가 이어받아도 품질 기준이 흔들리지 않는다.

## 이 장에서 얻을 기준

- Skill은 프롬프트 저장소가 아니라 반복 업무 절차/판단 기준/검증 기준이다.
- 한 번의 성공보다 반복되는 실패와 수정 기준이 Skill 후보를 만든다.
- 최신 정보, 토큰, 계정값, 일회성 로그는 Skill에 넣지 않는다.
- 하비/방울이/뽀동이처럼 역할이 다르면 Skill도 역할별로 나누는 편이 좋다.
- 공개 Skill과 내부 Skill은 보호해야 할 정보, 경로, 계정, 조직 맥락 기준으로 분리한다.
- 오래된 Skill은 자산이 아니라 위험이므로 실제 운영과 어긋나면 바로 고친다.

## 다음 장으로 가기 전 체크 질문

1. 지금 반복되는 일은 memory가 아니라 Skill로 남길 절차인가?
2. 이 Skill은 어떤 도구를 어떤 순서로 쓰는지 말하는가?
3. 실패했을 때 어디를 확인해야 하는지 들어 있는가?
4. 검증 기준이 실제 명령/체크 항목으로 적혀 있는가?
5. 공개해도 되는 정보와 내부에만 남길 정보가 분리되어 있는가?
