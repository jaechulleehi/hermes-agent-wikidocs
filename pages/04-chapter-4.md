## 4장. 기억/컨텍스트/프로필 경계

![4장 기억 컨텍스트 프로필 경계를 나누는 구조](../assets/images/chapter-heroes/ch04-memory-context-profile-boundary-codex.png)

AI 개인비서를 오래 쓰다 보면 “왜 같은 하비인데 오늘은 다르게 기억하지?”라는 순간이 온다. 이 문제는 대부분 모델 성능보다 **기억의 경계**에서 생긴다. 현재 대화의 맥락, 오래 남길 선호, 에이전트별 역할, 팀 공통 원본, 공개 문서 원본이 서로 다른데 이것을 하나의 기억처럼 다루면 AI가 오락가락하는 것처럼 보인다.

4장은 memory를 많이 넣는 법이 아니라, **무엇을 어디에 남길지** 정하는 장이다. [역할형 에이전트](https://wikidocs.net/345925)를 나누는 것만큼 중요한 것이 기억과 원본의 위치를 나누는 일이다. 이 경계가 잡혀야 하비가 메인 창구로 안정적으로 통합하고, 방울이/뽀동이 같은 역할형 에이전트가 같은 기준으로 이어받을 수 있다.

## 이 장에서 다루는 문제

| 글 | 질문 | 핵심 |
|---|---|---|
| 04-1 | 같은 AI 개인비서인데 기억은 왜 다르게 느껴질까 | session/memory/profile/source of truth를 나눈다 |
| 04-2 | 파일은 있는데 도구는 왜 못 읽을까 | 사람이 보는 위치와 도구가 실행되는 위치는 다르다 |
| 04-3 | 과거 유산과 현재 기준은 어떻게 나눌까 | archive와 현재 기준을 섞지 않는다 |
| 04-4 | 긴 대화에서 컨텍스트는 왜 흐려질까 | compaction은 요약이지 검증이 아니다 |

## 실제 운영에서 드러난 장면

OpenClaw에서 Hermes로 넘어올 때 가장 헷갈렸던 것은 “무엇이 이사된 것인가”였다. 예전 정체성 문서, memory, cron, gateway 흔적이 남아 있었지만 Hermes에서는 같은 구조로 자동 이식되지 않았다. 그래서 과거 유산은 참고 자료로 두고, 현재 기준은 Hermes의 profile, AGENTS, skill, cron, gateway, GitHub 원본처럼 실제로 읽히고 실행되는 층에 다시 놓아야 했다.

WikiDocs 책을 보강할 때도 같은 문제가 반복됐다. 사용자가 “4장 가자”라고 말하면 현재 메시지만 봐서는 짧은 요청처럼 보인다. 하지만 실제 작업에는 앞 장의 커밋 상태, TOC 구조, 이전 세션 요약, 책 전체의 문체 기준, 공개 가능한 사례 범위가 함께 들어간다. 이 중 하나만 보면 문장은 맞아도 흐름이 끊긴다.

예를 들어 3장을 마치고 4장을 시작할 때 필요한 확인은 단순히 “다음 장을 쓴다”가 아니었다. 먼저 `main`과 `origin/main`이 같은지 확인하고, TOC에서 4장에 속한 파일 5개만 뽑고, 이전 장에서 이미 설명한 역할 분리 이야기가 반복되지 않게 조정해야 했다. 또 OpenClaw 전환 사례는 살리되, 특정 환경값은 빼고 “과거 유산과 현재 기준을 나누는 법”으로 바꿔야 했다.

즉 기억 관리는 “AI가 더 많이 외우게 하는 일”이 아니다. 현재 작업에 필요한 맥락은 세션에서 확인하고, 반복될 선호는 memory에 남기고, 팀 공통 규칙은 shared-memory에서 보고, 공개 문서의 원본은 GitHub/WikiDocs 흐름으로 확인하는 일이다.

## 이 장에서 얻을 기준

| 층 | 맡는 일 | 넣으면 안 되는 것 |
|---|---|---|
| session | 지금 대화의 작업 범위와 임시 결정 | 다음 달에도 계속 필요한 규칙 |
| memory | 반복될 선호, 안정적인 사실, 자주 틀리는 교정 | 일일 작업 로그, 긴 초안, 임시 TODO |
| profile | 에이전트 역할, 말투, 도구/권한 경계 | 다른 에이전트의 현재 작업 상태 |
| shared-memory | 팀 공통 규칙, handoff, 공용 운영 원본 | 개인 대화의 모든 세부 기록 |
| Obsidian/HALOX Brain | 누적 지식, 운영 원장, 연결형 노트 | 짧은 시스템 규칙의 복붙 |
| GitHub/WikiDocs | 공개 문서 원본과 배포 결과 | 비공개 설정값이나 내부 식별값 |

이 기준이 잡히면 [외부 도구/MCP/자동화 운영](https://wikidocs.net/345907)도 훨씬 안정된다. 도구 실패처럼 보이는 문제도 실제로는 profile, 권한, 경로, 원본 위치가 어긋난 경우가 많기 때문이다.

4. 긴 대화가 이어질 때 완료한 일과 남은 일을 어디서 확인할 것인가?
5. 공개 글로 옮길 때 내부값이 아니라 판단 기준만 남겼는가?
