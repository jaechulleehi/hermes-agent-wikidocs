## Hermes Agent 운영 체크리스트는 어떻게 써야 할까

[Hermes Agent](00-hermes-agent-core-concepts.md) 운영 체크리스트는 길게 쓰는 문서가 아니다. AI 개인비서, 역할형 에이전트, MCP, cron, WikiDocs 발행처럼 여러 요소가 얽힐 때 먼저 확인할 순서를 짧게 고정하는 도구다.

체크리스트가 실제로 도움이 되려면 설명보다 행동이 보여야 한다. “메모리를 확인한다”보다 “[session](03-why-same-harvey-feels-like-different-memory.md) 내용인지 memory 저장 대상인지 나눈다”가 낫고, “발행을 확인한다”보다 “TOC 링크, 이미지 경로, H1 사용 여부를 검증한다”가 낫다.

## 왜 체크리스트는 많은데도 잘 안 쓰일까

잘 안 쓰이는 체크리스트는 보통 세 가지 문제가 있다.

- 너무 길어서 시작점이 보이지 않는다.
- 설명은 많은데 실제 확인 항목이 없다.
- 누가, 언제, 어떤 도구로 확인할지 빠져 있다.

Hermes Agent 운영에서는 이 문제가 더 크게 드러난다. 하비가 메인 창구인지, [방울이](23-where-bangwooli-research-agent-is-strong-and-where-it-wobbles.md)에게 조사시킬지, 뽀동이가 문서화할지, 봉구가 실행 검증할지에 따라 체크리스트의 모양도 달라진다.

## 좋은 체크리스트의 조건

| 조건 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 짧다 | 관련 문서를 모두 확인한다 | TOC 링크 누락을 검사한다 |
| 순서가 있다 | 필요하면 재시작한다 | process 확인 후 log를 본다 |
| 역할이 보인다 | AI가 정리한다 | 방울이는 근거, 뽀동이는 구조를 맡는다 |
| 검증이 있다 | 발행한다 | push 후 WikiDocs 동기화 상태를 확인한다 |
| 업데이트 위치가 있다 | 다음에 참고한다 | 반복 규칙이면 skill에 반영한다 |

체크리스트는 설명서를 대체하지 않는다. 설명서를 보기 전, 무엇을 확인할지 정해주는 입구다.

## 실제 운영 체크리스트 예시

[WikiDocs](07-why-we-write-the-wiki-first.md) 페이지를 고칠 때는 이렇게 쓴다.

```text
1. 요청한 장과 관련된 파일만 수정했는가
2. TOC 제목과 페이지 첫 H2가 맞는가
3. 구분/나열에 `/`를 썼는가
4. AI스러운 표현이 남아 있지 않은가
5. H1, 헤딩 간격, 이미지 경로, TOC 링크 검증을 통과했는가
6. 커밋 메시지가 이번 장 작업을 설명하는가
7. push 후 working tree가 깨끗한가
```

이 정도면 뽀동이뿐 아니라 다음 작업자도 같은 기준으로 이어갈 수 있다.

## 운영 기준

체크리스트를 만들 때는 아래 기준을 둔다.

1. 한 체크리스트는 한 상황만 다룬다.
2. 항목은 행동 문장으로 쓴다.
3. 확인 순서를 바꾸면 위험해지는 항목은 위에 둔다.
4. 역할형 에이전트가 필요한 경우 담당 역할을 적는다.
5. 통과 기준이 없는 항목은 줄이거나 다시 쓴다.
6. 반복되는 항목은 skill이나 AGENTS.md로 승격한다.
7. 더 이상 쓰지 않는 항목은 지운다.

## FAQ

### 체크리스트는 어디에 두는 게 좋나요?

반복 작업 절차는 skill, 콘텐츠 기준은 REWRITE_GUIDE.md나 AGENTS.md, 임시 작업 상태는 세션이나 이슈에 두는 편이 좋다.

### 체크리스트가 너무 짧으면 빠뜨리지 않나요?

짧다고 약한 것은 아니다. 중요한 순서와 검증 기준이 있으면 짧은 체크리스트가 더 잘 쓰인다.

### 체크리스트와 복구 플레이북은 어떻게 다른가요?

체크리스트는 평소 작업의 누락을 막고, 복구 플레이북은 문제가 생긴 뒤 확인 순서와 최소 조치를 정한다.
