## Hermes Agent에서 일을 나누는 네 가지 실행 방식

Hermes Agent에서 일을 나눈다는 말은 두 층으로 봐야 한다. 하나는 **어떤 역할이 필요한가**이고, 다른 하나는 **그 역할을 어떤 방식으로 실행시킬 것인가**다.

![Hermes Agent 일을 나누는 네 가지 실행 방식](../assets/images/chapter-heroes/ch5-4-four-ways-to-assign-work-codex.png)

[역할형 에이전트](https://wikidocs.net/345925)를 나누는 기준은 조사형/정리형/실행형처럼 업무 성격을 구분하는 일이다. 반면 profile 직접 호출, delegation, subagent, cron은 그 역할을 실제로 움직이는 실행 방식이다. 이 둘을 섞어 생각하면 “누구에게 맡길까”와 “어떻게 돌릴까”가 한꺼번에 흐려진다.

## 먼저 역할과 실행 방식을 나눈다

예를 들어 “WikiDocs에 새 운영 사례를 추가하고 배포해줘”라는 요청이 있다고 하자. 이 요청에는 조사, 정리, 파일 수정, 검증, 발행이 함께 들어 있다.

역할 기준으로 보면 조사형/정리형/실행형이 필요하다. 실행 방식 기준으로 보면 지금 대화에서 바로 처리할지, 별도 profile을 직접 부를지, delegation으로 빠르게 나눌지, 독립 subagent를 띄울지 판단해야 한다. 이 판단이 반복되면 [역할형 에이전트별 Skill](https://wikidocs.net/346237)로 남겨 각 에이전트가 어떤 기준을 따라야 하는지 고정할 수 있다.

| 구분 | 묻는 질문 | 예시 |
|---|---|---|
| 역할 분리 | 어떤 실패를 줄여야 하는가? | 근거 부족은 조사형, 구조 문제는 정리형, 검증 누락은 실행형 |
| 실행 방식 | 그 역할을 어떤 단위로 움직일 것인가? | profile 직접 호출, delegation, subagent, cron |

## 네 가지 실행 방식

| 실행 방식 | 의미 | 좋은 경우 | 주의점 |
|---|---|---|---|
| 메인 창구 직접 처리 | 현재 AI 개인비서가 바로 판단하고 답한다 | 짧은 판단, 우선순위, 범위 조정, 최종 보고 | 깊은 조사/긴 수정까지 붙잡으면 병목이 된다 |
| profile 직접 호출 | 특정 profile의 에이전트를 바로 부른다 | 방울이/뽀동이/하망이처럼 memory, skill, 톤, 역할 기준이 중요한 일 | 사용자가 라우팅을 너무 많이 떠안으면 피곤해진다 |
| delegation | 메인 에이전트가 하위 작업을 맡기고 결과만 받아 통합한다 | 빠른 조사, 비교, 리뷰, 병렬 확인처럼 부모가 통합할 수 있는 일 | 하위 에이전트는 사용자와 직접 대화하지 않으므로 입력과 완료 기준이 선명해야 한다 |
| 독립 subagent 실행 | 별도 Hermes 프로세스나 worktree, background 작업으로 독립 실행한다 | 오래 걸리는 코딩, 독립 검증, 긴 파일 작업, 충돌을 피해야 하는 작업 | 오버헤드가 크고 결과 회수/충돌/검증 기준을 따로 관리해야 한다 |
| cron 자동화 | 정해진 시간이나 조건에 fresh session으로 실행한다 | 매일 브리핑, 정기 모니터링, 반복 리포트 | 현재 대화 맥락을 기대하면 실패한다. prompt가 self-contained해야 한다 |

네 가지라고 부를 때는 보통 직접 처리, profile 직접 호출, delegation, 독립 subagent를 뜻한다. 여기에 반복성과 시간 조건이 붙으면 cron이 별도 실행 방식으로 들어온다.

## 언제 profile을 직접 시키는가

profile 직접 호출은 “이 일은 그 에이전트의 정체성과 축적된 기준이 중요하다”는 뜻이다.

예를 들어 방울이에게 확장조사를 맡기면 조사형 기준, 출처 확인 습관, 신호 판단 방식이 살아난다. 뽀동이에게 WikiDocs 구조 정리를 맡기면 문체, 전자책 호환, SEO/GEO, 본문 링크 기준이 함께 따라온다. 하망이에게 이미지를 맡기면 본문 메시지와 시각 QA 기준을 분리해서 볼 수 있다.

이 방식은 역할이 분명할 때 좋다. 대신 사용자가 매번 “누구를 불러야 하지?”를 고민하게 만들면 [AI 개인비서 메인 창구](https://wikidocs.net/345891)의 장점이 사라진다. 그래서 기본은 메인 창구가 받고, 필요할 때 특정 profile로 넘기는 편이 안정적이다.

## 언제 delegation을 쓰는가

delegation은 현재 작업 안에서 빠르게 하위 작업을 나누는 방식이다. 별도 profile을 길게 운영하기보다, 부모 에이전트가 작은 조사/검토/비교를 맡기고 결과를 받아 통합한다.

좋은 delegation 요청은 이렇게 생긴다.

```text
공식 Hermes Agent 문서 기준으로 profile, delegation, subagent 차이를 확인해줘.
각 방식의 좋은 사용처와 주의점을 표로 정리하고,
WikiDocs 독자에게 설명할 때 헷갈릴 표현을 알려줘.
```

나쁜 delegation 요청은 “이거 처리해줘”처럼 범위 없이 끝난다. 하위 에이전트는 사용자의 추가 질문을 받을 수 없기 때문에 범위, 출력 형식, 판단 기준을 처음에 줘야 한다.

## 언제 독립 subagent를 띄우는가

독립 subagent는 더 무겁지만 더 강한 분리다. 별도 Hermes 프로세스, worktree, background 실행처럼 독립된 세션과 실행 환경을 갖는다.

이 방식은 오래 걸리는 개발 작업, 여러 파일을 고치는 작업, 별도 검증이 필요한 작업에 맞다. 예를 들어 실행형 에이전트가 별도 worktree에서 기능을 구현하고, 메인 창구가 결과 diff와 테스트 결과만 받아 검토하는 흐름이다.

다만 독립 실행은 조율 비용이 크다. 어느 브랜치에서 작업하는지, 무엇을 완료로 볼지, 충돌이 나면 누가 해결할지, 최종 통합자가 누구인지가 없으면 결과가 흩어진다.

## 공식 기능 기준: delegation과 subagent

Hermes Agent의 delegation은 메인 에이전트가 하위 작업을 맡기고 결과를 받아 통합하는 방식이다. 병렬 조사, 비교, 리뷰처럼 범위가 선명하고 부모가 최종 판단할 수 있는 일에 맞다.

subagent는 더 독립적인 실행 단위다. 별도 세션/프로세스/작업공간으로 움직일 수 있어서 긴 구현이나 검증에 유리하지만, 그만큼 결과 회수와 충돌 관리가 필요하다. 둘 다 “역할형 에이전트”라는 개념과 연결되지만, 하나는 역할 분리이고 다른 하나는 실행 방식이라는 점을 구분해야 한다.

## 실행 방식 선택 기준

| 상황 | 추천 방식 |
|---|---|
| 한두 문장 판단이나 보고면 충분하다 | 메인 창구 직접 처리 |
| 특정 역할의 memory/skill/톤이 중요하다 | profile 직접 호출 |
| 짧은 하위 조사나 병렬 검토가 필요하다 | delegation |
| 오래 걸리는 파일 수정/코딩/검증이 필요하다 | 독립 subagent 실행 |
| 정해진 시간에 반복되어야 한다 | cron 자동화 |
| 결과가 공유 콘텐츠로 남는다 | 정리형 에이전트와 실행형 검증을 함께 둔다 |

이 표의 핵심은 “강한 방식이 항상 좋은 방식은 아니다”라는 점이다. 짧은 판단에 독립 subagent를 띄우면 느리고, 긴 검증 작업을 메인 창구가 붙잡으면 품질이 흔들린다.

## WikiDocs 페이지 추가 요청으로 보는 실행 방식

이번 페이지를 추가하는 요청도 여러 층으로 나뉜다.

1. 메인 창구가 요청을 해석한다.
2. 기존 2장/3장/5장 구조를 확인한다.
3. 새 페이지는 5장에 넣는 것이 맞다고 판단한다.
4. 2장과 3장에는 “직접 처리/위임/역할 분리” 문맥에서 새 페이지로 연결한다.
5. 파일을 수정하고 WikiDocs 규칙을 검증한다.
6. GitHub 원본에 반영하고 공개 배포 흐름으로 넘긴다.

이 흐름에서 중요한 것은 “에이전트를 많이 썼다”가 아니다. 역할과 실행 방식을 구분했기 때문에 독자가 나중에 같은 문제를 만나도 판단 기준을 재사용할 수 있다.

같은 요청이라도 실행 방식은 달라질 수 있다. “이 문장만 고쳐줘”라면 메인 창구가 직접 처리하면 된다. “공식 문서와 기존 장을 비교해서 빠진 내용을 찾아줘”라면 delegation이 빠르다. “뽀동이 문체와 WikiDocs 발행 기준으로 전체 장을 다시 잡아줘”라면 profile 기준이 중요하다. “매일 아침 같은 기준으로 신호를 찾아줘”라면 cron이 맞다. 실행 방식은 멋있어 보이는 쪽이 아니라 실패 위험을 가장 줄이는 쪽으로 고른다.

## 운영 체크리스트

- 지금 필요한 것은 역할 분리인가, 실행 방식 선택인가?
- 메인 창구가 직접 처리해도 충분한가?
- 특정 profile의 memory/skill/톤이 필요한가?
- 하위 작업이 짧고 병렬화 가능한가?
- 독립 실행이 필요할 만큼 오래 걸리거나 충돌 위험이 있는가?
- 반복 실행이라면 cron prompt가 fresh session에서도 충분한가?
- 최종 통합자와 검증 기준이 정해졌는가?

## FAQ

### profile 직접 호출과 delegation은 무엇이 다른가요?

profile 직접 호출은 특정 역할 에이전트를 바로 부르는 방식이다. 그 profile의 memory, skill, 톤, 판단 기준을 쓰고 싶을 때 적합하다. delegation은 현재 에이전트가 하위 작업을 맡기고 결과를 받아 통합하는 방식이다. 빠른 분해와 병렬 검토에 좋다.

### subagent는 delegation과 같은 말인가요?

넓게 보면 둘 다 하위 에이전트를 쓰는 방식이지만 운영 감각은 다르다. delegation은 부모 작업 안에서 빠르게 나누는 가벼운 위임에 가깝고, 독립 subagent 실행은 별도 세션/프로세스/작업공간을 가진 무거운 실행에 가깝다.
