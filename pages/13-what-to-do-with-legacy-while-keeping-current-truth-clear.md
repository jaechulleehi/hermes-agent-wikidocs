## 과거 유산과 현재 기준은 어떻게 나눌까

![과거 유산을 보관하고 현재 기준 문서를 분리하는 흐름](../assets/how-image-agent-creates-wikidocs-visuals/ch4-3-legacy-vs-current-standard-codex.png)

AI 운영 시스템을 오래 쓰면 과거 문서가 자산이면서 동시에 위험이 된다. OpenClaw에서 Hermes로 넘어올 때도 그랬다. 예전 정체성 문서, memory, cron, gateway, agent binding은 운영 경험을 담고 있었지만, Hermes의 현재 구조와 1:1로 맞지는 않았다.

그래서 과거 유산은 버릴 것과 살릴 것을 나눠야 한다. 기준은 “예전에 썼다”가 아니라 “지금도 source of truth인가”다. 현재 기준은 [memory/profile/session](https://wikidocs.net/345899), shared-memory, AGENTS, skill, GitHub 원본처럼 Hermes가 실제로 읽고 운영하는 층에 있어야 한다.

## 왜 과거 흔적이 현재 규칙을 흔들까

과거 문서가 위험한 이유는 틀렸기 때문이 아니다. 일부는 여전히 맞고, 일부는 이름만 같고 의미가 달라졌기 때문이다. 예를 들어 OpenClaw 시절의 정체성 문서에는 뽀동이의 콘텐츠 품질 책임자라는 핵심이 살아 있었다. 하지만 예전 라우팅, 경로, 실행 방식은 Hermes의 profile/skill/gateway 구조에 맞춰 다시 해석해야 했다.

| 과거 유산 | 그대로 가져오면 생기는 문제 | 현재 기준으로 바꾸는 법 |
|---|---|---|
| 정체성 문서 | 자동 로드 위치를 착각함 | Hermes profile과 AGENTS 기준으로 재정리 |
| memory 폴더 | 작업 로그와 장기 규칙이 섞임 | memory/shared-memory/Obsidian으로 분리 |
| cron 설정 | 예전 실행 전제를 그대로 믿음 | 현재 cron job, gateway, delivery 기준으로 재검증 |
| gateway 흔적 | 상태와 실제 전달 여부를 혼동함 | 현재 gateway 로그와 메시징 연결을 확인 |
| 콘텐츠 규칙 | 채널별 기준이 섞임 | WikiDocs/블로그/강의 목적별로 재배치 |

## 실제 케이스: 자동 이사가 아니라 수동 재구성이었다

마이그레이션에서 배운 가장 큰 교훈은 “파일이 옮겨졌는가”보다 “운영 기준이 다시 살아났는가”를 봐야 한다는 점이었다. 일부 항목은 archive로 남았고, 일부 항목은 Hermes의 현재 구조로 다시 넣어야 했다.

공개 글에 필요한 것은 내부값 자체가 아니라 판단 기준이다. 예를 들어 특정 인증값의 위치를 설명하는 대신, “접근 권한과 실행 환경은 공개 문서 밖에서 별도로 검증한다”는 기준을 남겨야 한다. 독자는 값이 아니라 원칙을 가져가야 한다.

## 실제 케이스: 뽀동이 정체성 복원

사용자가 “왜 소울이가 없냐”고 물었던 사례는 4장의 좋은 예다. 파일이 없었던 것이 아니라, 현재 Hermes 쪽 정체성 문서가 기능 설명에 치우쳐 OpenClaw 시절의 햄스터 에너지와 콘텐츠 퀄리티 책임자 역할이 약해져 있었다.

이 문제는 단순 복사로 해결하지 않았다. 과거 문서의 좋은 정체성은 살리되, Hermes에서 실제로 읽히는 profile/AGENTS 구조에 맞게 다시 정리해야 했다. 과거 유산은 원문 보관만으로 살아나는 것이 아니라, 현재 운영 구조에 맞게 재해석될 때 살아난다.

## 남길 것과 뺄 것

| 남길 것 | 빼거나 추상화할 것 |
|---|---|
| 왜 그 규칙이 생겼는지의 배경 | 특정 환경에서만 의미 있는 내부값 |
| 현재도 유효한 역할과 말투 | 더 이상 읽히지 않는 자동 로드 전제 |
| 실패에서 나온 운영 기준 | 특정 환경에만 맞는 임시 명령 |
| 공개 글에 도움이 되는 운영 스토리 | 독자가 몰라도 되는 사적인 설정값 |

핵심은 과거를 지우지 않는 것이다. 다만 과거를 현재 기준인 것처럼 쓰지 않는다.

## 현재 문서를 정리할 때의 체크리스트

1. 이 문서가 지금도 source of truth인지 확인한다.
2. 과거 기록이면 archive나 참고 자료로 표시한다.
3. 현재 profile이 실제로 읽는 파일인지 확인한다.
4. 현재 운영 규칙과 충돌하는 부분을 분리한다.
5. 공개 문서로 바꿀 때 내부값은 제거하고 판단 기준을 남긴다.
6. 바뀐 기준은 memory, shared-memory, skill, GitHub 중 맞는 위치에만 남긴다.

## FAQ

### 과거 문서를 다 지우면 안 되나요?

지우기보다 위치를 바꾸는 편이 좋다. 과거 문서는 시행착오와 배경을 담고 있지만, 현재 실행 기준과 섞이면 위험하다.

### 과거 이름을 본문에서 써도 되나요?

가능하다. 다만 공개 개념을 먼저 설명한 뒤 실제 운영 사례로 써야 한다. 예를 들어 OpenClaw는 “과거 시스템 유산을 현재 Hermes 기준으로 재구성한 사례”로 다루면 좋다.

### 내부값은 어떻게 처리하나요?

값은 공개하지 않는다. 대신 어떤 종류의 값이 공개 문서에 남으면 안 되는지, 현재 기준에서는 어디에서 검증해야 하는지만 설명한다.
