## 과거 유산과 현재 기준은 어떻게 나눌까

AI 운영 시스템을 오래 쓰면 과거 문서가 자산이면서 동시에 위험이 된다. OpenClaw에서 Hermes로 넘어올 때도 그랬다. 예전 SOUL, memory, cron, gateway, agent binding은 운영 경험을 담고 있었지만, Hermes의 현재 구조와 1:1로 맞지는 않았다.

그래서 과거 유산은 버릴 것과 살릴 것을 나눠야 한다. 이때 기준은 “예전에 썼다”가 아니라 “지금도 source of truth인가”다. 현재 기준은 [memory/profile/session](https://wikidocs.net/345899), shared-memory, AGENTS, skill, GitHub 원본처럼 Hermes가 실제로 읽고 운영하는 층에 있어야 한다.

## 왜 과거 흔적이 현재 규칙을 흔들까

과거 문서가 위험한 이유는 틀렸기 때문이 아니다. 일부는 여전히 맞고, 일부는 이름만 같고 의미가 달라졌기 때문이다. 예를 들어 OpenClaw의 정체성 문서에는 뽀동이의 콘텐츠 품질 책임자라는 핵심이 살아 있었다. 하지만 예전 라우팅, 경로, 실행 방식은 Hermes의 profile/skill/gateway 구조와 맞춰 다시 해석해야 했다.

| 과거 유산 | 그대로 가져오면 생기는 문제 | 현재 기준으로 바꾸는 법 |
|---|---|---|
| SOUL/IDENTITY | 자동 로드 위치를 착각함 | Hermes profile의 SOUL/AGENTS 기준으로 재정리 |
| memory 폴더 | 작업 로그와 장기 규칙이 섞임 | memory/shared-memory/Obsidian으로 분리 |
| cron 설정 | 예전 runtime 전제를 그대로 믿음 | 현재 cron job, gateway, delivery 기준으로 재검증 |
| gateway 흔적 | status와 실제 전달 상태를 혼동함 | 현재 gateway 로그와 메시징 연결을 확인 |
| 콘텐츠 규칙 | 채널별 기준이 섞임 | WikiDocs/블로그/강의 목적별로 재배치 |

## 실제 케이스: OpenClaw 설정은 자동 이사가 아니라 수동 재구성이었다

마이그레이션에서 배운 가장 큰 교훈은 “파일이 옮겨졌는가”보다 “운영 기준이 다시 살아났는가”를 봐야 한다는 점이었다. 일부 항목은 archive로 남았고, 일부 항목은 Hermes의 현재 구조로 다시 넣어야 했다.

이때 민감정보나 독자가 몰라도 되는 내부값은 공개 본문에 넣지 않는다. 필요한 것은 실제 값이 아니라 판단 기준이다. 예를 들어 “token이 어디 있었다”가 아니라 “credential은 공개 문서에 남기지 않고, 현재 profile/gateway 설정에서 별도로 검증한다”가 독자에게 필요한 문장이다.

## 실제 케이스: 뽀동이 soul은 없어진 것이 아니라 약해진 것이었다

로이드가 “왜 소울이가 없냐”고 물었던 사례는 4장의 좋은 예다. 파일이 없었던 것이 아니라, 현재 Hermes SOUL이 기능 설명에 치우쳐 OpenClaw 시절의 햄스터 에너지와 콘텐츠 퀄리티 책임자 정체성이 약해져 있었다.

이 문제는 복사로 해결하지 않았다. OpenClaw의 좋은 정체성은 살리되, Hermes에서 실제로 로드되는 SOUL/AGENTS 구조에 맞게 재정리해야 했다. 과거 유산은 원문 보관이 아니라 현재 운영 구조에 맞는 재해석으로 살아난다. 이 기준은 나중에 [OpenClaw에서 Hermes로 넘어올 때 점검할 것](https://wikidocs.net/345920)을 만들 때도 그대로 쓰인다.

## 남길 것과 뺄 것

| 남길 것 | 빼거나 추상화할 것 |
|---|---|
| 왜 그 규칙이 생겼는지의 배경 | 토큰, 계정, 내부 경로, 채널 ID |
| 역할 분리와 판단 기준 | 오래된 명령을 그대로 따라 하라는 문장 |
| 실패/복구 순서 | 특정 개인/고객/비공개 프로젝트 상세 |
| 공개 글에 도움이 되는 운영 스토리 | 독자가 몰라도 되는 내부 설정값 |

## 현재 문서를 정리할 때의 체크리스트

1. 이 문서가 지금도 source of truth인지 확인한다.
2. archive, 참고자료, 현재 기준 문서를 구분한다.
3. current profile이 실제로 읽는 파일인지 확인한다.
4. 기억할 규칙인지, 세션/작업 로그인지 나눈다.
5. 공개 문서로 바꿀 때 민감정보와 내부값을 제거한다.
6. 관련 페이지에 contextual link를 건다.

## FAQ

### 과거 문서를 다 지우면 안 되나요?

지우기보다 역할을 바꿔야 한다. 과거 문서는 archive/근거 자료로 남길 수 있지만, 현재 기준처럼 읽히면 안 된다.

### 과거 이름을 본문에서 써도 되나요?

가능하다. 다만 먼저 공개 개념을 설명하고, OpenClaw나 하비/뽀동이 같은 이름은 실제 사례로 써야 한다.

### 민감정보는 어떻게 처리하나요?

본문에는 넣지 않는다. 필요하면 “credential은 별도 보안 경로에서 관리한다”처럼 원칙만 남긴다.
