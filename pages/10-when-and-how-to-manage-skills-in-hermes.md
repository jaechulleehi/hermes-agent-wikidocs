## Hermes Agent 스킬은 언제 만들고 어떻게 관리할까

[Hermes Agent](00-hermes-agent-core-concepts.md)에서 skill은 “나중에 또 할 일”을 위한 작업 매뉴얼이다. 한 번 성공한 명령을 대화 속에만 남기면 다음 세션에서 다시 헤맨다. 반대로 모든 일을 skill로 만들면 skill 폴더가 쓰레기통이 된다.

좋은 기준은 반복성, 위험도, 검증 필요성이다. 같은 일을 다시 할 가능성이 있고, 실수하면 비용이 있으며, 검증 절차가 필요한 작업이라면 skill로 남길 가치가 있다.

## 스킬은 많을수록 좋은 게 아니다

skill은 에이전트의 기억을 강하게 만든다. 그래서 잘 만든 skill은 품질을 올리지만, 오래된 skill은 오히려 사고를 만든다.

예를 들어 [WikiDocs](07-why-we-write-the-wiki-first.md) 작업에서 “H1 금지, 헤딩 간격 확인, 중점 문자 금지, 커밋/푸시” 같은 절차는 반복된다. 이런 것은 skill이 맞다. 하지만 오늘만 쓴 임시 파일 경로나 특정 세션의 작업 로그는 skill이 아니다.

## 언제 skill로 만들까

| 조건 | skill로 만들 가능성 |
|---|---|
| 같은 작업을 3번 이상 반복할 것 같다 | 높음 |
| 검증 순서가 있다 | 높음 |
| 실수하면 공개 문서나 배포에 영향이 있다 | 높음 |
| 사용자 선호가 계속 적용되어야 한다 | 높음 |
| 오늘만 쓰는 임시 명령이다 | 낮음 |
| 프로젝트 진행 로그다 | 낮음 |

skill은 “무엇을 기억할까”보다 “다음에 어떻게 다시 할까”에 가깝다.

## 만든 뒤가 더 중요하다

skill은 한 번 만들고 끝나는 문서가 아니다. 실제 작업 중 빠진 절차가 발견되면 바로 고쳐야 한다. 로이드가 “구분할 때는 /를 써”라고 정정했을 때, 원고만 고치면 다음 장에서 다시 실수할 수 있다. 그래서 AGENTS.md, [memory](03-why-same-harvey-feels-like-different-memory.md), skill까지 함께 고쳤다.

이게 skill 관리의 핵심이다. 성공한 절차를 저장하고, 실패한 절차를 패치하고, 더 이상 맞지 않는 절차는 없애야 한다.

## 실제 운영 예시

```text
하비야, 이건 앞으로 계속 반복될 것 같아.
방울이가 조사하고, 뽀동이가 WikiDocs 구조로 정리하고,
검증 후 커밋/푸시하는 절차를 skill에 반영해줘.
다음부터는 같은 기준으로 시작하게 해줘.
```

이런 요청은 skill로 남기기 좋다. 반대로 “이번 파일 하나만 이름 바꿔줘”는 skill이 아니라 현재 작업이다.

실제 운영에서는 SEO/GEO 치트시트 제작 과정에서 이 기준이 그대로 드러났다. 이미지 한 장을 만든 뒤에도 브랜드 톤, 금지 장식, 헤더 여백, LinkedIn CTA 기준이 반복될 가능성이 보였고, 그래서 치트시트 제작 skill과 LinkedIn 본문 skill을 분리했다. 자세한 흐름은 10장의 실제 운영 케이스에서 볼 수 있다.

## 운영 기준

skill을 만들거나 고칠 때는 아래 기준을 둔다.

1. 트리거 조건을 분명히 쓴다.
2. 필요한 파일, 명령, 검증 순서를 적는다.
3. 사용자 선호와 금지 사항을 반영한다.
4. 토큰, 웹훅, 개인 경로는 원문으로 넣지 않는다.
5. 실제 작업 중 빠진 절차를 발견하면 바로 patch한다.
6. 오래된 skill은 archive하거나 삭제한다.
7. memory에는 사실과 선호를, skill에는 절차를 남긴다.

## FAQ

### memory와 skill 중 어디에 남겨야 하나요?

사용자 선호나 오래 유지할 사실은 memory에 가깝다. 반복 실행 절차, 검증 방법, 명령 흐름은 skill에 가깝다.

### skill이 많아지면 더 똑똑해지나요?

꼭 그렇지는 않다. 최신 기준으로 관리된 skill은 강하지만, 오래된 skill은 잘못된 절차를 반복하게 만든다.
