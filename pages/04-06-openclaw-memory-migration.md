## OpenClaw에서 Hermes로 기억을 옮길 때 무엇을 버릴까

Hermes Agent 같은 AI 운영 시스템을 오래 쓰면 과거 문서가 자산이면서 동시에 위험이 된다. 특히 [Obsidian LLM Wiki](https://wikidocs.net/346129)처럼 누적되는 지식층이 생기면, 과거 유산과 현재 기준을 더 명확히 나눠야 한다. OpenClaw에서 Hermes로 넘어올 때도 그랬다. 예전 SOUL, IDENTITY, memory, cron, gateway, agent binding은 운영 경험을 담고 있었지만, Hermes의 현재 구조와 1:1로 맞지는 않았다.

그래서 기억 이관은 파일 복사가 아니라 기준 재구성이다. 무엇을 살리고, 무엇을 archive로 두고, 무엇을 현재 Hermes의 memory/shared-memory/Obsidian/profile/skill 구조로 다시 배치할지 판단해야 한다. 이 정리가 끝나야 [OpenViking/RAG](https://wikidocs.net/346131) 같은 회수층도 낡은 기준을 반복하지 않는다.

## 과거 기억을 그대로 옮기면 왜 위험할까

과거 문서가 위험한 이유는 틀렸기 때문이 아니다. 일부는 여전히 맞고, 일부는 이름만 같고 의미가 달라졌기 때문이다. “memory”라는 이름이 같아도 OpenClaw 시절의 쓰임과 Hermes의 주입 방식은 다를 수 있다.

| 과거 유산 | 그대로 가져오면 생기는 문제 | 현재 기준으로 바꾸는 법 |
|---|---|---|
| SOUL/IDENTITY | 자동 로드 위치를 착각함 | SOUL.md와 AGENTS.md 역할로 재정리 |
| user memory | 사용자 선호와 작업 로그가 섞임 | USER.md/memory/session_search로 분리 |
| workspace memory | 프로젝트 상태와 장기 규칙이 뒤섞임 | shared-memory/Obsidian/GitHub log로 재배치 |
| cron/gateway 흔적 | 예전 runtime을 현재 기준으로 착각함 | 현재 profile/gateway/cron 상태로 재검증 |
| 콘텐츠 규칙 | 채널별 기준이 섞임 | WikiDocs/블로그/강의 목적별로 분리 |

## 실제 케이스: 뽀동이 SOUL은 없어진 것이 아니라 약해진 것이었다

사용자가 “왜 소울이가 없냐”고 물었던 사례는 기억 이관의 좋은 예다. 파일이 없었던 것이 아니라, 현재 Hermes SOUL이 기능 설명에 치우쳐 OpenClaw 시절의 햄스터 에너지와 콘텐츠 퀄리티 책임자 정체성이 약해져 있었다.

이 문제는 예전 파일을 통째로 복사해서 해결할 일이 아니었다. OpenClaw의 좋은 정체성은 살리되, Hermes에서 실제로 로드되는 SOUL.md와 AGENTS.md 구조에 맞게 재정리해야 했다. 과거 유산은 원문 보관이 아니라 현재 운영 구조에 맞는 재해석으로 살아난다.

## 남길 것과 버릴 것

| 구분 | 남길 것 | 버리거나 archive할 것 |
|---|---|---|
| 정체성 | 에이전트의 역할, 톤, 품질 기준 | 현재 로드되지 않는 중복 문서 |
| 운영 규칙 | 지금도 반복되는 판단 기준 | 예전 runtime에만 맞는 명령 |
| 사용자 선호 | 장기적으로 반복될 협업 방식 | 특정 날짜의 작업 상태 |
| 프로젝트 지식 | 누적 지식으로 연결할 원장 | 오래된 임시 메모 |
| 복구 경험 | 재발 방지 체크리스트 | 불필요한 내부값 |

## 기억 이관 체크리스트

1. 이 문서가 지금도 source of truth인지 확인한다.
2. 현재 Hermes가 실제로 읽는 파일인지 확인한다.
3. 정체성, 운영 규칙, 사용자 선호, 작업 로그를 나눈다.
4. 장기 규칙은 memory/USER.md로 압축한다.
5. 팀 공통 기준은 shared-memory로 보낸다.
6. 누적 지식은 Obsidian LLM Wiki로 보낸다.
7. 반복 절차는 skill이나 체크리스트로 승격한다.
8. 공유 문서에는 내부값을 제거하고 판단 기준만 남긴다.

## 이관 체크리스트 예시

OpenClaw에서 Hermes로 옮길 때 중요한 것은 “많이 가져오기”가 아니라 “현재 운영에 맞게 재분류하기”다. 예전 문서가 맞는 말을 하고 있어도, 지금의 도구 구조와 역할 체계에 맞지 않으면 그대로 옮기면 안 된다.

```text
[ ] 지금도 반복 적용되는 규칙인가
[ ] 특정 에이전트의 정체성/역할인가
[ ] 사용자 선호인가, 작업 로그인가
[ ] 팀 전체가 같이 봐야 하는가
[ ] 공개 문서로 바꿔도 되는 내용인가
[ ] 내부 경로/토큰/계정/채널값이 섞여 있지 않은가
```

| 과거 자료 | 이관 판단 | 새 위치 |
|---|---|---|
| 에이전트 말투/역할 기준 | 유지 | profile / AGENTS.md |
| 사용자 반복 선호 | 유지 | USER.md / memory |
| 오래된 임시 작업 상태 | 폐기 또는 session_search | 장기 memory 금지 |
| 팀 운영 규칙 | 정리 후 유지 | shared-memory |
| 함께 읽을 만한 운영 교훈 | 정리 | WikiDocs |

## 자주 헷갈리는 질문

### 과거 memory를 전부 Hermes memory로 옮기면 안 되나요?

안 된다. 과거 memory 안에는 장기 규칙, 작업 로그, 프로젝트 상태, 오래된 설정이 섞여 있을 수 있다. 그대로 옮기면 현재 판단을 흐린다.

### OpenClaw 이름을 공유 글에서 써도 되나요?

가능하다. 다만 먼저 일반 개념을 설명하고, OpenClaw는 실제 마이그레이션 사례로 써야 한다. 읽는 사람에게 필요한 것은 내부 세계관이 아니라 이관 기준이다.

### 이 내용은 9장 마이그레이션과 어떻게 다르나요?

4장은 기억 이관의 원칙을 다룬다. 9장은 실제 전환/복구 체크리스트와 실행 순서를 다룬다.
