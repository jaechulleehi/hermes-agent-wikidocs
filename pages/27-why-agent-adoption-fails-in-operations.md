## AI 에이전트 도입은 왜 운영에서 자주 무너질까

AI 에이전트 도입이 운영에서 무너지는 이유는 모델 성능이 부족해서만은 아니다. 대부분은 요청 흐름, 권한, 검증, 기록, 책임 경계가 정리되지 않은 상태에서 에이전트를 업무 안에 넣기 때문이다.

[Hermes Agent](https://wikidocs.net/346055)를 조직에서 쓰려면 “AI가 대신 일한다”가 아니라 “AI 개인비서와 역할형 에이전트가 어떤 순서로 일하고, 사람이 어디서 판단하고, 결과가 어디에 남는가”를 먼저 설계해야 한다. 데모는 한 번 성공하면 되지만 운영은 같은 품질을 반복해야 한다.

## 왜 처음에는 모델부터 바꾸려 할까

처음 AI 에이전트를 도입하면 문제를 모델 성능으로 보기 쉽다.

```text
응답이 약하다 → 더 좋은 모델을 쓰자
조사가 부족하다 → 더 긴 프롬프트를 쓰자
실행이 불안하다 → 더 강한 에이전트를 붙이자
```

물론 모델은 중요하다. 하지만 조직 운영에서 더 자주 무너지는 지점은 모델이 아니라 흐름이다. 누가 요청했고, 어떤 근거를 봤고, 어디까지 실행해도 되는지, 결과를 누가 승인할지 정해져 있지 않으면 좋은 모델도 흔들린다.

## 도입 조직이 자주 겪는 시행착오

| 시행착오 | 실제 문제 |
|---|---|
| 데모 흐름을 운영 흐름으로 착각한다 | 한 번 되는 것과 매일 반복되는 것은 다르다 |
| 모든 일을 하나의 에이전트에게 맡긴다 | 조사/정리/실행/검증 책임이 섞인다 |
| 사람 개입을 예외로 둔다 | 승인과 검토가 늦게 끼어들어 흐름이 깨진다 |
| 기록을 채팅에만 남긴다 | 나중에 재사용하거나 감사하기 어렵다 |
| 실패 시 복구 기준이 없다 | 문제가 생기면 담당자 감으로 처리한다 |

조직 도입은 이 시행착오를 줄이는 설계부터 시작해야 한다.

## 실제 운영 흐름으로 보면 무엇이 달라질까

로이드의 운영에서는 하비가 메인 창구 역할을 한다. 사용자는 하비에게 요청하고, 하비는 바로 답할지, 방울이에게 확장조사를 맡길지, 뽀동이가 구조를 잡게 할지, 봉구가 실행 검증을 맡을지 판단한다. 이미지가 필요하면 [하망이](https://wikidocs.net/345989)가 시각 방향을 잡을 수 있다.

조직에 이 구조를 옮길 때는 이름보다 책임이 중요하다.

```text
요청 접수 → 범위 판단 → 역할형 에이전트 위임 → 사람 검토 → 실행/발행 → 기록/체크리스트 업데이트
```

이 흐름을 설명할 수 있어야 조직용 AI 에이전트 운영이 시작된다.

## 조직 도입 기준

처음 도입하는 조직은 아래 순서로 본다.

1. AI가 맡을 업무와 맡지 않을 업무를 나눈다.
2. 요청이 들어오는 메인 창구를 정한다.
3. 조사형/정리형/실행형/이미지형 에이전트의 책임을 나눈다.
4. 각 단계의 입력, 출력, 실패 조건을 적는다.
5. 사람 검토가 필요한 지점을 명시한다.
6. 결과물이 남을 [source of truth](https://wikidocs.net/345915)를 정한다.
7. 실패했을 때 볼 체크리스트와 [복구 플레이북](https://wikidocs.net/345918)을 만든다.
8. 작은 업무 하나로 반복 운영한 뒤 확장한다.

## 작은 도입 예시

처음부터 전사 자동화를 만들 필요는 없다. 예를 들어 주간 리서치 보고서 하나부터 시작할 수 있다.

```text
1. Slack에서 하비에게 주간 주제를 요청한다.
2. 방울이가 공식 문서와 시장 자료를 확장조사한다.
3. 뽀동이가 보고서 구조와 WikiDocs 초안을 만든다.
4. 담당자가 검토하고 공개 가능 정보만 남긴다.
5. GitHub에 커밋하고 WikiDocs에 발행한다.
6. 반복 기준은 skill이나 체크리스트로 남긴다.
```

이 흐름이 안정되면 다른 팀 업무로 확장할 수 있다.

## FAQ

### 조직 도입은 어느 업무부터 시작하는 게 좋나요?

반복되지만 위험도가 낮고, 결과 검토가 쉬운 업무부터 시작하는 것이 좋다. 주간 리서치, 회의 요약, 내부 FAQ, 문서 초안이 좋은 출발점이다.

### 에이전트를 많이 만들수록 좋은가요?

아니다. 역할이 분명하지 않으면 에이전트가 많을수록 흐름이 복잡해진다. 먼저 메인 창구와 책임 경계를 정한 뒤 필요한 역할만 늘리는 편이 낫다.

### 완전 자동화로 바로 가도 되나요?

초기에는 권장하지 않는다. 사람 검토 지점이 있는 반자동 흐름으로 시작하고, 실패 패턴과 복구 기준이 쌓인 뒤 자동화 범위를 넓히는 편이 안전하다.
