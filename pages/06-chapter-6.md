## 6장. WikiDocs/블로그/강의 콘텐츠 시스템

좋은 조사 결과가 있다고 바로 좋은 글이 되지는 않는다. 또 좋은 블로그 글이 있다고 바로 강의가 되지도 않는다. 콘텐츠 시스템은 원자료, 위키, 공개 문서, 블로그, 강의, 이미지 자산을 각각 다른 역할로 나누는 운영 구조다.

우리는 Hermes Agent 책을 만들면서 이 차이를 분명히 봤다. 처음에는 기존 블로그를 WikiDocs로 옮기는 작업처럼 보였지만, 실제로는 공식 docs 반영, 실제 운영 케이스 회수, 본문 내부 링크, 이미지, GitHub 발행, WikiDocs 동기화까지 이어지는 콘텐츠 운영이었다.

## 이 장에서 다루는 문제

| 문제 | 흔한 착각 | 실제 기준 |
|---|---|---|
| WikiDocs와 블로그 | 같은 글을 복사하면 된다 | WikiDocs는 책 구조, 블로그는 유입/캠페인 목적 |
| Obsidian | 메모가 많으면 지식이 된다 | source note와 운영 원장을 연결해야 한다 |
| 조사 결과 | 정보가 많으면 글이 좋아진다 | 독자 문제/판단 기준/CTA로 재구성해야 한다 |
| 이미지 | 글 다 쓰고 나중에 붙인다 | 메시지와 위치를 먼저 정해야 한다 |
| 강의 | 문서를 슬라이드로 바꾸면 된다 | 흐름/실습/전환 포인트를 다시 설계해야 한다 |

## 실제 운영 장면: 이 책 자체가 콘텐츠 시스템이다

로이드가 “원래 우리 블로그내용 잘 옮겼는지, 공식 docs 잘 옮겼는지, 내용이 축약되어 보이지 않는지”를 물었을 때, 작업은 단순 이전 검수가 아니었다. `SOURCE_MAP.md`로 블로그 1~27편과 공식 docs 매핑을 확인하고, 각 장마다 세션/Slack/shared-memory에서 실제 운영 이야기를 찾아 다시 썼다.

여기서 WikiDocs는 최종 공개 책이고, GitHub는 원본이다. Obsidian과 shared-memory는 운영 기록과 근거를 담고, 뽀동이는 독자가 읽을 수 있는 구조로 바꾼다. 하망이는 필요한 이미지를 만들고, 하비는 최종 통합과 검증을 본다. 실제 이미지 제작 흐름은 [하망이와 WikiDocs 본문 이미지를 만드는 법](https://wikidocs.net/345989)에서 따로 다룬다.

## 이 장에서 얻을 기준

- WikiDocs는 evergreen한 운영서로 쓴다.
- 블로그는 특정 문제/키워드/캠페인에 맞춰 파생한다.
- 강의는 문서를 그대로 읽는 것이 아니라 흐름과 실습을 다시 설계한다.
- Obsidian은 누적 지식과 원장, shared-memory는 작업 패키지와 handoff에 가깝다.
- 이미지 자산은 장식이 아니라 독자의 이해를 돕는 메시지 단위로 만든다.

이 장은 [외부 도구/MCP/자동화 운영](https://wikidocs.net/345907)과도 이어진다. cron 조사가 콘텐츠 신호를 만들고, GitHub/WikiDocs가 발행 흐름을 잡으며, skill은 반복 제작 품질을 지킨다.
