## 부록 A-3. 나만의 AI 팀 설계 워크시트

이 워크시트는 Hermes Agent를 처음 세팅하거나 기존 AI 사용 방식을 정리할 때 쓰는 빈칸형 점검표다. 목표는 멋진 에이전트 이름을 많이 만드는 것이 아니라, 요청을 누가 받고, 어떤 역할로 나누고, 무엇을 기억하고, 어떤 도구와 연결할지 정하는 것이다.

처음에는 간단히 적어도 된다. 중요한 것은 한 번에 완성하는 것이 아니라, 실제 운영하면서 memory, Skill, toolset, cron, gateway 기준을 조금씩 안정화하는 것이다.

## 1. 내 AI 팀의 목적

```text
내가 AI 팀으로 반복하고 싶은 업무:

이 업무가 지금 자주 막히는 이유:

AI가 대신해주면 좋은 부분:

사람이 계속 판단해야 하는 부분:
```

## 2. 메인 창구 정하기

| 질문 | 내 답 |
|---|---|
| 사용자의 요청을 먼저 받을 AI 개인비서는 누구인가 |  |
| 이 메인 창구가 직접 처리해도 되는 일은 무엇인가 |  |
| 다른 역할형 에이전트에 넘겨야 하는 신호는 무엇인가 |  |
| 최종 결과를 어디로 보고해야 하는가 |  |

## 3. 역할형 에이전트 나누기

| 역할 | 맡길 일 | 맡기면 안 되는 일 | 검증 기준 |
|---|---|---|---|
| 조사형 에이전트 |  |  |  |
| 정리형 에이전트 |  |  |  |
| 실행형 에이전트 |  |  |  |
| 이미지 제작형 에이전트 |  |  |  |
| 제품/기능 정리형 에이전트 |  |  |  |

역할을 나눌 때는 “누가 더 똑똑한가”보다 “어떤 실패 방식이 다른가”를 기준으로 본다. 조사형은 근거가 약해질 수 있고, 정리형은 그럴듯하지만 약한 글을 만들 수 있으며, 실행형은 작은 실수가 실제 상태 변경으로 이어질 수 있다.

## 4. 기억 설계

| 남길 정보 | 둘 곳 | 이유 |
|---|---|---|
| 사용자 선호와 말투 | memory/profile |  |
| 팀 공통 규칙 | shared-memory |  |
| 프로젝트별 기준 | AGENTS.md 또는 프로젝트 문서 |  |
| 과거 작업 결과 | session search/GitHub/WikiDocs |  |
| 긴 원문과 참고 자료 | Obsidian/RAG/GitHub |  |
| 남기면 안 되는 값 | secret store/내부 보안 문서 |  |

## 5. 반복 업무를 Skill로 만들기

| 반복 업무 | Skill 후보인가 | 아직 Skill로 만들면 안 되는 이유 | 검증 순서 |
|---|---|---|---|
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |

Skill은 한 번 한 일을 무조건 저장하는 곳이 아니다. 같은 절차가 반복되고, 검증 기준이 분명하며, 다음에도 재사용할 가능성이 있을 때 만든다.

## 6. 도구와 채널 연결

| 연결 대상 | 연결 방식 | 먼저 확인할 것 |
|---|---|---|
| Slack/Telegram/Discord | gateway | 호출 규칙, 전달 채널, 멀티봇 침묵 기준 |
| GitHub | CLI/API/MCP | 인증, branch, diff, commit/push 기준 |
| WikiDocs | GitHub 연동/MCP | TOC, 이미지, 공개 반영 확인 |
| Google Workspace | MCP/API | OAuth scope, 비용, 권한 |
| 정기 작업 | cron | fresh session prompt, delivery target, 실패 보고 |

## 7. 첫 번째 운영 시나리오

```text
사용자 요청:

하비가 먼저 판단할 것:

방울이가 조사할 것:

뽀동이가 정리할 것:

봉구가 실행/검증할 것:

하망이가 이미지로 도울 수 있는 부분:

최종 결과물:

검증 기준:

다음에 남길 기억/Skill/체크리스트:
```

## 8. 운영 후 회고 질문

1. 요청이 어디서 시작됐는가?
2. 역할 분리가 과했거나 부족하지 않았는가?
3. 결과물이 실제로 검증됐는가?
4. 다음에도 반복할 수 있는 절차가 생겼는가?
5. memory에 남길 것과 Skill로 남길 것이 구분됐는가?
6. 공개 문서로 옮길 때 보호해야 할 정보가 제거됐는가?

이 질문에 답할 수 있으면 AI 팀은 단순한 캐릭터 묶음이 아니라, 반복 가능한 업무 운영 구조가 된다.
