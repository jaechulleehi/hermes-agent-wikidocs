## 크론 조사에서 WikiDocs 발행까지 이어지는 AI 업무 자동화 케이스

AI 업무 자동화의 핵심은 사람이 매번 “이제 조사해줘”라고 말하지 않아도 일이 시작되는 구조를 만드는 것이다. Hermes Agent에서는 cron이 그 시작점을 맡을 수 있고, 하비/방울이/뽀동이 같은 역할형 에이전트가 그 뒤를 이어받는다.

이 케이스는 크론 조사, 확장조사, 글쓰기, 리뷰, GitHub/WikiDocs 발행이 하나의 흐름으로 연결되는 방식이다. 단순한 자동 뉴스 요약이 아니라, 반복적으로 콘텐츠 후보를 만들고 공개 문서까지 이어가는 운영 패턴이다.

## 실제 업무 상황

로이드는 Hermes Agent와 AI 업무 자동화 관련 내용을 계속 발행해야 한다. 그런데 매번 빈 화면에서 글감을 찾고, 조사하고, 구조를 잡고, WikiDocs에 반영하면 흐름이 끊긴다.

그래서 자동화의 시작점을 사람이 아니라 cron에 둔다.

```text
cron 정기 조사
→ 하비가 요약과 우선순위 판단
→ 방울이 확장조사
→ 하비가 뽀동이에게 글쓰기 요청
→ 뽀동이가 WikiDocs 구조로 정리
→ 하비 또는 실행형 에이전트가 GitHub 반영
→ WikiDocs 동기화
```

## 처음에 헷갈리기 쉬운 지점

이 흐름을 만들 때 가장 쉬운 착각은 “cron이 글까지 써주면 된다”라고 생각하는 것이다. 하지만 실제 운영에서는 cron이 최종 글을 쓰기보다 좋은 입력을 만드는 편이 안전하다.

cron은 fresh session에서 실행된다. 이전 대화 맥락을 믿고 움직이면 빠뜨리는 정보가 생긴다. 그래서 cron prompt에는 조사 범위, 기간, 제외할 내용, 결과 형식, 독자, 후속 작업 기준이 들어가야 한다.

## 역할 분리 기준

| 단계 | 담당 | 핵심 책임 | 검증 기준 |
|---|---|---|---|
| 정기 조사 | cron/하비 | 최신 신호 수집, 후보 정리 | 출처와 날짜가 있는가 |
| 확장조사 | 방울이 | 맥락, 비교, 반례, 근거 보강 | 근거와 해석이 분리되어 있는가 |
| 구조화 | 뽀동이 | 독자 문제, 목차, 흐름 정리 | WikiDocs 페이지 구조에 맞는가 |
| 최종 판단 | 하비 | 발행 여부, 우선순위, 연결 위치 결정 | 책 전체 흐름과 맞는가 |
| 발행 | GitHub/WikiDocs | 커밋, push, 동기화 | TOC/링크/검증이 통과했는가 |

## 발행 기준

이 케이스에서 발행 기준은 “내용이 맞는가”만으로 충분하지 않다. WikiDocs 책에 들어가려면 다음 기준을 통과해야 한다.

- 독자 문제가 첫 문단에서 보이는가?
- 내부 이름보다 공개 개념이 먼저 나오는가?
- 실제 운영 흐름이 기능 설명보다 앞서는가?
- TOC에서 들어갈 위치가 명확한가?
- SOURCE_MAP 또는 BOOK_STRUCTURE에 원천과 반영 이유가 남아 있는가?
- GitHub diff로 수정 이력을 추적할 수 있는가?
- WikiDocs 동기화 후 사이드바 흐름이 어색하지 않은가?

## 재사용 체크리스트

- cron prompt가 self-contained 한가?
- 조사 결과가 바로 글이 아니라 원천 자료로 남는가?
- 방울이에게 넘길 확장조사 질문이 분리되어 있는가?
- 뽀동이에게 목적, 독자, 원자료, 원하는 구조가 전달되는가?
- 하비가 최종 통합과 발행 위치를 판단하는가?
- GitHub source of truth와 WikiDocs 공개본의 역할이 분리되어 있는가?

## FAQ

### cron이 바로 글까지 쓰면 안 되나?

가능은 하지만 추천하지 않는다. 반복 작업은 맥락이 얕아지기 쉽고, 공개 글은 독자 문제와 책 전체 흐름을 함께 봐야 한다. cron은 시작점, 글쓰기는 정리형 에이전트와 리뷰 단계를 거치는 편이 안전하다.

### 왜 방울이와 뽀동이를 나눠야 하나?

방울이는 근거와 맥락을 넓히는 역할이고, 뽀동이는 읽히는 구조와 문장 흐름을 만드는 역할이다. 두 역할을 섞으면 근거는 얕고 문장만 그럴듯한 글이 나오기 쉽다.

### GitHub를 꼭 거쳐야 하나?

WikiDocs를 단순 발행 채널로만 쓴다면 바로 수정할 수 있다. 하지만 책처럼 계속 커지는 콘텐츠라면 GitHub가 source of truth가 되어야 수정 이력, 리뷰, 롤백이 가능하다.
