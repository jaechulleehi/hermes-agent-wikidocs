## 크론 조사에서 WikiDocs 발행까지 이어지는 AI 업무 자동화 케이스

cron 자동화는 [Hermes Agent](https://wikidocs.net/346055)에서 마법처럼 보이지만, 실제 운영에서는 시작점일 뿐이다. 예약된 조사가 곧바로 좋은 글이 되는 것은 아니다. 조사 결과를 하비가 판단하고, 방울이가 확장조사하고, 뽀동이가 WikiDocs 구조로 다시 쓰고, GitHub에 커밋되어야 공개 자산이 된다.

이 케이스는 AI 업무 자동화를 “자동 실행”이 아니라 “자동 시작 후 [역할형 에이전트](https://wikidocs.net/345925)가 이어받는 흐름”으로 보는 방법을 보여준다. 핵심은 cron이 모든 일을 처리하게 만드는 것이 아니라, 반복 신호를 놓치지 않게 하고 이후 판단과 품질 관리는 역할별 흐름으로 넘기는 것이다.

## 실제 업무 상황

주기적으로 확인해야 하는 주제는 [cron](https://wikidocs.net/345926)에 잘 맞는다. 예를 들어 Hermes Agent 공식 문서 변화, AI 에이전트 운영 사례, SEO/GEO 관련 자료처럼 반복적으로 살펴볼 주제가 있다.

하지만 cron은 fresh session에서 돈다. 그래서 프롬프트가 self-contained여야 하고, 결과를 어디로 보낼지, 사람이 무엇을 검토할지, 어떤 기준이면 [WikiDocs](https://wikidocs.net/345908) 후보가 되는지 명확해야 한다.

실제 운영에서는 다음 문제가 자주 생긴다.

- cron 결과가 너무 길어져서 사람이 읽지 않는다.
- 출처는 많지만 “지금 왜 중요한지” 판단이 없다.
- 좋은 신호가 있어도 다음 담당자가 정해져 있지 않아 흘러간다.
- 조사 결과가 Slack에만 남고 WikiDocs나 GitHub로 이어지지 않는다.
- 자동화가 실패했을 때 어디서부터 복구할지 모른다.

따라서 cron 작업은 “매일 알아서 조사해줘”가 아니라 “이 기준으로 신호를 모으고, 이 형식으로 보고하고, 이 조건이면 다음 단계로 넘겨줘”에 가깝게 설계해야 한다.

## 역할 분리

| 단계 | 담당 | 기준 |
|---|---|---|
| 예약 조사 | cron | 정해진 시간에 신호를 모은다 |
| 1차 판단 | 하비 | 지금 다룰 만한 주제인지 본다 |
| 확장조사 | 방울이 | 공식 문서/사례/근거를 보강한다 |
| 구조화 | 뽀동이 | WikiDocs 페이지나 운영 메모로 바꾼다 |
| 실행/검증 | 봉구 또는 실행 흐름 | 파일 수정, 검증, 커밋/푸시를 맡는다 |

이렇게 나누면 cron이 모든 일을 떠안지 않는다. 자동화는 반복 신호를 잡고, 품질은 역할형 에이전트와 검증 흐름이 만든다.

## 좋은 cron 프롬프트의 조건

cron은 미래의 새 세션에서 실행된다. 지금 대화의 맥락을 기억할 것이라고 기대하면 안 된다. 그래서 프롬프트에는 최소한 아래 요소가 들어가야 한다.

| 요소 | 설명 |
|---|---|
| 목적 | 무엇을 감시하거나 수집할지 |
| 범위 | 어떤 출처를 보고 어떤 출처는 제외할지 |
| 판단 기준 | 중요한 신호와 단순 소음을 어떻게 나눌지 |
| 출력 형식 | Slack 보고, 파일 저장, WikiDocs 후보 등 |
| 다음 행동 | 하비 검토, 방울이 확장조사, 뽀동이 정리 중 무엇으로 넘길지 |
| 실패 대응 | 결과가 없거나 도구가 실패했을 때 어떻게 보고할지 |

특히 “결과가 없을 때”의 형식이 중요하다. cron은 매번 큰 발견을 만드는 도구가 아니다. 변화가 없으면 없다고 짧게 말하고, 변화가 있으면 왜 중요한지와 다음 행동을 함께 남겨야 한다.

## 운영 기준

1. cron prompt는 현재 세션에 의존하지 않게 쓴다.
2. 결과는 Slack, local, WikiDocs 후보 중 어디로 갈지 정한다.
3. 조사 결과에는 출처와 판단 근거를 남긴다.
4. 바로 발행하지 말고 하비 또는 사람이 판단하는 지점을 둔다.
5. 글이 될 주제는 방울이 확장조사와 뽀동이 구조화를 거친다.
6. 발행 전 WikiDocs 전자책 검증과 GitHub 커밋을 통과시킨다.
7. 반복 실패는 [복구 플레이북](https://wikidocs.net/345918)이나 skill로 남긴다.

## 예시 흐름

```text
월요일 오전 9시
cron이 Hermes Agent 관련 새 문서, 릴리즈, 운영 사례를 확인한다.

하비
신호를 보고 지금 다룰 만한 주제인지 판단한다.

방울이
공식 문서와 외부 사례를 추가로 확인한다.

뽀동이
독자 문제, 운영 사례, 체크리스트, FAQ 구조로 WikiDocs 초안을 만든다.

봉구 또는 실행 흐름
파일 수정, 링크 검증, 커밋/푸시를 처리한다.
```

이 흐름이 안정되면 cron은 단순 알림 봇이 아니라 콘텐츠 파이프라인의 시작점이 된다.

## FAQ

### cron이 바로 글까지 쓰면 안 되나요?

가능은 하지만 위험하다. cron은 반복 신호 수집에 강하고, 공개 글 품질은 조사/정리/검증이 붙을 때 안정된다. 특히 WikiDocs 글은 독자 흐름, 내부 링크, 전자책 서식까지 확인해야 하므로 바로 발행보다 검토 단계를 두는 편이 낫다.

### 왜 방울이와 뽀동이를 나눠야 하나요?

방울이는 근거와 범위를 넓히는 데 강하고, 뽀동이는 독자가 읽을 구조로 바꾸는 데 강하다. 역할을 나누면 결과가 더 안정된다. 조사형 에이전트의 강점은 [조사형 에이전트는 어디서 강하고 어디서 흔들릴까](https://wikidocs.net/345895)에서, 정리형 에이전트의 강점은 [정리형 에이전트는 어디서 강하고 어디서 흔들릴까](https://wikidocs.net/345896)에서 더 자세히 다룬다.

### GitHub를 꼭 거쳐야 하나요?

이 책에서는 GitHub가 source of truth다. WikiDocs는 공개 배포 채널이므로 원본 이력은 GitHub에 남기는 편이 좋다. 이 흐름은 [GitHub와 WikiDocs로 콘텐츠를 발행하고 고치는 흐름](https://wikidocs.net/345994)에서 실제 케이스로 다시 다룬다.
