## SEO/GEO 치트시트를 콘텐츠 자산으로 만든 실제 케이스

SEO/GEO 치트시트 케이스는 [Hermes Agent](https://wikidocs.net/346055)가 단일 산출물을 만드는 도구가 아니라 콘텐츠 운영 시스템으로 쓰이는 장면을 보여준다. 시작은 이미지 한 장이었지만, 실제 흐름은 Slack 요청, 형식 판단, 이미지 제작, QA, skill화, LinkedIn 본문, WikiDocs 기록으로 이어졌다.

![SEO GEO 치트시트가 콘텐츠 자산으로 이어지는 흐름](../assets/how-image-agent-creates-wikidocs-visuals/ch10-6-linkedin-skill-content-asset-codex.png)

이 케이스의 핵심은 “예쁜 카드뉴스를 만들었다”가 아니다. 반복될 가능성이 있는 제작 기준을 찾아 [Skill](https://wikidocs.net/345904)로 분리하고, 배포 문안까지 이어 붙이고, 시행착오를 다음 콘텐츠의 기준으로 남겼다는 점이다. 그래서 7장의 [WikiDocs/블로그/강의 콘텐츠 시스템](https://wikidocs.net/345911)과 [하망이 이미지 제작 기준](https://wikidocs.net/345989)이 함께 적용된다.

## 프로젝트: 치트시트 한 장을 운영 자산으로 만들기

이 프로젝트에서는 하나의 카드형 콘텐츠를 만들고 끝내지 않는다. 메시지 압축, 이미지 제작 방식 선택, QA, 사용자 피드백, skill화, 배포 문안, WikiDocs 기록까지 이어지는 전체 흐름을 만든다.

## 목표

- SEO와 GEO의 차이를 한눈에 이해되는 구조로 압축한다.
- 창작형 이미지가 아니라 구조형 콘텐츠 이미지가 맞는지 판단한다.
- 결과물을 vision QA와 사용자 피드백으로 개선한다.
- 반복 제작 기준을 skill로 분리한다.
- LinkedIn/블로그/WikiDocs에 맞게 각각 다른 형태로 재사용한다.

## 사전 준비

| 준비 항목 | 설명 |
|---|---|
| 핵심 메시지 | 독자가 저장하고 싶은 한 문장 또는 대비 구조가 있어야 한다 |
| 채널 목적 | LinkedIn용인지, 블로그 삽입용인지, WikiDocs 사례용인지 정한다 |
| 제작 방식 | HTML-to-PNG, 이미지 생성, 다이어그램 중 무엇이 맞는지 고른다 |
| 브랜드 기준 | 색상, 장식, 여백, 톤, 금지 요소를 정한다 |
| QA 기준 | 잘림, 오탈자, 가독성, 모바일 화면, 과한 장식을 확인한다 |

## 시작점

요청은 SEO와 GEO의 차이를 한 장으로 설명하는 치트시트였다. 독자가 한눈에 이해해야 하므로 긴 설명보다 대비 구조가 필요했다. 뽀동이는 메시지를 압축하고, 하망이는 시각 콘셉트를 잡고, 하비는 전체 흐름과 배포 방향을 묶는 구조가 맞았다.

처음부터 [WikiDocs](https://wikidocs.net/345908) 글을 쓰는 작업은 아니었다. 하지만 결과적으로는 WikiDocs에 남길 만한 운영 케이스가 됐다. 이미지 제작 과정에서 브랜드 톤, 금지 장식, 헤더 여백, LinkedIn 본문, CTA, 후속 skill 기준이 함께 생겼기 때문이다.

## 설정 단계

### 1. 메시지를 대비 구조로 줄인다

치트시트는 긴 설명을 담는 문서가 아니다. 저장할 만한 구조가 있어야 한다.

```text
SEO는 검색 결과에서 발견되기 위한 조정이고,
GEO는 생성형 AI 답변 안에서 인용/추천되기 위한 조정다.
```

이 메시지를 기준으로 표, 카드, 흐름도 중 어떤 형식이 맞는지 결정한다.

### 2. 제작 방식을 고른다

| 방식 | 적합한 경우 | 이 케이스에서의 판단 |
|---|---|---|
| 창작형 이미지 생성 | 분위기, 일러스트, 썸네일이 중요할 때 | 텍스트 정확도가 중요해 부적합 |
| HTML-to-PNG | 카드뉴스, 표, 치트시트처럼 글자와 배치가 중요할 때 | 적합 |
| 다이어그램 | 흐름과 관계를 보여줄 때 | 보조 자료로 가능 |

SEO/GEO 치트시트는 글자 정확도와 레이아웃이 중요했다. 그래서 창작형 이미지보다 구조형 HTML-to-PNG가 맞았다.

### 3. 카드 구조를 만든다

```text
상단: SEO vs GEO 한 줄 정의
본문: 비교 표 또는 좌우 대비
하단: 실무 적용 기준 3개
CTA: 저장해두고 콘텐츠 점검 때 보기
```

긴 설명은 카드 안에 넣지 않는다. LinkedIn 본문이나 WikiDocs 페이지가 설명을 맡고, 이미지는 요약과 저장성을 맡는다.

### 4. QA를 진행한다

첫 시안이 나오면 다음을 확인한다.

| QA 항목 | 확인 질문 |
|---|---|
| 가독성 | 모바일에서도 제목과 표가 읽히는가 |
| 잘림 | 하단 CTA나 여백이 잘리지 않았는가 |
| 장식 | 메시지와 무관한 방사형/번쩍임/과한 배경이 없는가 |
| 톤 | HaloX/퇴근후AI 톤과 맞는가 |
| 정확성 | SEO/GEO 정의가 과장되거나 틀리지 않았는가 |
| 재사용성 | 다음 치트시트에도 쓸 수 있는 구조인가 |

### 5. 피드백을 규칙으로 바꾼다

사용자 피드백은 “이번 이미지만 수정”하고 끝내지 않는다. 반복될 가능성이 있으면 금지 규칙이나 QA 기준으로 바꾼다.

```text
피드백: 상단 장식이 과하고 산만하다.
규칙: HaloX 치트시트류에서는 방사형 장식과 과한 광원 효과를 쓰지 않는다.

피드백: 헤더 아래 여백이 답답하다.
규칙: 헤더/서브타이틀/본문 사이에는 충분한 breathing space를 둔다.
```

### 6. skill 후보로 분리한다

같은 유형의 치트시트가 반복될 것 같다면 skill로 만든다.

```text
skill 후보:
- HaloX/퇴근후AI 치트시트 제작 절차
- 메시지 압축 방식
- HTML-to-PNG 레이아웃 기준
- 금지 장식과 여백 기준
- vision QA 체크리스트
- LinkedIn 본문/CTA 작성 기준
```

skill은 결과물이 아니라 반복 절차를 저장하는 곳이다. 한 번 만든 이미지를 저장하는 것과 다르다.

## 운영 흐름

```text
1. Slack에서 치트시트 제작 요청이 들어온다.
2. 하비가 창작형 이미지가 아니라 구조형 HTML-to-PNG가 맞다고 판단한다.
3. 뽀동이가 SEO/GEO 메시지를 입문자용 대비 구조로 줄인다.
4. 하망이 또는 디자인 파이프라인이 세로형 카드 이미지를 만든다.
5. vision QA와 사용자 피드백으로 금지 장식, 여백, 하단 잘림을 수정한다.
6. 반복 가능성이 보이자 전용 skill로 기준을 분리한다.
7. LinkedIn 본문/CTA를 만들고 배포 흐름까지 정리한다.
8. WikiDocs 실제 운영 케이스로 남긴다.
```

## 배포 문안 예시

```text
SEO와 GEO를 같은 말처럼 쓰면 콘텐츠 전략이 흐려집니다.

SEO는 검색 결과에서 발견되는 문제이고,
GEO는 생성형 AI 답변 안에서 인용되고 추천되는 문제에 가깝습니다.

요즘 콘텐츠를 만들 때는 둘 중 하나만 보면 부족합니다.
독자가 직접 찾는 경로와 AI가 답을 구성하는 경로를 함께 설계해야 합니다.

저장해두고 콘텐츠 점검할 때 보세요.
```

같은 내용을 WikiDocs에 넣을 때는 문안이 달라진다. LinkedIn은 저장/공유를 유도하고, WikiDocs는 운영 절차와 기준을 남긴다.

## 시행착오

첫 시안은 깔끔했지만 상단 장식이 원치 않는 인상을 줄 수 있었다. 그래서 방사형 장식을 제거하고, 이후 HaloX 치트시트류에서는 그런 장식을 피하는 기준이 생겼다. 또 헤더 아래 여백이 답답하다는 피드백이 있었고, 헤더/서브타이틀/본문 영역 간 간격을 다시 조정했다.

이 시행착오는 단순 디자인 수정이 아니다. “좋은 이미지”의 기준이 사용자 피드백과 QA를 거쳐 운영 규칙으로 바뀐 순간이다. 다음부터는 비슷한 치트시트를 만들 때 같은 실수를 줄일 수 있다.

## 이 케이스에서 Hermes Agent가 한 일

| 역할 | 한 일 |
|---|---|
| 하비 | 요청을 해석하고 HTML-to-PNG 방향, LinkedIn 본문, CTA 흐름을 판단했다 |
| 뽀동이 | SEO/GEO 메시지를 독자가 저장할 수 있는 구조로 정리했다 |
| 하망이/디자인 파이프라인 | 이미지 제작과 시각 QA를 맡았다 |
| skill | 반복 제작 규칙을 재사용 가능한 절차로 분리했다 |
| WikiDocs | 결과를 공개 운영 케이스로 남겼다 |

## 문제 해결

### 카드가 예쁘지만 정보가 약할 때

메시지를 다시 한 문장으로 줄인다. 치트시트는 장식보다 판단 기준이 중요하다.

### 글자가 많아 가독성이 떨어질 때

카드는 요약만 맡기고, 자세한 설명은 LinkedIn 본문이나 WikiDocs 페이지로 보낸다.

### 매번 비슷한 피드백이 반복될 때

피드백을 skill의 금지 규칙이나 QA 체크리스트로 저장한다. 같은 실수를 반복하면 자동화가 아니라 반복 노동이다.

### WikiDocs에 넣을지 애매할 때

하나의 이미지 결과물이 아니라 판단 기준이 생겼는지 본다. 요청 해석, 제작 방식 선택, QA, skill화, 배포 문안까지 남았다면 WikiDocs 사례가 될 수 있다.

## 판단 기준

- 콘텐츠 산출물은 이미지 하나로 끝내지 않는다.
- 반복될 가능성이 있으면 skill 후보로 본다.
- 사용자 피드백은 감상으로 끝내지 않고 금지 규칙/QA 기준으로 바꾼다.
- LinkedIn, 블로그, WikiDocs는 같은 내용을 복붙하지 않고 채널 목적에 맞게 바꾼다.
- 공유 케이스에는 내부 파일 ID나 보호해야 할 정보가 아니라 흐름과 기준만 남긴다.
- 관련 기준은 [콘텐츠 시스템](https://wikidocs.net/345911), [체크리스트](https://wikidocs.net/345919), [실제 운영 케이스](https://wikidocs.net/345990)에 연결한다.

## FAQ

### 이 케이스는 왜 Hermes Agent 책에 들어가나요?

Hermes Agent가 단순히 답변을 생성한 것이 아니라 요청 해석, 제작 방식 선택, QA, skill화, 배포 문안, 지식화까지 이어지는 운영 흐름을 보여주기 때문이다.

### 카드뉴스 하나를 만들 때도 skill이 필요한가요?

한 번만 만들면 필요 없다. 하지만 같은 형식이 반복되고, 브랜드 톤과 QA 기준이 생기면 skill로 분리하는 것이 좋다.
