## GitHub와 WikiDocs로 콘텐츠를 발행하고 수정하는 흐름

WikiDocs 책을 안정적으로 운영하려면 GitHub가 원본이고 WikiDocs가 공개 채널이라는 기준이 흔들리면 안 된다. 공개 페이지를 바로 고치는 방식은 빠르지만, 책처럼 계속 커지는 콘텐츠에서는 수정 이력과 구조 관리가 약해진다.

이 케이스는 하비가 GitHub와 연결해 콘텐츠를 수정하고, 뽀동이가 글 구조를 정리하고, WikiDocs가 공개본으로 동기화되는 흐름을 다룬다.

## 실제 업무 상황

로이드의 Hermes Agent 책은 한 번 올리고 끝나는 글 모음이 아니다. Slack 대화, 크론 조사, 방울이 확장조사, 뽀동이 정리, 하망이 이미지 제작, 하비 최종 통합이 계속 들어온다.

그래서 발행 기준은 다음처럼 잡는다.

```text
원천 자료 확인
→ BOOK_STRUCTURE/SOURCE_MAP 반영 여부 확인
→ pages 본문 작성 또는 수정
→ TOC 위치 확인
→ README/SEO_GEO 필요 시 보강
→ 검증 스크립트 실행
→ git commit/push
→ WikiDocs 동기화 확인
```

## GitHub를 source of truth로 두는 이유

GitHub를 원본으로 두면 다음이 가능하다.

- 어떤 글이 언제 왜 바뀌었는지 추적할 수 있다.
- TOC, 페이지, 이미지, README, SOURCE_MAP을 한 번에 맞출 수 있다.
- 잘못된 수정이 들어갔을 때 롤백할 수 있다.
- 여러 에이전트가 작업해도 diff로 검수할 수 있다.
- WikiDocs 공개본과 전자책/PDF 기준을 함께 관리할 수 있다.

## 발행 전 확인할 문서

| 문서 | 확인할 것 |
|---|---|
| `TOC.md` | 페이지 위치와 사이드바 제목이 독자 흐름에 맞는가 |
| `BOOK_STRUCTURE.md` | 새 글이 책의 독자 여정과 장 역할에 맞는가 |
| `SOURCE_MAP.md` | 원천 자료와 실제 운영 케이스가 기록되어 있는가 |
| `README.md` | 책 소개와 차별점이 현재 구조를 반영하는가 |
| `SEO_GEO.md` | 검색 키워드와 GEO 질문이 보강되어야 하는가 |
| `pages/*.md` | H1 없이 H2부터 시작하고, FAQ/체크리스트/다음 링크가 있는가 |
| `assets/` | 이미지가 상대 경로로 연결되어 있는가 |

## 발행 기준

새 페이지를 발행하기 전에 다음을 통과해야 한다.

- 제목이 내부 작업명이 아니라 독자 질문 또는 약속으로 되어 있는가?
- 첫 2~4문단 안에 답이 나오는가?
- 공식 기능 설명과 우리 운영 경험이 구분되어 있는가?
- 실제 케이스, 실패 지점, 운영 기준이 들어 있는가?
- 중점 문자를 쓰지 않고 슬래시(`/`)로 구분했는가?
- 민감한 토큰, webhook, 채널 ID, 개인 경로가 제거되어 있는가?
- TOC 링크와 이미지 경로 검증이 통과했는가?

## 수정 기준

이미 발행된 글도 운영 경험이 쌓이면 수정한다. 단, 모든 대화를 바로 본문에 섞지 않는다.

먼저 `SOURCE_MAP.md`나 운영 로그에 다음처럼 남긴다.

```text
주제:
실제 상황:
영향받는 장:
바뀐 운영 기준:
본문 반영 방식:
검증 기준:
```

그다음 관련 페이지를 수정하고, 필요하면 README나 BOOK_STRUCTURE도 함께 갱신한다.

## FAQ

### WikiDocs에서 바로 수정하면 안 되나?

빠른 오탈자 수정은 가능하지만, 구조가 바뀌거나 새 케이스가 들어가는 수정은 GitHub에서 먼저 해야 한다. 그래야 TOC, source map, README, 검증 결과가 함께 남는다.

### 글 하나만 바꿔도 SOURCE_MAP을 수정해야 하나?

단순 문장 수정은 필요 없다. 하지만 새 운영 케이스, 새 장, 새 발행 기준, 공식 문서 연결이 들어가면 SOURCE_MAP에 남기는 편이 좋다.

### 커밋 메시지는 어떻게 쓰면 좋나?

무엇을 왜 바꿨는지 보이게 쓴다. 예를 들어 `Add real operation cases chapter`처럼 구조 변경이 드러나는 메시지가 좋다.
