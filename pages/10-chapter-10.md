## 11장. Hermes Agent AI 업무 자동화 사례

에르메스 에이전트(Hermes Agent)로 AI 업무 자동화를 한다는 말은 “에이전트가 알아서 다 해준다”는 뜻이 아니다. 실제 운영에서는 요청이 들어오고, 메인 창구가 일을 해석하고, 조사형/정리형/실행형/이미지형 에이전트가 역할을 나누고, 마지막에는 검증 가능한 문서나 발행물로 남는다.

![Hermes Agent 실제 운영 케이스 흐름](../assets/images/chapter-heroes/ch10-real-ops-cases-tool-badges-codex.webp)

11장은 그 흐름을 실제 업무 자동화 사례와 AI 자동화 사례로 보여준다. Slack 요청, cron 조사, 방울이 확장조사, 뽀동이 문서화, 하망이 이미지 제작, GitHub/WikiDocs 발행이 어떻게 이어지는지 따라 할 수 있게 정리했다. 앞 장들이 개념과 판단 기준을 설명했다면, 이 장은 “그 기준이 실제 요청에서 어떻게 움직이는가”를 보여주는 실습형 사례 모음이다.

## 이 장을 읽는 방법

각 사례는 결과물 자랑이 아니라 운영 절차다. 그래서 “무엇을 만들었나”보다 “어떤 입력이 들어왔고, 어떤 판단을 거쳤고, 어떤 검증을 통과했는가”를 보면서 읽는 것이 좋다.

| 순서 | 케이스 | 따라 할 수 있는 흐름 |
|---|---|---|
| 11-1 | 하망이와 WikiDocs 이미지 제작 | 페이지 메시지 압축 → 이미지 방향 결정 → 생성/검수 → asset 연결 → 발행 확인 |
| 11-2 | 크론 조사에서 WikiDocs 발행 | 주기 조사 등록 → 하비 판단 → 방울이 확장조사 → 뽀동이 원고화 → WikiDocs 반영 |
| 11-3 | 방울이/뽀동이 handoff | 조사 결과를 링크 묶음이 아니라 주장/근거/반례/독자 질문으로 넘기는 법 |
| 11-4 | GitHub/WikiDocs 발행 | GitHub 원본 관리 → WikiDocs 공개 반영 → 링크/이미지/전자책 규칙 검증 |
| 11-5 | Slack 스레드 분배 | 한 줄 요청 → 하비 라우팅 → 보조 에이전트 작업 → 최종 통합 보고 |
| 11-6 | SEO/GEO 치트시트 자산화 | 이미지 한 장 → QA 기준 → skill화 → 배포 문안 → 운영 케이스 기록 |

## 사례를 읽고 남길 실행 기준

| 산출물 | 확인 질문 |
|---|---|
| 재현 가능한 업무 자동화 사례 | 입력/역할 분리/중간 판단/검증/발행 결과가 모두 보이는가 |
| 역할형 에이전트 handoff 예시 | 방울이 조사와 뽀동이 글쓰기, 하망이 이미지 QA가 이어지는가 |
| 발행/검증 체크리스트 | GitHub 원본과 WikiDocs 공개본을 함께 확인하는가 |
| 다음 자산화 기준 | 결과물이 Skill, 체크리스트, 블로그, 강의 중 어디로 이어질지 정했는가 |

## 먼저 준비할 것

이 장의 사례를 그대로 따라 하려면 모든 도구를 한 번에 갖출 필요는 없다. 다만 아래 네 가지는 미리 결정되어 있어야 한다.

| 준비 항목 | 왜 필요한가 | 관련 장 |
|---|---|---|
| 메인 창구 | 요청을 누가 해석하고 분배할지 정해야 한다 | [AI 개인비서 메인 창구](https://wikidocs.net/345892) |
| 역할 분리 | 조사/정리/실행/이미지 작업을 한 에이전트에게 몰아주지 않기 위해 필요하다 | [역할형 에이전트](https://wikidocs.net/345925) |
| 원본 위치 | 결과물이 Slack에만 남지 않게 하기 위해 필요하다 | [source of truth](https://wikidocs.net/345902) |
| 발행 기준 | WikiDocs/블로그/강의/이미지 중 어디로 보낼지 정하기 위해 필요하다 | [콘텐츠 시스템](https://wikidocs.net/345911) |

처음에는 Slack과 GitHub/WikiDocs만 있어도 충분하다. 이후 반복 주제가 생기면 cron을 붙이고, 반복 절차가 생기면 [Skill](https://wikidocs.net/345904)로 분리하면 된다.

## 공통 아키텍처

```text
사용자 요청 또는 cron 신호
        ↓
하비: 목적/역할/결과물 판단
        ↓
방울이: 근거/사례/반례 확장조사
        ↓
뽀동이: 독자 문제/제목/본문/FAQ/링크 구조화
        ↓
하망이 또는 실행형 에이전트: 이미지/검증/발행 작업
        ↓
GitHub 원본 반영 → WikiDocs 공개 반영 → Slack 완료 보고
```

이 구조에서 중요한 점은 중간에 사람이 판단할 수 있는 지점이 있다는 것이다. cron이 조사 결과를 보내면 하비가 `넘겨/더 파/제품/보류/중복`처럼 다음 액션을 정한다. 이미지가 나오면 하망이가 끝이 아니라 vision QA와 사용자 피드백을 거친다. 원고가 완성되면 뽀동이는 바로 끝내지 않고 링크, H1, 이미지 경로, 중점 문자, 문체를 검증한다.

## 커뮤니티 대화에서 보이는 반복 질문

OpenClaw와 Hermes Agent 운영 커뮤니티 대화를 훑어보면 실제 사용자가 막히는 지점은 고급 기능보다 기본 운영 경계에 몰려 있었다. 이 장의 사례는 그 질문을 Hermes Agent 판단 기준으로 다시 정리해 읽는다.

| 반복 질문 | 이 책에서 연결되는 기준 |
|---|---|
| 어디에 설치해야 하나 | 0장 설치 환경과 9장 보안/격리 |
| API/OAuth/구독제 중 무엇을 써야 하나 | 0장 provider/model/config와 비용 경계 |
| 봇이 갑자기 답하지 않으면 어디를 보나 | 5장 gateway/cron/delivery 진단 |
| Memory.md가 길어지면 어떻게 하나 | 4장 memory/profile/shared-memory/Obsidian/RAG 분리 |
| 남의 Skill을 가져와도 되나 | 6장 Skill 검증과 내부화 |
| 팀 채널에 여러 봇을 넣어도 되나 | 8장 멀티봇 호출/침묵 규칙 |

따라서 실제 운영 케이스는 “우리가 멋지게 쓴 이야기”가 아니라, 독자가 같은 문제를 만났을 때 확인할 수 있는 재현 가능한 판단표여야 한다.

## AI 업무 자동화 사례를 읽을 때 볼 체크리스트

| 체크 항목 | 좋은 사례의 조건 | 나쁜 사례의 신호 |
|---|---|---|
| 시작점 | 요청/cron/자료 변화가 분명하다 | “뭔가 해줘”만 남아 있다 |
| 역할 분리 | 누가 무엇을 맡는지 보인다 | 한 에이전트가 조사/작성/검증을 모두 떠안는다 |
| 중간 판단 | 보류/확장/발행 기준이 있다 | 결과가 많을수록 좋은 것으로 착각한다 |
| 공유 범위 | 보호해야 할 정보와 읽는 사람에게 필요한 정보가 분리된다 | Slack 대화를 그대로 옮긴다 |
| 검증 | 링크/이미지/형식/문체를 확인한다 | 만들었다는 사실만 보고한다 |
| 자산화 | 문서/skill/체크리스트/다음 사례로 남는다 | 다음에 같은 일을 처음부터 다시 설명한다 |

## 바로 써볼 수 있는 요청 예시

아래 요청은 이 장의 사례들을 시작할 때 쓸 수 있는 기본형이다.

```text
하비야, 이 주제를 Hermes Agent 업무 자동화 사례로 만들 수 있을지 봐줘.

1. 방울이는 공식 문서, 실제 운영 사례, 반례를 확장조사해줘.
2. 뽀동이는 WikiDocs 독자가 따라 할 수 있는 구조로 정리해줘.
3. 하망이가 필요한 이미지 방향이 있으면 별도로 잡아줘.
4. 최종 결과는 시작 상황, 운영 흐름, 체크리스트, FAQ, 다음 링크로 정리해줘.
5. 불필요한 세부값이나 보호해야 할 정보는 공개하지 말고 판단 기준만 남겨줘.
```

cron으로 시작할 때는 조금 더 구체적으로 적는다.

```text
매일 오전 8시에 AI 업무 자동화 사례를 조사해줘.
새로운 신호가 있으면 출처, 핵심 요약, 왜 중요한지, 다음 액션 태그를 함께 정리해줘.
다음 액션 태그는 넘겨/더 파/제품/보류/중복 중 하나로 표시해줘.
결과는 Slack으로 보내고, WikiDocs 후보가 있으면 뽀동이가 이어받을 수 있는 handoff 형식으로 정리해줘.
```

## 이 장에서 얻을 기준

- AI 업무 자동화와 AI 워크플로우 자동화는 “완전 자동 작성”이 아니라 “반복 신호를 놓치지 않고 역할형 에이전트가 이어받는 구조”다.
- Slack 대화는 그대로 옮기지 않고 독자 문제, 운영 흐름, 판단 기준으로 재작성한다.
- 콘텐츠로 남길 사례는 source of truth, 본문 링크, 이미지 경로, 전자책 형식을 함께 검증한다.
- 반복되는 절차는 skill이나 체크리스트 후보로 본다.
- 실제 케이스는 보호해야 할 정보가 아니라 상황/판단/기준/결과만 남긴다.

## 책을 마무리하며

이 책의 핵심은 AI를 더 많이 쓰는 법이 아니다. 요청을 해석하고, 역할을 나누고, 근거를 확인하고, 문서로 남기고, 반복 가능한 기준으로 바꾸는 법이다. Hermes Agent는 그 흐름을 하나의 운영 시스템으로 묶는 도구다.

처음에는 하비 하나에게 묻는 것으로 시작해도 된다. 하지만 일이 쌓이면 조사형/정리형/실행형/이미지형 에이전트가 필요해지고, 기억과 source of truth가 필요해지고, 체크리스트와 복구 플레이북이 필요해진다. 11장의 실제 케이스들은 그 전환이 어떻게 일어나는지 보여준다.
