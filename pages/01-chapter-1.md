## 1장. 왜 AI 챗봇이 아니라 AI 팀인가

![01. 왜 AI 챗봇이 아니라 AI 팀인가](../assets/images/chapter-heroes/ch01-why-ai-team-codex-only.png)

처음에는 좋은 AI 챗봇 하나면 충분하다고 생각했다. 질문하면 답하고, 글도 써주고, 코드도 도와주니까 더 좋은 모델을 고르면 일이 풀릴 줄 알았다. 그런데 [Hermes Agent](https://wikidocs.net/346055)를 실제 업무에 붙이면서 문제의 모양이 달라졌다.

답변 하나가 좋아도 다음 일이 계속 남았다. 로이드가 Slack에서 “에르메스 에이전트 블로그가 어디까지 정리됐는지 보고, 링크도 정리해줘”라고 던지면 그것은 단순 요약 요청이 아니었다. 기존 블로그가 빠짐없이 옮겨졌는지 확인해야 했고, 공식 docs와 맞는지 봐야 했고, WikiDocs 독자가 처음 읽어도 흐름이 보이도록 다시 배열해야 했다. 중간에는 본문 내부 링크가 WikiDocs에서 안 먹는 문제도 발견됐고, GitHub 원본과 WikiDocs 공개 페이지의 링크 방식까지 다시 맞춰야 했다.

이때 필요한 것은 “말 잘하는 AI 하나”가 아니었다. 하비가 요청을 받아 전체 흐름을 잡고, 방울이가 부족한 근거를 확장조사하고, 뽀동이가 책의 구조와 문장을 다듬고, 하망이가 이미지 메시지를 잡고, 봉구 같은 실행형이 파일 수정과 검증을 맡을 수 있어야 했다. 사용자는 매번 모든 역할을 세세히 지시하고 싶지 않다. 요청 하나가 들어온 뒤 어떤 역할로 나뉘고 다시 하나로 묶이는지가 중요하다.

이 장은 그 관점 전환을 다룬다. 에르메스 에이전트(Hermes Agent)를 단순 대화 도구가 아니라 [AI 개인비서](https://wikidocs.net/345923), [역할형 에이전트](https://wikidocs.net/345925), 기록과 검증이 함께 움직이는 업무 자동화 운영 시스템으로 이해하기 위한 출발점이다.

## 이 장의 핵심 질문

이 장의 핵심 질문은 단순하다.

```text
왜 좋은 AI 챗봇 하나로는 실무 자동화가 충분하지 않았을까?
```

실제 운영에서 부딪힌 문제는 다음과 같았다.

- 질문은 잘 답하지만, 업무 흐름은 사람이 계속 이어 붙여야 했다.
- 조사, 정리, 실행, 이미지 제작, 기록이 한 대화 안에 섞이면서 실패 원인을 찾기 어려웠다.
- 같은 AI 개인비서처럼 보여도 [profile](https://wikidocs.net/345899), memory, session 상태에 따라 다르게 느껴졌다.
- OpenClaw에서 Hermes로 넘어오며 과거 유산과 현재 기준점이 섞였다.
- WikiDocs처럼 공개 문서로 나가려면 원문 이전, 공식 docs 반영, 내부 링크, 이미지, 검증, GitHub 발행이 한 흐름으로 묶여야 했다.
- 민감정보나 독자가 몰라도 되는 내부 디테일은 제거하고, 대신 운영 판단과 시행착오의 이야기만 남겨야 했다.

## 실제 운영에서 관점이 바뀐 순간

가장 선명한 사례는 이 WikiDocs 책 자체다. 처음 작업은 “블로그 내용을 WikiDocs로 옮기자”에 가까웠다. 하지만 막상 책으로 만들기 시작하자 일이 여러 층으로 갈라졌다.

```text
기존 블로그 1~27편 확인
→ 공식 Hermes Agent docs와 매핑
→ TOC 재구성
→ 본문을 책 문체로 리라이트
→ 개념 허브와 contextual hyperlink 추가
→ WikiDocs page ID 기반 링크로 수정
→ 검증
→ GitHub commit/push
→ 공개 페이지 확인
```

이 흐름은 챗봇에게 “정리해줘”라고 한 번 말해서 끝나는 일이 아니다. 조사형, 정리형, 실행형, 이미지형, 콘텐츠형 판단이 계속 필요하다. 그래서 1장의 메시지는 “AI를 많이 띄우자”가 아니라 “일이 실제로 굴러가도록 역할과 기준을 나누자”에 가깝다.

또 하나 중요한 기준은 민감정보 처리다. 실제 운영 스토리를 넣는다고 해서 토큰, 계정, 개인 경로, 내부 채널 ID, 독자가 몰라도 되는 설정값까지 공개할 필요는 없다. 공개 문서에 남길 것은 “어떤 혼선이 있었고, 어떤 운영 기준으로 해결했는가”다. 세부값은 제거하고, 판단 구조와 재사용 가능한 체크리스트만 남긴다.

## 읽는 순서

먼저 [AI 챗봇과 AI 개인비서는 어떻게 다를까](https://wikidocs.net/345923)에서 대화 도구와 운영 창구의 차이를 잡는다. 그다음 [나만의 AI 팀은 어떻게 구성할까](https://wikidocs.net/345924)에서 역할형 에이전트를 왜 나누는지 본다.

이후 [하비/방울이/뽀동이는 어떻게 읽어야 할까](https://wikidocs.net/345935)에서 하비/방울이/뽀동이/봉구/비벙이/하망이가 각각 어떤 운영 이름인지 먼저 확인한다. 이 안내를 읽고 나면 뒤에서 친구들 이름이 나와도 내부 세계관이 아니라 실제 운영 사례로 이해하기 쉽다.

그다음 [Hermes Agent 주요 개념과 기능](https://wikidocs.net/346055)을 읽으면 memory, session, profile, skill, MCP, cron, gateway, WikiDocs, GitHub가 왜 따로 나뉘는지 보인다. 이어서 [Hermes Agent는 왜 운영 시스템인가](https://wikidocs.net/345890)를 읽으면 이 개념들이 하나의 운영 루프로 묶인다. 마지막으로 [OpenClaw에서 Hermes로 왜 넘어왔나](https://wikidocs.net/345889)에서 이 관점이 실제 전환 과정에서 어떻게 생겼는지 확인한다.

## 이 장에서 가져가야 할 기준

이 장을 읽고 나면 아래 기준이 남아야 한다.

- AI 개인비서는 답변자가 아니라 업무 흐름의 메인 창구다.
- 역할형 에이전트는 캐릭터가 아니라 책임과 실패 패턴을 나누는 방식이다.
- 실제 운영에서는 `방울이 시켜서 확장조사`, `뽀동이가 구조 정리`, `하망이가 이미지 방향 정리`처럼 이름으로 호출한다.
- Hermes Agent는 챗봇보다 운영 시스템에 가깝다.
- OpenClaw에서 Hermes로의 전환은 리브랜딩이 아니라 운영 기준점 재정리였다.
- 실제 케이스를 공개할 때는 민감정보가 아니라 문제, 판단, 기준, 결과만 남긴다.
- 좋은 AI 활용은 프롬프트보다 구조, 기록, 검증, 체크리스트에서 갈린다.
