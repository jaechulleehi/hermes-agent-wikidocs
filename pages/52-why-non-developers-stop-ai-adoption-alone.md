## 비개발자 AI 도입은 왜 혼자 하다 멈출까

비개발자가 AI 에이전트와 바이브코딩 도구를 쓰다 멈추는 이유는 대부분 코드를 몰라서가 아니다. 더 자주 막히는 지점은 “무엇을 만들고 싶은지”, “AI에게 어디까지 맡겨도 되는지”, “결과가 맞는지 어떻게 확인할지”가 정리되지 않은 상태에서 혼자 계속 시도하기 때문이다.

AI 개인비서와 역할형 에이전트를 조직에 도입할 때도 같은 문제가 반복된다. 처음에는 ChatGPT, Claude Code, Cursor, Codex 같은 도구가 신기하게 느껴진다. 하지만 실제 업무에 붙이면 프롬프트 한 줄로 끝나지 않는다. 문제 정의, 자료 위치, 승인 기준, 실패했을 때 물어볼 사람, 다음에 남길 기록이 필요하다.

## 이 글의 답

비개발자 AI 도입은 `딸깍 자동화`가 아니라 **함께 보고 고치는 운영 학습**에 가깝다. 혼자 막히는 이유는 능력이 부족해서가 아니라 피드백 구조가 없기 때문이다.

비개발자가 AI 도입에서 오래 버티려면 아래 네 가지가 필요하다.

- 코딩 문법보다 업무 흐름을 먼저 적는다.
- 완성품보다 작은 반복 업무 하나를 고른다.
- AI가 만든 결과를 확인할 체크리스트를 둔다.
- 막혔을 때 다시 물어볼 사람/에이전트/문서 위치를 만든다.

Hermes Agent는 이 네 가지를 메인 창구, 역할형 에이전트, memory, Skill, WikiDocs/GitHub 기록으로 운영 구조 안에 넣는 방식이다.

## 비개발자는 왜 코드보다 먼저 방향에서 막힐까

비개발자가 AI를 쓰다 멈추는 순간은 생각보다 비슷하다.

```text
ChatGPT로 이것저것 해봄
→ Claude Code나 Cursor로 무언가 만들어봄
→ 처음 화면은 나옴
→ 에러나 수정 요청이 생김
→ 어디를 고쳐야 할지 모름
→ 다시 처음부터 묻거나 포기함
```

겉으로는 코드 문제처럼 보이지만 실제로는 방향 문제일 때가 많다.

- 어떤 업무를 줄이려는지 불분명하다.
- 입력 자료가 어디에 있는지 정리되지 않았다.
- 화면/결과물의 성공 기준이 없다.
- 에러가 났을 때 “무엇을 보여주고 질문해야 하는지” 모른다.
- 한 번 성공한 흐름을 다음에도 다시 쓰게 남기지 않는다.

그래서 비개발자에게 필요한 첫 훈련은 코딩 문법 암기가 아니라 **업무를 AI가 다룰 수 있는 단위로 쪼개는 일**이다.

## `딸깍` 기대가 실패하는 이유

AI 도구는 한 번에 멋진 데모를 보여줄 수 있다. 하지만 업무 자동화는 데모와 다르다. 실제 업무에는 예외, 승인, 민감 정보, 변경되는 조건, 반복 품질이 있다.

`딸깍` 기대가 위험한 이유는 세 가지다.

| 기대 | 실제로 필요한 것 | 운영 기준 |
|---|---|---|
| 한 문장으로 완성된다 | 문제 정의와 입력 자료가 필요하다 | 요청 템플릿 |
| AI가 알아서 고친다 | 오류 메시지와 현재 상태를 보여줘야 한다 | 디버깅 기록 |
| 한 번 만들면 끝난다 | 다음에도 쓸 기준으로 남겨야 한다 | Skill/문서화 |
| 사람이 빠져도 된다 | 승인/검증 지점은 남아야 한다 | 사람 검토 |

Hermes Agent 관점에서는 자동화를 “AI가 대신하는 일”로만 보지 않는다. **AI가 할 일과 사람이 볼 일을 나누는 구조**로 본다.

## 혼자 하지 않는 구조가 왜 중요한가

비개발자에게 가장 큰 장벽은 “이게 맞는 방향인지 모르겠다”는 감각이다. 이때 필요한 것은 더 긴 프롬프트가 아니라 피드백 루프다.

Hermes Agent에서는 이 피드백 루프를 역할로 나눌 수 있다.

| 막히는 지점 | 혼자 할 때 | Hermes식 보완 |
|---|---|---|
| 무엇을 만들지 모르겠다 | 아이디어만 많고 시작하지 못한다 | 하비가 목표/범위를 좁힌다 |
| 자료가 흩어져 있다 | 노션/메일/Slack/파일을 오가다 멈춘다 | 방울이가 근거와 입력 자료를 모은다 |
| 설명이 길어져 산만하다 | AI 답변이 그럴듯하지만 약해진다 | 뽀동이가 흐름과 산출물 구조를 잡는다 |
| 기능 요구가 모호하다 | 만들다 계속 바뀐다 | 비벙이가 요구사항과 검증 기준으로 바꾼다 |
| 실행이 불안하다 | 에러가 나면 멈춘다 | 봉구가 실행/검증/복구 순서를 맡는다 |
| 반복 기준이 없다 | 다음에 같은 일을 다시 설명한다 | Skill과 memory로 남긴다 |

핵심은 에이전트 이름을 늘리는 것이 아니다. 막히는 지점마다 다른 실패 방식을 가진 역할을 붙이는 것이다.

## 조직 도입에서는 왜 더 빨리 무너질까

개인은 어느 정도 머릿속 맥락으로 버틸 수 있다. 하지만 조직에서는 맥락이 사람마다 다르다. 그래서 비개발자 개인이 혼자 막히는 문제가 조직에서는 더 크게 나타난다.

- 누가 요청했는지 모른다.
- 어느 채널의 결과가 최종본인지 모른다.
- 누가 승인해야 하는지 모른다.
- AI가 참고해도 되는 자료와 안 되는 자료가 섞인다.
- 실패했을 때 원인을 다시 찾지 못한다.

따라서 조직의 AI 도입은 도구 교육만으로 끝나면 안 된다. “어떤 업무를 어떤 순서로 맡기고, 어디에 결과를 남기고, 누가 검증하는가”를 운영 문서로 꺼내야 한다.

## 작은 시작: 비개발자에게 맞는 첫 업무

처음부터 앱 하나를 만들거나 전사 자동화를 붙이려고 하면 실패 확률이 높다. 아래처럼 권한이 작고 검증이 쉬운 업무부터 시작하는 편이 좋다.

| 첫 업무 후보 | 좋은 이유 | 주의할 점 |
|---|---|---|
| 회의록을 결정 메모로 바꾸기 | 입력과 출력이 분명하다 | 발언록 요약으로 끝내지 않는다 |
| 리서치 링크를 비교표로 바꾸기 | 검증 가능한 출처가 남는다 | 링크 수집을 결론으로 착각하지 않는다 |
| 콘텐츠 초안을 발행용 구조로 바꾸기 | 사람 검토가 쉽다 | 과장된 문장과 AI 번역투를 줄인다 |
| 반복 문의 답장 초안 만들기 | 자동 발송 없이 시작할 수 있다 | 가격/계약/개인정보는 사람 승인으로 둔다 |
| 개인 업무 대시보드 기획하기 | 앱 제작 전 요구사항을 정리할 수 있다 | 데이터 위치와 업데이트 주기를 먼저 정한다 |

이런 업무는 비개발자도 바로 시작할 수 있고, 실패해도 업무 전체가 망가지지 않는다.

## Hermes Agent로 바꾸면 흐름이 어떻게 달라질까

예를 들어 “고객 문의를 줄이고 싶다”는 요청이 있다고 하자. 바이브코딩 도구만 보면 바로 대시보드나 자동 답장 시스템을 만들고 싶어진다. 하지만 Hermes식 운영 흐름은 조금 다르다.

```text
요청: 고객 문의를 줄이고 싶다
→ 하비: 목표와 위험 범위 정리
→ 방울이: 최근 문의 유형/반복 질문/근거 자료 확인
→ 뽀동이: 문의 유형표/답변 초안/운영 기준 문서화
→ 비벙이: 필요한 기능과 데이터 구조 정리
→ 봉구: 작게 실행 가능한 자동화/검증 순서 제안
→ memory/Skill: 반복 분류 기준과 답변 생성 절차 저장
```

이 흐름을 거치면 “AI가 답장하게 하자”가 아니라 “어떤 문의는 초안만 만들고, 어떤 문의는 사람 승인으로 두며, 어떤 기준은 다음에도 반복되게 남긴다”로 바뀐다.

## 체크리스트

비개발자 AI 도입을 시작하기 전에 아래 질문에 답해보자.

1. 내가 줄이고 싶은 반복 업무는 무엇인가?
2. 그 업무의 입력 자료는 어디에 있는가?
3. 최종 산출물은 어떤 형태여야 하는가?
4. AI가 바로 실행하면 위험한 부분은 무엇인가?
5. 사람이 꼭 확인해야 하는 지점은 어디인가?
6. 한 번 성공하면 다음에도 써야 할 기준은 무엇인가?
7. 그 기준은 memory, Skill, WikiDocs, shared-memory 중 어디에 남길 것인가?

이 질문에 답하지 못한 상태에서 도구부터 붙이면 자동화가 아니라 반복 실험이 된다.

## FAQ

### 비개발자는 코딩 도구를 쓰면 안 되나요?

아니다. 오히려 Claude Code, Codex, Cursor 같은 도구는 비개발자에게도 강력하다. 다만 코딩 도구를 쓰기 전에 업무 흐름, 입력 자료, 성공 기준을 먼저 적어야 한다. 그래야 AI가 만든 결과를 판단할 수 있다.

### 혼자 배우면 안 되나요?

혼자 배울 수는 있다. 하지만 실제 업무에 붙이는 단계에서는 피드백 구조가 필요하다. 사람 동료가 없어도 하비/방울이/뽀동이처럼 역할을 나눠 질문하고 검증하면 혼자 하는 느낌을 줄일 수 있다.

### 조직에서는 교육부터 해야 하나요, 자동화부터 해야 하나요?

작은 자동화 하나를 교육 재료로 삼는 편이 좋다. 추상 교육만 하면 실제 업무에 붙지 않고, 큰 자동화부터 하면 위험하다. 권한이 작고 검증이 쉬운 업무 하나를 고르고, 그 과정을 운영 문서로 남기는 방식이 안전하다.
