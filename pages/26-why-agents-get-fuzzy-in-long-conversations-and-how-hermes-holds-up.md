## 긴 대화에서 컨텍스트는 왜 흐려질까

![긴 대화를 압축 회수 기록으로 정리하는 흐름](../assets/how-image-agent-creates-wikidocs-visuals/ch4-4-long-context-compaction-codex.png)

긴 대화는 편하지만 위험하다. 앞에서 합의한 기준, 완료한 작업, 남은 범위가 계속 쌓이면 AI 개인비서는 모든 것을 기억하는 것처럼 보이다가 어느 순간 흐려진다. 이때 필요한 것은 더 긴 대화가 아니라 작업 범위, handoff, source of truth, 검증 기준이다.

Hermes Agent의 context compaction은 긴 대화를 이어가게 도와준다. 하지만 압축은 마법이 아니다. 무엇을 남기고 무엇을 버릴지 기준이 없으면, 압축된 요약도 잘못된 방향을 오래 유지할 수 있다.

## 컨텍스트가 흐려지는 순간

| 신호 | 실제 위험 | 필요한 조치 |
|---|---|---|
| “아까 말한 것”이 많아짐 | 범위가 암묵적으로 변함 | 현재 작업 목록과 완료 기준 재정리 |
| 여러 장을 한 번에 고침 | 범위 밖 변경이 섞임 | git diff와 대상 파일 검증 |
| 공개 기준이 흐려짐 | 내부값이 본문에 들어갈 수 있음 | 공개 가능한 이야기만 남김 |
| 링크/이미지/TOC가 많아짐 | 기술 검증이 빠짐 | WikiDocs 검증 스크립트 실행 |
| 이전 세션을 기억으로 착각함 | 오래된 진행 상태를 믿음 | session_search나 GitHub 로그로 회수 |

긴 대화의 문제는 AI가 게으르다는 뜻이 아니다. 작업 자체가 여러 층으로 쌓이기 때문에, 중간중간 상태를 다시 고정하지 않으면 판단 기준이 흐려진다.

## 실제 운영 장면: WikiDocs 장별 리라이트

1장, 2장, 3장을 차례로 다시 쓸 때 대화는 길어졌다. 각 장마다 TOC를 확인하고, 이전 세션 맥락을 회수하고, 실제 운영 사례를 공개 가능한 이야기로 바꾸고, 수정 후 검증/커밋/푸시까지 이어졌다.

이 과정에서 다음 장을 시작할 때마다 다시 확인해야 하는 것이 있었다.

1. 현재 HEAD와 origin/main이 같은가?
2. 작업트리가 clean인가?
3. 이번 장의 대상 파일은 어디까지인가?
4. 이전 장에서 반복한 설명을 다시 쓰고 있지 않은가?
5. 공개하면 안 되는 내부값을 사례처럼 남기지 않았는가?

이 확인을 하지 않으면 글은 이어지는 것처럼 보이지만, 실제로는 범위 밖 변경이나 중복 설명이 섞일 수 있다.

이번 책 작업에서도 비슷한 일이 있었다. 4장만 고치려던 흐름에서 5장 실행 방식 페이지와 연결된 변경이 함께 보였다. 그대로 커밋하면 4장 보강 커밋에 다른 장의 수정이 섞일 수 있었다. 그래서 diff를 확인한 뒤 4장 범위 밖 변경은 되돌리고, 4장 파일 5개만 남긴 상태에서 다시 검증했다. 긴 대화에서는 “좋은 수정”도 범위 밖이면 다음 커밋으로 분리해야 한다.

## Hermes가 줄여주는 부분

Hermes는 session_search, memory, skills, profile, cron, gateway 같은 층을 제공한다. 이 덕분에 과거 대화를 찾고, 장기 선호를 유지하고, 반복 절차를 skill로 재사용할 수 있다. 하지만 최종 책임은 운영 기준에 있다.

특히 WikiDocs 작업에서는 다음 순서가 안전했다.

1. 현재 git 상태 확인
2. TOC에서 이번 장 범위 확인
3. 세션 기록과 공용 규칙에서 실제 운영 케이스 회수
4. 공개 가능한 이야기로 추상화
5. 본문 링크와 서식 검증
6. 커밋/푸시 후 clean 상태 확인

이 흐름은 [체크리스트/복구 플레이북](https://wikidocs.net/345921)으로도 이어진다. 장별 리라이트처럼 여러 역할이 이어지는 작업은 [Slack 스레드에서 하비가 일을 분배하는 방식](https://wikidocs.net/345995)과 함께 보면 더 선명하다.

## 운영 기준

- 긴 대화가 이어지면 중간마다 작업 범위와 완료 기준을 다시 쓴다.
- context compaction은 “요약”이지 “검증”이 아니다.
- 커밋 전에는 대상 파일과 범위 밖 변경을 반드시 확인한다.
- memory에는 작업 로그를 넣지 않고, 필요한 경우 session_search나 GitHub 로그로 회수한다.
- 공개 콘텐츠는 내부값 제거 기준을 매번 다시 적용한다.
- 다음 사람이 이어받을 수 있게 완료/남음/다음을 짧게 남긴다.

## FAQ

### context compaction은 언제 필요하나요?

장별 리라이트, 긴 디버깅, 여러 에이전트가 이어받는 작업처럼 맥락이 길어질 때 필요하다. 다만 compaction 후에는 반드시 현재 파일 상태와 완료 기준을 다시 확인해야 한다.

### 긴 대화가 무조건 나쁜가요?

아니다. 긴 대화는 맥락을 쌓는 데 유리하다. 다만 작업이 길어질수록 checkpoint, 검증, source of truth 확인이 필요하다.

### memory에 모든 작업 내역을 넣으면 해결되나요?

아니다. 작업 내역은 memory가 아니라 세션 기록, GitHub 커밋, shared-memory handoff에서 찾는 것이 맞다. memory에는 반복될 선호와 안정적인 규칙만 남긴다.
