## 긴 대화에서 컨텍스트는 왜 흐려질까

긴 대화가 쌓이면 에이전트의 판단은 조금씩 흐려질 수 있다. 이유는 단순하다. 중요한 결정, 임시 작업, 오래 유지할 규칙, 감정 섞인 피드백, 파일 경로, 다음 액션이 한 대화 안에 함께 쌓이기 때문이다.

[Hermes Agent](00-hermes-agent-core-concepts.md)는 session, memory, skill, profile, search, context compaction 같은 장치로 이 문제를 줄일 수 있다. 하지만 장치가 있다고 자동으로 안정되는 것은 아니다. 어떤 정보는 memory로, 어떤 절차는 skill로, 어떤 결과는 repo 문서로 옮겨야 한다.

## 컨텍스트가 흐려지는 순간

긴 대화에서 흔히 생기는 문제는 아래와 같다.

| 문제 | 설명 | 결과 |
|---|---|---|
| 결정이 대화 중간에만 남음 | 중요한 기준이 문서나 memory로 옮겨지지 않음 | 다음 세션에서 다시 설명해야 함 |
| 압축이 반복됨 | 세부 지시가 요약되며 약해짐 | 예외 규칙을 놓칠 수 있음 |
| 임시 작업과 영구 규칙이 섞임 | 오늘 할 일과 앞으로 지킬 기준이 같은 층에 있음 | memory가 지저분해짐 |
| 절차가 skill로 남지 않음 | 매번 같은 검증을 다시 설명함 | 반복 작업 품질이 흔들림 |
| source of truth가 흐려짐 | repo, Obsidian, shared-memory, memory가 섞임 | 무엇을 믿어야 할지 헷갈림 |

컨텍스트 문제는 “더 많이 기억하기”보다 “어디에 남길지 나누기”로 풀어야 한다.

## Hermes가 줄여주는 부분

Hermes Agent는 긴 대화를 버티기 위한 여러 장치를 갖고 있다.

- [session](03-why-same-harvey-feels-like-different-memory.md) search로 과거 대화를 다시 찾을 수 있다.
- memory로 오래 유지할 사용자 선호와 규칙을 남길 수 있다.
- [skill](10-when-and-how-to-manage-skills-in-hermes.md)로 반복 절차를 저장할 수 있다.
- profile로 역할과 도구 경계를 나눌 수 있다.
- [cron](05-daily-briefing-bot-workflow.md)이나 delegation처럼 fresh session에서 실행되는 작업은 self-contained prompt가 필요하다.
- GitHub repo와 WikiDocs를 source of truth로 두면 대화 밖에도 결과물이 남는다.

하지만 이 장치들은 운영 기준이 있어야 힘을 낸다.

## 실제 운영 예시

로이드가 “구분할 때 중점 문자를 쓰지 말고 /를 써”라고 피드백했다고 하자. 이건 단순한 현재 작업 수정이 아니다. 앞으로 모든 WikiDocs/Hermes 글에서 지켜야 할 문체 규칙이다.

그래서 이 규칙은 한 곳에만 두면 안 된다.

```text
현재 원고 → 중점 문자 제거
AGENTS.md → 작성 규칙 반영
skill → 검증 절차 반영
memory → 사용자 선호로 저장
commit → Git 기록으로 남김
```

이렇게 옮겨야 다음 장에서도 같은 실수를 줄일 수 있다.

## 컨텍스트 압축이 필요한 신호

아래 신호가 보이면 context compaction을 고려한다.

- 장별 리라이트와 커밋 내역이 많이 쌓였다.
- 새 규칙이 여러 번 추가됐다.
- 같은 피드백을 다시 받을 가능성이 있다.
- 다음 작업에서 이전 세부 기준을 계속 참조해야 한다.
- 대화가 길어져 답변이 느려지거나 흐름이 복잡해졌다.

압축은 대화를 버리는 일이 아니다. 다음 작업에 필요한 기준만 남기는 정리 작업이다.

## 운영 기준

긴 대화를 안정적으로 이어가려면 아래 기준을 둔다.

- 오래 유지할 선호는 memory에 남긴다.
- 반복 절차는 skill로 옮긴다.
- 현재 프로젝트 기준은 AGENTS.md와 repo 문서에 남긴다.
- 임시 진행 상태는 todo나 Git 상태로 확인한다.
- 중요한 작업은 commit/push로 끊어 간다.
- 압축 전에는 마지막 완료 commit과 다음 작업을 명확히 남긴다.

## FAQ

### context compaction은 언제 해야 하나요?

작업 기준이 많이 쌓였고 다음 장으로 넘어가기 전에 중요한 규칙을 잃을 수 있을 때 하는 편이 좋다. 장별 리라이트가 끝난 시점이 좋은 끊김점이다.

### memory에 모든 작업 내역을 넣으면 안 되나요?

안 된다. memory에는 오래 유지할 선호와 규칙만 넣는다. 작업 내역은 Git commit, SOURCE_MAP, BOOK_STRUCTURE, session history로 남기는 편이 안전하다.

### 긴 대화가 무조건 나쁜가요?

아니다. 긴 대화는 맥락을 많이 담을 수 있다. 다만 결정, 규칙, 절차, 결과물을 적절한 위치로 옮기지 않으면 다음 작업에서 흐려진다.
