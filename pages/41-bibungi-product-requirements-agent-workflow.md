## 비벙이는 아이디어를 제품 요구사항으로 어떻게 바꿀까

제품 아이디어는 처음부터 요구사항 문서가 아니다. Slack에서 나온 한 줄 요청, 고객 피드백, 내부 불편함은 그대로 개발 작업이 되기 어렵다. Hermes Agent에서 비벙이 같은 제품/기능 정리형 에이전트가 필요한 이유는 이 사이를 메우기 위해서다.

이 사례의 핵심은 “좋은 아이디어를 더 많이 모으는 것”이 아니다. 문제를 좁히고, 사용자를 정하고, 해야 할 일과 하지 않을 일을 나누고, 봉구나 개발 에이전트가 이어받을 수 있는 작업 단위로 바꾸는 것이다.

## 시작 상황

새 기능 아이디어는 보통 이런 말로 시작된다.

```text
이거 자동으로 되면 좋겠는데?
```

이 문장만으로는 개발이 어렵다. 누가 쓰는 기능인지, 언제 필요한지, 성공 조건이 무엇인지, 기존 기능과 충돌하지 않는지 알 수 없기 때문이다.

## 맡긴 역할

| 역할 | 담당 |
|---|---|
| 하비 | 요청의 목적과 우선순위를 판단한다 |
| 비벙이 | 문제 정의, 사용자 흐름, 요구사항, 비범위를 정리한다 |
| 방울이 | 유사 도구/공식 문서/경쟁 사례를 조사한다 |
| 뽀동이 | 요구사항 문서를 읽기 좋은 형태로 다듬는다 |
| 봉구 | 확정된 작업 단위를 실행하고 검증한다 |

## 막힌 지점

제품 정리가 실패하는 가장 흔한 이유는 아이디어를 그대로 태스크로 바꾸기 때문이다.

나쁜 예시는 이렇다.

```text
메일 요약 기능 만들어줘.
```

이 요청에는 입력, 출력, 예외, 보안, 검증 조건이 없다. 좋은 요구사항은 기능 이름보다 사용 장면이 먼저 보인다.

## 운영 규칙

비벙이는 아이디어를 아래 순서로 정리한다.

1. 사용자가 겪는 문제를 한 문장으로 쓴다.
2. 이 기능을 쓰는 사람과 쓰지 않는 사람을 나눈다.
3. 입력/처리/출력 흐름을 적는다.
4. 이번 버전에 하지 않을 일을 명시한다.
5. 검증 가능한 완료 조건을 정한다.
6. 봉구나 개발 에이전트가 바로 이어받을 작업 단위로 쪼갠다.

## 따라 하는 방법

```text
비벙아, 이 아이디어를 제품 요구사항으로 정리해줘.

아이디어:
Slack에서 받은 고객 요청을 자동으로 정리해서 답장 초안까지 만들고 싶다.

정리 형식:
1. 해결하려는 문제
2. 대상 사용자
3. 사용 전/후 흐름
4. 요구사항
5. 이번에 하지 않을 것
6. 위험 요소
7. 검증 조건
8. 봉구가 이어받을 작업 목록
```

## 좋은 예와 나쁜 예

| 구분 | 예시 |
|---|---|
| 나쁜 예 | “메일 요약 기능 만들기” |
| 좋은 예 | “최근 24시간 고객 메일 중 답장이 필요한 메일만 분류하고, 초안은 만들되 자동 발송하지 않는다” |

## 체크리스트

- 문제와 기능을 구분했는가?
- 사용자와 사용하지 않을 대상을 나눴는가?
- 이번 버전의 비범위를 적었는가?
- 민감정보/권한/실패 시 처리 기준을 포함했는가?
- 봉구가 실행할 수 있는 작업 단위로 내려왔는가?

## 확장 아이디어

비벙이의 요구사항 정리는 제품 개발뿐 아니라 내부 자동화에도 쓸 수 있다. “매주 리포트 자동 생성”, “WikiDocs 발행 검증”, “이미지 생성 QA” 같은 반복 업무도 문제/흐름/검증 조건으로 바꾸면 Skill이나 cron으로 확장하기 쉬워진다.
